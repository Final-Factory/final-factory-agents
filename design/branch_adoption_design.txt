Branch adoption: tying a conversation to a branch it did not create
==================================================================
Revision 1, 2026-09-06.
Revision 2, 2026-09-06: 5.6, the prefix rule, after Ben asked whether the existing "every
branch ffbox makes starts with ffbox/" validation survives adoption. It did not, and not
because the design dropped it: there is no such validation to drop. The prefix holds today by
construction -- `launch` coerces the name, the harvest rename builds one out of the prefix --
and the only outright refusal guards the mirror, not origin. `push_bundle` pushes whatever it
is given. Adoption is the first path that can hand it a name outside the prefix, so 5.6 turns
the construction argument into a check at the push: outside the prefix, add commits to a
branch origin already has, never create one. Section 14 and the tests in 16 follow it.


1. What this is for
-------------------

An operator has a branch on origin that somebody else made -- another agent's lane run, a
Claude Code session on a laptop, a colleague's push -- and wants to open a thread in
#agent-testing and work on that branch: read it, fix what is wrong with it, add to it, and
have the review happen on the pull request the branch already has.

Today there is no way to say so. A conversation gets its branch by pushing one, and the name
it gets is minted by the harness. `run_ref` starts a first turn at the class's base_ref
(ffwatch.py:6714), the container is checked out on a branch named after the run id
(restore-workspace.sh:152-157), and if the agent checks out `feature/x` and commits there, the
harvest renames the result to `ffbox/feature-x-<run id>` and pushes that instead
(harvest-workspace.sh:134-141). The operator's branch is never touched. What lands on origin
is a second branch carrying a copy of the work, with its own pull request, and nothing in
either one says they are the same change.

This design adds one thing: a conversation may be told which branch it owns instead of
discovering it by pushing.


2. What already works, and why the change is small
--------------------------------------------------

The "one branch per conversation" machinery introduced at schema v12 (ffwatch.py:405-409) is
keyed on a single column, `conversation.branch`, and nothing in it cares how that column came
to be filled. With a value in it:

  * `run_ref` returns the branch ahead of the pinned base and ahead of a per-submission --ref,
    so the run starts standing on it (ffwatch.py:6714-6741);
  * `launch` passes it as --branch and WITHHOLDS --branch-prefix, so the harvest cannot rename
    whatever the agent ends on (ffwatch.py:7199-7201);
  * `publish` refuses to push any other name for that conversation (ffwatch.py:8208-8213);
  * the claim is `UPDATE ... WHERE branch IS NULL`, so a value that is already there is never
    overwritten (ffwatch.py:8244);
  * `reconcile_publication` prefers the owned name over whatever a stranded run harvested
    (ffwatch.py:8517-8528);
  * the container is told in words that it is standing on the conversation's branch and must
    not make another (discord-task.sh:545-562);
  * an open pull request on that branch is reused rather than duplicated (ffwatch.py:8269).

So the feature is: write the column before the first turn launches, and deal with the four
things that assume the column was filled by a push.


3. Two tiers
------------

The work splits by the NAME of the branch being adopted, because two fences in the publish
path are drawn around the `ffbox/` prefix and around commit identity.

TIER A -- the branch is already under `branch_prefix` (`ffbox/...`). This is the common case:
resuming a branch an earlier lane run left behind, after its thread was closed or its turn
ceiling rotated. Sections 4, 5, 6, 7, 10, 11 and 12 apply. Nothing in the mirror path or the
harvest changes.

TIER B -- the branch has a foreign name (`feature/x`, `loth/save-fix`, anything a person or a
non-ffbox agent pushed). Everything in Tier A, plus sections 8 and 9. Section 9 is the one
with teeth: without it every turn on such a branch refuses to publish.

Both tiers ship together. Tier A is separated out because it is the half that can be built
and tested first, and because a box that only ever adopts `ffbox/` branches never exercises
sections 8 and 9 at all.


4. The adoption record
----------------------

Two columns on `conversation`, added to `ADDED_COLUMNS` (ffwatch.py:316) beside the v12 block,
with `SCHEMA_VERSION` going 15 to 16:

    ("conversation", "branch_adopted_at", "TEXT"),
    ("conversation", "branch_adopted_by", "TEXT"),

`branch_adopted_at` NULL means the branch was claimed by a push, which is every conversation
that exists today and every one opened without a directive. Not-NULL means the branch was
adopted, and it is the flag the rest of this design reads: the mirror routing in section 8,
the range flag in section 9, and the page in section 12.4. `branch_adopted_by` is the Discord
snowflake or unix login of whoever adopted it, kept for the same reason `run.branch_existed`
is kept (ffwatch.py:429-434): when somebody later asks why a run's commits are sitting on a
stranger's branch, the record answers without anyone reading a log.

No new config keys, so `ffbox/config.md` is unchanged. That is deliberate: everything here is
per-conversation, and a box-wide switch for it would only be a way to turn off a feature
nobody has to use.


5. Validation: what may be adopted
----------------------------------

Adoption happens in one function, `adopt_branch(conv_id, branch, by)`, and both ingresses call
it. It refuses rather than adapts, and every refusal carries the reason back to whoever asked.

  1. `git check-ref-format --branch <name>` passes. Same check restore-workspace.sh:153 makes
     before creating one, made earlier so the answer arrives in the thread instead of in a
     container's stderr.

  2. The name is not protected and is not a key of `publish_bases`. A run that ended on master
     is already refused at harvest (harvest-workspace.sh:128-132) and again on the host
     (ffbox:1694-1699); adopting master would produce a conversation every turn of which fails
     at the very end. Refuse at the start. ffwatch has no list of protected names today -- it
     lives in `ffbox` as `PROTECTED_BRANCHES` (default `develop master main`) and reaches the
     container as FFBOX_PROTECTED_BRANCHES -- so this adds a mirrored constant with a comment
     naming ffbox as the original, the way `ffweb.py` mirrors `LOCAL_KINDS`.

  3. `refs/remotes/<push_remote>/<name>` resolves in `git_dir` after a fetch. This is the
     check that the branch EXISTS on origin, and it doubles as proof that the golden checkout
     can see it, which section 9 needs at publish time.

  4. No other conversation owns it:
     `SELECT id FROM conversation WHERE branch=? AND state<>'closed'`. One branch, one
     conversation, in both directions. Adopting a CLOSED conversation's branch is allowed and
     is the Tier A case; adopting a live one's would give two threads a shared branch and two
     agents a race for a fast-forward.

  5. This conversation owns no branch and has no run that pushed. Re-pointing a conversation
     that has already published would strand its pull request against a branch its next turn
     no longer touches. Say so and stop.

On success: write `branch`, `branch_adopted_at`, `branch_adopted_by`, and, for Tier B, run the
mirror sync of section 8 immediately so that a mirror problem is reported now rather than at
the launch of the first turn.

5.6 The prefix rule, and where it has to be enforced

Every branch ffbox creates on origin is under `branch_prefix` (`ffbox/`, ffwatch.py:531). That
must keep being true, and adoption is the first thing in the pipeline that can put a name
outside the prefix in front of the push.

What holds it today is construction rather than a check, which is worth being precise about
before changing anything. `launch` COERCES a name it is given into the prefix
(ffwatch.py:7012-7013). The harvest rename builds the published name out of the prefix, the
sanitised branch name and the run id (harvest-workspace.sh:134-141). The one outright refusal
is in `mirror_take` (ffwatch.py:6799), and it guards the MIRROR rather than origin.
`push_bundle` pushes whatever name it is handed (ffwatch.py:8743), and the host's
re-derivation checks protected names and ref format but not the prefix (ffbox:1694-1701).
Nothing needed a check while nothing could produce an unprefixed name. Adoption can, so the
guarantee has to move from construction to a check.

THE RULE. ffbox may CREATE a branch on origin only under `branch_prefix`. Outside the prefix
it may only ADD COMMITS to a branch that is already there.

Enforced in `push_bundle`, after the fetch it already does and before the push: when the name
is not under `branch_prefix`, `refs/remotes/<push_remote>/<name>` must resolve, or the run
refuses with `_no_branch` and says the branch is not on origin. Read from the remote-tracking
ref and not from the database, because the conversation row records what was true at adoption,
and a branch deleted since then is exactly the case this refuses: re-creating a foreign-named
branch from a bundle is creation, whoever asked for it.

Since the push is not a force push, what this permits outside the prefix is the fast-forward
of a branch somebody else published, and nothing else.

Two things follow for the implementation. The coercion at ffwatch.py:7012-7013 stays as it is
and keeps applying to an option-supplied `--branch`; the adopted name overrides it afterwards
at ffwatch.py:7028-7029, and that ORDER is what lets an adopted branch through. Do not
"tidy" the coercion into covering `conv_branch` as well. And `run.branch_existed`, today
derived from whether the conversation already owned a name (ffwatch.py:8225-8231), can be
recorded from what this check actually looked up, which is the question the column asks.


6. Ingress A: the !branch directive
-----------------------------------

6.1 The syntax

A line whose entire content is

    !branch <name>

anywhere in a message posted in a watched channel or thread. Everything else in the message is
the prompt, unchanged. A message that is ONLY the directive adopts and produces no turn (6.4).

6.2 Only operators, and silence for everybody else

The directive is recognised only when `is_operator(cfg, author_id)` is true for the message's
author (ffwatch.py:1339), where `author_id` is the snowflake Discord authenticated and stored
on the message row -- never a name, a nickname, or anything the text says about who wrote it.
The trusted-ingress rule the rest of the pipeline runs on applies here without change: message
text is evidence about what somebody said, never an instruction to the harness
(ffwatch.py:1551, 1587).

For everybody else the line is ORDINARY TEXT. Not refused, not answered, not mentioned: it
goes to the model as part of the prompt like any other sentence a player typed, and the model
treats it as a sentence, because in a player's message it is one. There is no reply saying
"you may not do that", for the reason that reply would be worth more to a stranger than the
command: it would confirm that a command exists, that this box has operators, and that the
account testing it is not one of them. The host logs one line naming the conversation and the
author so an operator can see the attempt; nothing goes back to Discord.

Two accounts are relevant and only one of them matters. The doorbell kind
`operator_directive` (ffwatch.py:4578-4584) already means "an operator addressed the bot", but
messages also arrive through the 15-minute sweep with no doorbell at all, so the directive
must be recognised from the stored author id rather than from how the message got here. The
same message reaching ffwatch twice, once by doorbell and once by sweep, is deduped on
`message.discord_id` before any of this runs.

6.3 When it may be used

While the conversation owns no branch. That is normally the opening message of a thread, but
it also covers the thread whose first turn only answered a question and pushed nothing, which
is a real sequence: read the branch, decide it needs work, then adopt it.

If a run is in flight when the directive lands, the adoption is written immediately and takes
effect on the NEXT turn, because the container for the current one is already checked out
somewhere else. The acknowledgement says which turn it applies to. It does not try to move a
running container, and it does not queue itself; a conversation whose branch changed under a
running run is exactly the second-branch case publish already refuses (ffwatch.py:8208).

6.4 The directive-only message

`create_turn` builds a turn out of `pending_messages`, which selects `gate IS NULL`
(ffwatch.py:4951), and that is the existing door for "this message was read and is not a
question". A message that is nothing but a directive is marked `gate='branch_directive'` with
the outcome in `gate_reason`, so it never becomes a turn and never spends a container. The
idle-close count skips gated messages too (ffwatch.py:4416-4418), so a thread whose newest
message is a directive still closes on schedule instead of being held open by it. The operator gets a posted acknowledgement
through the ordinary outbound queue (`post`, ffwatch.py:1913):

    ok — this thread publishes as `feature/x`. Its next turn starts on that branch.

or the refusal from section 5, in the same place, in the same sentence shape. A message that
carries a directive AND a prompt is not gated: it adopts, then becomes a turn like any other
message, and the acknowledgement rides along in that turn's reply rather than being posted
separately.

6.5 Where it is parsed

Inside `insert_message` (ffwatch.py:3692), after the `rowcount == 0` early return that drops
duplicates and beside `demote_for_stranger`, which is the other thing decided per new message
about who is speaking. One place covers every ingress -- doorbell, sweep, operator DM -- and
the rowcount check is what stops a re-read of a thread from re-adopting or re-posting.

That is also early enough. Ingest and `claim_turns` run in the same poll pass, ingest first, so
the column is on the conversation row before anything schedules a turn against it. Parsing
later -- in `create_turn`, or in `launch` -- would mean the first turn of an adopted thread
launches on the wrong ref and then has to be thrown away.

Not on the local ingress. `is_operator` looks a value up in a table of Discord snowflakes, and
`submit()` writes the unix uid as the author id; a login that happens to be all digits must
never be looked up there, which is the warning `upsert_conversation` already carries
(ffwatch.py:3617-3620). A local conversation reaches adoption through `ffwatch adopt` and
nothing else.


7. Ingress B: ffwatch adopt
---------------------------

    ffwatch adopt --conversation N --branch feature/x [--json]

A subparser beside `close` (ffwatch.py:11343), calling the same `adopt_branch`. It exists for
three jobs the directive cannot do: adopting into a LOCAL conversation (`ffwatch submit` has
no Discord thread to type a directive into), repairing a thread where the directive was
mistyped, and being the thing the tests drive without a Discord fixture.

It prints the refusal reasons of section 5 to stderr and exits non-zero, so a script can tell
whether it worked.

`ffwatch submit --branch` keeps its present meaning, which is different and should stay
different: it names the branch a NEW run STARTS on, under the `ffbox/` prefix, for a
conversation that owns nothing (ffwatch.py:7007-7013). Adoption is about a branch that already
exists on origin. Two different questions, two different flags.


8. The mirror (Tier B)
----------------------

A container resolves --ref against the local mirror and nothing else
(restore-workspace.sh:115-121). `mirror_carries` asks whether a branch is there
(ffwatch.py:6747), and `mirror_take` puts one there from the golden checkout -- but only for
names under `branch_prefix`, and it says why: it must not be able to move a branch CI reads
(ffwatch.py:6794-6801). An adopted `feature/x` fails that fence, which means it fails the
launch guard at ffwatch.py:7028-7046, which means every turn of the conversation dies with
BranchUnavailable.

Add a sibling rather than widening the fence:

    mirror_sync_from_origin(branch)
        git -C <git_dir> fetch --quiet <push_remote>
        git -C <git_dir> push <mirror> +refs/remotes/<push_remote>/<branch>:refs/heads/<branch>

The fence on the new function is different from `mirror_take`'s, and that difference is the
argument for it. `mirror_take` pushes a ref the RUN produced, so an unprefixed name there
would let a run's own work stand in the mirror as somebody else's branch. This function can
only ever write the value origin already has, so the worst it can do is make the mirror agree
with GitHub sooner than the CI runners' fetch would (runners/lib/mirror.sh:77-81). It keeps
the protected-name refusal anyway, because a mirror whose `develop` moves outside the runners'
control is a debugging problem nobody should have to have.

Two call sites:

  * At adoption (section 5), so a branch the mirror cannot be given is reported in the thread.
  * At EVERY launch of an adopted conversation, not only when `mirror_carries` says no. This
    is the half that makes the workflow usable: it means an operator can push a commit to the
    branch from their own machine between two turns, and the next turn starts on top of it
    rather than on a stale copy. For a `branch_adopted_at IS NULL` conversation nothing
    changes -- `mirror_take` stays exactly as it is, and its cheap local push stays the repair
    path for an ffbox branch missing from the mirror.

The post-publish `mirror_take(branch)` at ffwatch.py:8248 routes to whichever of the two suits
the name, so an adopted branch's new head reaches the mirror the same way an ffbox branch's
does.


9. The bundle range and the identity fence (Tier B)
---------------------------------------------------

9.1 What breaks

Harvest picks the range base as the most specific of --base-refs that is an ancestor of HEAD
(harvest-workspace.sh:88-110), which is `origin/develop` or `origin/master`, not where the run
started. Everything downstream is measured from there:

    _foreign=$(git log --format='%ae%n%ce' "${_hbase}..${_tip}" | grep -Fxv "$FFBOX_GIT_EMAIL")

in the container (harvest-workspace.sh:148-150) and again on the host, re-derived from the
bundle (ffbox:1741-1748). On an adopted foreign branch that range contains the commits the
other agent made, wearing the other agent's identity, so every turn refuses to publish with
"commits claim an identity this run does not own". The changed-file ceiling
(ffbox:1769-1772) has the same defect from the other direction: it counts the whole adopted
branch, so adopting a large branch can blow a limit meant to bound what one run did.

9.2 The change

Split two things that are currently one value.

WHICH NAMED BRANCH THE WORK IS FOR keeps coming from the --base-refs scan and keeps being
written to publish_base.txt, because `pr_base` reads it to aim the pull request
(ffwatch.py:8372-8410). Nothing about that changes.

WHERE THE BUNDLE RANGE STARTS becomes the commit the run was checked out at, under a new flag:

    ffbox --range-from-start   ->   FFBOX_RANGE_FROM_START=1

added to the cold `-e` list (ffbox:1204-1215) and to the dispatch env file (ffbox:1387-1396)
so the two paths carry the same names, as they already do for every other FFBOX_ variable.
`launch` passes it when `branch_adopted_at` is set. In harvest, after the --base-refs scan
sets PUBLISH_BASE, the flag replaces PUBLISH_BASE_SHA with $BASE_SHA -- the sha
restore-workspace.sh recorded when it finished preparing the tree -- subject to the ancestry
test that is already there:

    git merge-base --is-ancestor "$BASE_SHA" HEAD

If that fails the run refuses to publish and says the work does not descend from the commit it
started at, which is the honest answer: something rewrote history under the run.

Then the range is exactly this conversation's own commits. Identity passes because those
commits are ffbox's. The ceiling counts this run's files. The push is a fast-forward from the
adopted head, so origin accepts it (ffwatch.py:8743).

9.3 Why this does not weaken the fence

The fence exists so that a commit wearing a person's name cannot ride out on a branch a
reviewer reads by author (ffwatch.py:1724-1726). It still covers every commit the run made; it
stops being asked about commits that were on origin before the conversation opened, which is
the correct scope, because those are genuinely that person's commits and they are already on
origin under their own name.

The container writes publish_base_sha.txt and could name a different base, but that was true
before this change and the host's check on it is unchanged: the bundle must verify against the
mirror (ffbox:1720-1724), so the named base has to be a commit the mirror already has. A
container cannot hide a commit it just made by naming a base below it, because no commit in
the mirror is a descendant of a commit that did not exist until this run. The set of bases a
container can get away with naming is the same before and after; the flag only changes which
one the honest path picks.

9.4 One consequence for the page

`ffweb._branch_note` documents that each publishing run bundles the whole branch against the
base, so the newest run's file count is the branch total (ffweb.py:2725-2740). For an adopted
conversation that stops being true: the count is per-turn. The docstring and the rendering
both need to say which they are showing, and for an adopted branch the per-turn number is the
more honest one anyway -- the cumulative figure there would be counting somebody else's files.

Ordinary conversations keep the present behaviour. Flipping the range for all continuations
would be a bigger and separate change, and would silently rewrite what that page has always
meant.


10. Pools: an adopted branch never takes a warm container
---------------------------------------------------------

Stated as a rule: a turn whose ref is a branch NAME that is not the branch its pool is staged
on gets a cold container. It never checks out the divergence inside a warm one.

Mostly this is what `pool_claim_for` already does. It matches on class and on branch, skipping
any warm container whose staged branch is not the one wanted, and a miss falls through to a
cold launch and is not an error (ffwatch.py:5990-6019). An adopted branch matches no pool,
because pools are staged on `pool_branch`, which follows the class's base_ref
(ffwatch.py:5271-5275), and staging a pool on one operator's branch would serve one
conversation and nothing else.

Two things to fix so the rule is true rather than accidental.

FIRST, the scheduler's pre-check asks about a different ref than the one `launch` will use. At
ffwatch.py:6095-6099 the ceiling is skipped when `pool_would_serve` says a warm container
exists, and the ref it passes is `turn_options.ref or conv_base_sha or class base_ref`. It
never consults `conversation.branch`. From turn 2 onward `conv_base_sha` is a pinned sha
(ffwatch.py:7344-7348), `looks_like_sha` is true, and `pool_would_serve` answers yes for any
warm container of the class (ffwatch.py:6033-6034) -- while `launch` then asks
`pool_claim_for` about the conversation's branch, misses, and cold-launches. On a full box
that is a run started past a ceiling that had no room for it. This predates adoption and
adoption makes it routine, so the fix belongs here: give both sides one function, the ladder
in `run_ref`, and let the pre-check ask about the ref the launch will actually use.

SECOND, a warm container must never be dispatched a turn whose branch it is not staged on,
even if some future caller asks. Keep that as an assertion in `launch` rather than a comment:
if `pool_claim_for` returned a container, its branch equals the ref, or the container goes
back and the turn cold-launches.

The cost is a cold start per turn, which is what every continuation of every conversation
already pays today for the same reason. It is not a new expense and it should not be described
as one in the reply or on the page.


11. What the agent is told
--------------------------

`preamble_branch` (discord-task.sh:545-563) tells a continuation that it is standing on the
conversation's branch, that the commits under it are earlier turns' work, and that it must not
branch or switch. All of that is right for an adopted branch except whose commits those are.
The job carries `bases.conversation_branch` already (ffwatch.py:6420); add
`bases.branch_adopted`, and when it is set say the true thing instead:

    You are on `<branch>`, which this conversation did not create. The commits on it are
    somebody else's work and the harness publishes back onto this branch by name whatever
    HEAD ends on, so read it before you change it -- `git log` and `git diff` against
    `origin/<base>` -- and add commits on top. Do not branch, do not switch, do not rebase,
    revert or amend what is already there.

`preamble_bases` needs nothing. It already short-circuits when the conversation owns a branch
and reports the base from `checked_out_base` (discord-task.sh:585-591), and `base_containing`
answers for an adopted branch exactly as it does for an ffbox one (ffwatch.py:8301).

The rebase sentence is worth having even though the container has no rebase available: the
model does not know that, and the failure it would otherwise try is the one that loses the
operator's branch.


12. Pull requests, replies and the page
---------------------------------------

12.1 An existing open PR is reused. `publish` looks one up for the branch before creating
anything (ffwatch.py:8269), so a thread adopted onto a branch that already has a pull request
comments and pushes into that PR rather than opening a second. This is the behaviour that
makes the review half of the workflow work, and it needs no change.

12.2 A PR closed without merging stays closed. `publish` refuses to reopen it and records why
(ffwatch.py:8276-8285). A human closing a pull request is a decision, and adoption does not
get to overturn it. The reply says the branch was pushed and no PR was opened, with that
reason.

12.3 The PR base is still master or develop, decided from the commit graph, not from the
adopted branch. An adopted branch that descends from neither gets no pull request and the
reason `pr_base` already writes (ffwatch.py:8410-8412). That is the right answer: a branch
based on something else is not a proposal this pipeline knows how to aim.

12.4 The page shows adoption. `_branch_note` (ffweb.py:2725) renders the branch for a
conversation that has one; for an adopted conversation it should say so and who did it, so
that a reviewer looking at a thread whose branch predates it is not left inferring. One word
and a name, not a row.


13. Failure modes, and the operator's side of the bargain
----------------------------------------------------------

CONCURRENT PUSHES. If the branch moves on origin while a turn is running, that turn's push is
a non-fast-forward and origin rejects it. The work survives in the run directory and
`reconcile_publication` will retry it (ffwatch.py:8461), but it will keep being rejected until
the branch is a fast-forward again. The launch-time mirror sync of section 8 narrows the
window to one run's duration; it cannot close it. The rule is: while a thread owns an adopted
branch, do not push to that branch from anywhere else while a turn is in flight. `push_bundle`
should say that in the failure text rather than only relaying git's stderr (ffwatch.py:8744-8745),
because the git message alone sends people looking in the wrong place.

THE BRANCH IS DELETED OR MERGED. A merged pull request takes its branch with it. The next turn
raises BranchUnavailable and says the branch is in neither the mirror nor the host checkout
(ffwatch.py:7042-7046). The message already tells the operator what to do: put the branch back,
or close the conversation so the next message starts a fresh one. Adoption adds a third option
worth naming in that text -- adopt a different branch -- but only for a conversation that has
not published, which by then it has. Leave the message as it is.

A STRANGER POSTS IN THE THREAD. `demote_for_stranger` moves the conversation to the fenced
class (ffwatch.py:3749) and the branch claim is untouched, so the work continues on the same
branch in a container with a different network and different clocks. In a private
#agent-testing that should not happen; it is written down because it is the one thing that
changes a conversation's class after birth.

ADOPTING SOMETHING ENORMOUS. Nothing here bounds the size of the branch being adopted, and
nothing needs to: the ceilings that matter bound what a RUN changes, and section 9 makes them
measure exactly that.


14. What this does not do
-------------------------

No conversation ever gets a second branch. No push becomes a force push. No protected branch
becomes publishable. No commit the harness makes may wear a person's identity. No branch
outside `branch_prefix` is ever created by ffbox; outside the prefix it can only add commits
to a branch that is already on origin (5.6). A stranger's message cannot adopt, redirect, or
name a branch. Those are the properties the existing fences hold, and every section above is
arranged so that they still hold afterwards.

There is no "detach" and no "re-adopt". A conversation that has published is on its branch for
life; if the branch was the wrong one, close the thread and open another. That is the same
answer the harness already gives for every other way of getting the branch wrong, and a
detach would exist mainly to be used at the worst possible moment.


15. Build order
---------------

  1. Schema, `adopt_branch` with the section 5 validation, the push-time prefix check of 5.6,
     `ffwatch adopt`. TIER A WORKS at the end of this step: a conversation pre-seeded with an
     `ffbox/` branch starts on it, cannot be renamed, and publishes onto it. The prefix check
     belongs here rather than with Tier B even though only Tier B can trip it, because a fence
     that arrives after the thing it fences is a fence nobody tested.
  2. The pool rule of section 10: one ref ladder shared by the scheduler's pre-check and
     `launch`.
  3. `mirror_sync_from_origin` and its two call sites (section 8).
  4. `--range-from-start` through ffbox into harvest (section 9). TIER B WORKS at the end of

16. Tests
---------

In test_ffwatch.py, alongside the branch tests that already exist there (10081, 10163, 10356,
10411):

  * an adopted conversation launches on the adopted branch, and its ffbox argv carries
    --branch <name> and NO --branch-prefix, on its FIRST turn;
  * adoption is refused for: a protected name, a publish_bases name, a name origin does not
    have, a branch another open conversation owns, and a conversation that has already pushed;
  * a non-operator's `!branch` line adopts nothing, produces no reply, and the message becomes
    an ordinary turn;
  * an operator's directive-only message adopts and creates no turn;
  * a turn on an adopted branch is not handed a warm container staged on develop, and the
    scheduler's pre-check agrees with `launch` about which ref it asked about;
  * `mirror_sync_from_origin` refuses a protected name and writes only the value origin has;
  * THE PREFIX RULE (5.6): a publish of a name outside `branch_prefix` that origin does NOT
    have is refused and leaves no branch; the same name once origin has it is pushed; and a
    conversation that adopted nothing still cannot reach the push with an unprefixed name at
    all, whatever the run harvested.

Against the shell, using `run_harvest` and `seed_agent_repo` (test_ffwatch.py:7187-7259):

  * with FFBOX_RANGE_FROM_START set, a repo whose history below the run's start carries a
    foreign author publishes cleanly, and publish_base.txt still names the right base;
  * with the flag set, a commit the RUN made wearing a foreign identity is still refused;
  * without the flag, behaviour is byte-for-byte what it is today.

Whatever `test_every_task_script_harvests_its_own_workspace` (test_ffwatch.py:5790) asserts
about the task scripts has to keep passing with the new flag threaded through both env paths.
