ffbox: a fetch phase that holds the credential, and an agent phase that does not
================================================================================

2026-08-30.

An ffbox run gets its workspace from a ZFS clone of /opt/FinalFactory, and golden exists because
the agent container cannot fetch: ffbox-net reaches Anthropic and Unity and not GitHub, and no git
credential goes inside. So the host keeps a full checkout current and clones it.

This replaces that with two containers. The first has GitHub and a credential and builds the
workspace. The second has neither and runs the agent. They share one directory on a host tmpfs.

Nothing about the agent's own reach changes: it keeps Anthropic and Unity, exactly as now. What it
loses is GitHub, which it never had.


1. What this removes
--------------------

  - The ZFS snapshot and clone on the run path, and the golden lock contention that comes with it.
  - 04-warmLibrary.sh entirely. The cache entry IS the warm workspace; there is nothing to warm.
  - The delta bundle of design/ffcache_design.txt, and the host-side plumbing that builds it.
  - Finding F7's remaining surface: the host never reads a tree a container wrote, because the
    workspace is a tmpfs the host does not run git in.
  - Roughly 9 GB, once golden stops needing a worktree and a Library.

What it does NOT remove is golden itself. Section 7.


2. The two phases, in ONE container
-----------------------------------

    fetch    the container starts dual-homed on ffghr-net and ffbox-net, --dns at the CI proxy,
             holding a short-lived GitHub credential. It restores the cache entry if one matches,
             fetches, and checks out the wanted commit. Our script, not model output.

    agent    the host disconnects ffghr-net and repoints /etc/resolv.conf at the agent proxy. The
             entrypoint unsets the credential and execs claude -p. GitHub is now unresolvable and
             unroutable; Anthropic and Unity are unchanged.

MEASURED ON 2026-08-30, in that order: github.com reachable while dual-homed, then blocked after
the disconnect, with api.anthropic.com and license.unity3d.com still reachable.

THE DISCONNECT IS THE ENFORCEMENT, not the resolv.conf edit. Disconnecting the network makes the
CI proxy unreachable whatever the container's resolver says, and the container cannot reverse it:
it holds no docker socket. Rewriting resolv.conf afterwards is plumbing — without it the container
keeps asking a proxy that is no longer there, and everything fails rather than just GitHub. That
is what --dns being fixed at creation costs, and it is a repair rather than an obstacle.

THE CREDENTIAL DROPS BECAUSE OUR SCRIPT RUNS FIRST. The entrypoint fetches, unsets, and only then
execs the agent, so the agent never sees it. That ordering is the whole guarantee; it does not
survive if anything the agent influences runs before the unset.

THIS DOES NOT APPLY TO CI, and the reason is not caution. A runner needs GitHub for its entire
life: it long-polls the broker for work, streams step results as they happen, uploads artifacts,
and deregisters at the end. The egress log for one real job shows results-receiver hit six times
across the run and pipelinesghubeus14 seven. Blocking GitHub after checkout would leave a job
unable to report that it passed. CI keeps its fence exactly as it is.

3. The workspace
----------------

One tmpfs per run, mounted by the one container that uses it — the same --tmpfs the CI runners
already use, at the same size. Nothing is shared between containers and nothing crosses a
container boundary, which is the simplification the single-container shape buys.

A host-side shared directory WAS the earlier plan, when this was two containers. It works — two
containers on different fences reading one host tmpfs was measured — but it needs the directory
created, owned by the container account, bind-mounted twice and removed on every exit path. None
of that is needed now.

Worth recording so nobody reaches for it again: a tmpfs-backed Docker VOLUME cannot be shared.
Each container that mounts one gets its own tmpfs instance, so the second sees an empty directory,
with no error. It has to be a host path if it is shared at all.

4. The credential
-----------------

The fetch phase gets a GitHub token scoped to reading this repository, and only for as long as
that container lives. An App installation token is the right shape: it expires in an hour on its
own, so a leak has a bounded life, and lib/gh.sh already mints one.

IT MUST NOT SURVIVE INTO THE WORKSPACE. `git fetch` with a credential helper writes it into
.git/config, and .git travels to the agent. The fetch phase uses a one-shot header
(-c http.extraHeader) and never a helper, and the phase ends by asserting that no credential
appears anywhere under .git. That assertion is the point: it fails the run rather than handing the
agent a token in a config file.


5. What the host enforces, and what it does not
-----------------------------------------------

ENFORCED, because the containers hold no docker socket and cannot change any of it:

  - that ffghr-net is gone before the agent starts, which is what makes GitHub unreachable
  - which credentials the container's environment carries at launch
  - the ordering: the entrypoint fetches and unsets before it execs the agent

NOT ENFORCED: what the fetch phase does with the credential while it holds it, and the unset
itself. Both rest on the entrypoint being our script and running to completion before the agent
starts. That is a weaker guarantee than two containers would give — there, the credential and the
agent could never coexist in one process tree — and it is the price of the simpler shape. It is
sound because nothing the agent influences runs before the unset.


6. The cache, unchanged
-----------------------

The fetch phase restores /ffcache/<branch>@<scope>.tar exactly as a CI job does, then fetches on
top. A miss is no longer special: with GitHub reachable it clones from scratch, slowly, instead of
failing. That is what removes golden's last job on the run path.

Agent runs still never write the cache. They mount /ffcache read-only and have no staging
directory, so there is nothing to promote and no code path that would promote it.


7. What golden is still for
---------------------------

ffwatch.py:223 reads it as a git-dir for repository state. That wants a real repository and
nothing more, so golden becomes a bare mirror: `git fetch` into it keeps update-golden.sh's job,
and the worktree and Library go away with the clone path.

Whether even that survives is a question for whoever changes ffwatch. It is out of scope here.


8. Security properties
----------------------

The agent container is unchanged in what it holds: the Claude token and the Unity credentials,
which it needs and which the design has always accepted it can read from its own environment. It
gains nothing and loses GitHub.

The fetch container is new surface, and it is small: our script, no model output, no Unity, no
prompt, exiting in the time a fetch takes. Its credential is read-scoped and short-lived.

What this improves on today: golden is a host directory that ffbox writes through a bind mount and
the host later runs git in. Section 1 says why that goes.


9. Migration
------------

Each step leaves a working machine.

  1. The fetch phase as a script, exercised by hand against a real cache entry.
  2. ffbox grows --workspace tmpfs alongside the clone path, defaulting to clone: dual-home,
     fetch, disconnect, repoint, unset, exec.
  3. Prove a real run end to end on tmpfs, including harvest.
  4. Flip the default, leaving the clone path reachable for one cycle.
  5. Delete the clone path, 04-warmLibrary.sh, and the delta bundle.
  6. Golden becomes a bare mirror.

No host tmpfs to provision: the workspace is the container's own --tmpfs, as CI's already is.


10. Open items
--------------

  a. Whether the entrypoint or the host repoints resolv.conf. The host doing it by `docker exec`
     keeps the sequence in one place; the entrypoint doing it needs a signal that the disconnect
     has happened, which is the branch.info pattern again.
  b. Whether a fetch that fails should fail the run or fall through to the cache entry as it
     stands. Falling through is a run against a slightly old tree; failing is no run at all.
  c. What ffwatch actually needs from golden, which decides whether the bare mirror survives.
