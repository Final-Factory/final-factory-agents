ffgithubrunners: single-use GitHub Actions runners in rootless containers
=========================================================================

Revision 3, 2026-08-28. Same shape as revision 2, three mechanisms replaced after measuring them
on Loth2400. The Library overlay moves out of the container and into the Docker daemon, because
the container cannot mount anything under the capability set section 14 requires. The warm Unity
Library and the warm checkout move out of the image and onto a dataset, because once the daemon
composes the overlay there is no reason for them to be image layers. Section 13 grows from two
lines to a real list, because moving the workflow's `run:` steps off the host and into a
container breaks several of them. Section 10 records why deploy.yml is now out of scope. Two
sections are new: 2.1 splits the work into two phases, because only the first is the point, and
13.5 sequences the cutover, because revision 2 assumed an empty box and there is not one.

Four decisions taken on 2026-08-28 are folded in and close three open questions. Final-Factory is
on the free plan and wants org-wide runners anyway, so there is no runner group and finding F2 is
accepted rather than fixed (section 8). The Unity seat count is not treated as a constraint;
reliable reclaim is (10.2). The test-results check run is RETAINED rather than traded away, which
turns revision 3's one genuine loss into about forty lines of `run:` step (10.2, 13.3). And
performance work is deliberately phase 2, so phase 1 ships with a plain --tmpfs workspace, the
cache steps untouched, and a workflow diff of two steps (2.1).

Revision 2, 2026-08-27. Replaced revision 1's KVM guest model with rootless containers.
Revision 1, 2026-08-27. Single-use KVM guests. Superseded.

Section 4 records what revision 1 got wrong and why, because the reasoning was not obviously bad
and will be re-proposed by anyone who reads only the requirements. Revisions 1 and 2 are kept in
the git history; nothing else in this file refers to them.

Scope: replace the four hand-installed GitHub Actions runners in /opt/github-actions-runner-N
with a checked-in, reinstallable harness that runs every CI job in a throwaway rootless
container. Covers the host layout, the image, the workspace, the slot lifecycle, the GitHub
identity, what replaces game-ci, the install script, the boundary with ffbox, the cutover from
the runners that are there now, and what stays unsolved. Nothing here uninstalls the current
runners; 13.5 says when they can go.

Why this exists: the runners today are unpacked tarballs that a person configured by hand and
that nothing in git describes. That is two problems wearing one coat. The reinstall problem is
that rebuilding this machine means remembering what was typed in August. The isolation problem
is worse: main.yml triggers on [push, pull_request] with `runs-on: self-hosted`, GitHub
evaluates the workflow file from the pushed branch, and every step outside the game-ci container
runs directly on this host as FinalFactoryTester. Anyone who can push a branch to any repo in
the Final-Factory org can read that account's git credential, its Claude token, and its rootless
Docker socket. The game-ci container is not a boundary, because it wraps one step of a job whose
other steps the attacker also writes.


0. What this must do
--------------------

  1. ONE JOB PER CONTAINER. A job runs in a container that did not exist before the job and does
     not exist after it. Nothing a job writes reaches the next job except through GitHub.

  2. NO CREDENTIAL ON THE WORKLOAD ACCOUNT. The account whose namespace a job runs in must hold
     nothing worth stealing. Separately, the account holding the credential that mints runner
     registrations must not be reachable from inside a job. See docs/ci-runner-security-findings.md
     finding F1, which is the reason this is a requirement rather than a nicety.

  3. NO UNATTENDED ROOT. Carried from design/rootless_docker_design.txt section 0. A process with
     no human at a keyboard must not be able to become root on this host. Install-time root is
     fine; a human types that. This design needs NO sudo grant at run time at all.

  4. NOTHING THE HOST WRITES IS READ BACK FROM THE CONTAINER. No writable bind mount out of a
     job, and no host-side command run against a directory a job wrote. Finding F7 is the live
     instance of that pattern elsewhere on this box, and this design must not add a second one.
     Revision 3 puts this requirement under real strain, because the overlay upperdir IS a host
     directory a job writes. Section 6.4 is how it holds.

  5. GAME-CI'S USEFUL BEHAVIOUR IS PRESERVED, ITS LICENCE LEAK IS NOT. Section 10. Activation
     must give the seat back on every exit path including a kill, which is more than game-ci
     manages today (fact o). The test-results check run is part of "useful behaviour" and is
     retained rather than traded away; 10.2 says how.

  6. REINSTALLABLE FROM GIT. One command on a bare Ubuntu box with ZFS reproduces the whole
     thing.

  7. SEPARATE FROM FFBOX. No shared folders, scripts, datasets, systemd units, images, Docker
     daemons, networks or user accounts, and no import of ffbox code. Both systems now run
     rootless containers on the same machine, which makes this harder to hold than it was in
     revision 1 and therefore more worth stating. Section 3.

  8. NO WORSE THAN TODAY ON THE CLOCK THAT MATTERS, WHICH IS BUILD AND TEST. Fact m says the ram
     disk is the whole game and phase 1 keeps it with a plain --tmpfs, so that clock is unchanged.
     There is a second one: fact v says checkout and LFS are up to 9.9 GB that persistent runners
     fetch incrementally and an ephemeral container fetches every time. PHASE 1 ACCEPTS THAT
     REGRESSION deliberately (2.1) and phase 2 is the remedy. Acceptance 15.10 measures it once
     there is something to measure.

Explicitly NOT a requirement: protecting a job from itself. A job gets namespace-root inside its
own container and is welcome to it.


1. Verified facts
-----------------

Facts a through p were measured on Loth2400 on 2026-08-27. Facts q through z were measured on
2026-08-28 while reviewing revision 2, and several of them are the reason this revision exists.

  a. THE RUNNERS ARE PERSISTENT AND ORG-SCOPED. Four Runner.Listener processes under
     run-helper.sh, no systemd units, no "ephemeral" key in any .runner. All four register
     against https://github.com/Final-Factory, the ORG. Credentials sit on disk: .credentials
     (mode 0664) and .credentials_rsaparams (0600) per runner.

  b. THE HOST IS A DELL POWEREDGE R720. Two Xeon E5-2680 v2, 10 cores each with SMT, 40 logical
     CPUs. 755 GB RAM. Bare metal.

  c. NUMA IS TWO NODES WITH INTERLEAVED CPU NUMBERING. Even logical CPUs are node 0, odd are
     node 1; SMT siblings are 20 apart. Node distances 10 local, 20 remote. Recorded because it
     shaped revision 1; under containers it is background rather than a design input.

  d. VIRTUALBOX WAS TRIED HERE AND REMOVED. 7.0.16 and 7.1.16 both in rc state, a VM directory at
     ~lothsahn/VirtualBox VMs/RRobin. KVM is present and unused. The owner's account of the
     VirtualBox era is that guests locked up.

  e. ARC IS UNCAPPED AND SWAP IS 2 GB. zfs_arc_max is 0, so c_max is 377.9 GB, half of RAM. ARC
     held 26.0 GB while the box was idle, at a 99.1% hit rate. Two gigabytes of swap means
     memory pressure does not degrade, it fails.

  f. THERE IS ROOM. rpool is 3.62T with 2.14T free.

  g. RUNNER 2.336.0 SUPPORTS WHAT THIS NEEDS. --ephemeral is documented in its own --help as
     "only take one job and then let the service un-configure the runner after the job
     finishes". GetJitConfig is in Runner.Listener.dll, JitConfig in Runner.Common.dll.

  h. THE WORKFLOWS ROUTE ON LABELS, NOT NAMES. main.yml and deploy.yml use
     `runs-on: self-hosted`. determinism-nightly.yml uses `runs-on: [finalfactory-mode2-windows]`
     and is a Windows runner this design does not touch.

  i. GAME-CI EXPOSES NO ISOLATION CONTROLS. Its declared inputs, read from the worker log on this
     box, are dockerCpuLimit, dockerMemoryLimit, dockerIsolationMode, chownFilesTo,
     runAsHostUser, sshAgent, customImage, containerRegistryRepository and
     containerRegistryImageVersion. Resource caps and file ownership, nothing else.

  j. THE HOST ACCOUNT IS RICH AND DOES EVERYTHING. FinalFactoryTester runs the runners, owns the
     rootless daemon at /run/user/1015/docker.sock, runs ffbox's containers, holds
     .git-credentials in plaintext, .claude/.credentials.json and .config/ffbox/secrets.env, is
     in the sudo group, and is logged into interactively. Finding F1.

  k. _work IS A 40 GB TMPFS. makeRamDisk.sh mounts one per runner.

  l. FFBOX SHARES THIS BOX AND HAS THE SAME RESOURCE SHAPE. max_concurrent_runs defaults to 2,
     the README documents 8, the owner's target is 4. The owner measures a run at about 32 GB of
     RAM plus disk, and about 72 GB if it moves to a ram disk. Its containers carry no cpuset.
     Section 5.3 budgets for eight identical Unity workloads, four of each.

  m. THE RAM DISK IS WORTH ABOUT 4x. Build and test on the tmpfs _work runs about 15 minutes
     against about an hour on ZFS-backed storage. Measured by the owner on this box with ARC
     already in play, so this is tmpfs against ZFS-plus-cache, not tmpfs against cold disk. It is
     the largest single performance lever in the system and the memory budget is built on it.

  n. FFBOX'S IMAGE IS THE GAME-CI IMAGE. ffbox/Dockerfile opens
     `FROM unityci/editor:ubuntu-6000.3.19f1-windows-mono-3.2.2`, the same tag main.yml passes as
     customImage, with a comment requiring the two be kept in lockstep. The container already IS
     the Unity environment, so there is no nested-Docker problem to solve. This fact is what
     revision 1 did not know.

  o. FFBOX ALREADY RETURNS UNITY SEATS CORRECTLY AND GAME-CI DOES NOT. ffbox/unity-license.sh
     installs `trap return_license EXIT INT TERM`, and its own comment states that game-ci's
     return_license.sh is an ordinary step which "a cancelled or crashed job never reaches. That
     is how CI quietly leaks seats."

  p. THE HOST-READS-CONTAINER-OUTPUT PATTERN IS ALREADY A HOLE HERE. ffbox bind-mounts the
     workspace read-write and the host runs git in that directory afterwards. Finding F7.
     Requirement 4 exists so this design does not repeat it.

  q. THERE IS NO UNITY ON THIS HOST. /opt/github-actions-runner-1 holds the runner tarball, bin,
     externals and run-helper.sh, and nothing else. `unity-editor` and `unity-hub` do not exist
     outside a container and /opt/unity does not exist. Unity reaches a job only because game-ci
     runs `docker run unityci/editor:<tag>` from INSIDE the job. This is the fact that explains
     deploy.yml, and section 10.3 is its consequence.

  r. A CONTAINER CANNOT MOUNT OVERLAYFS UNDER THE FLAGS SECTION 14 WANTS. Measured against the
     rootless daemon on kernel 6.8, lowerdir on the container's own overlay2 rootfs and upperdir
     on tmpfs, which is exactly the shape revision 2 section 6 proposed:

         --cap-add=SYS_ADMIN            mount rc=0
         docker default capability set  mount: permission denied
         --cap-drop=ALL                 mount: permission denied
         --cap-drop=ALL, unshare -Ur    unshare(CLONE_NEWUSER): Operation not permitted

     Docker's default set does not carry CAP_SYS_ADMIN, so this fails before section 14's flags
     are considered. With --cap-drop=ALL the default seccomp profile also refuses
     unshare(CLONE_NEWUSER), so the namespace-root route is closed too. Revision 2's entrypoint
     overlay cannot be built.

  s. THE DAEMON CAN MOUNT IT, AND THE CONTAINER THEN NEEDS NO CAPABILITIES. `docker volume create
     --driver local --opt type=overlay --opt device=overlay --opt o=lowerdir=...,upperdir=...,
     workdir=...` makes the rootless daemon perform the mount inside rootlesskit, where it holds
     namespace-root. Measured with lowerdir on ZFS and upperdir on tmpfs, consumed by a container
     run with --cap-drop=ALL --security-opt=no-new-privileges:

         read from lower        served from the ZFS copy
         write a new file       rc=0, landed in the tmpfs upper
         append to a lower file rc=0, copied up into tmpfs, lower untouched
         delete a lower file    rc=0, whiteout char device in tmpfs, lower untouched
         mount line             overlay ... redirect_dir=nofollow,uuid=on,xino=off,userxattr

     `userxattr` is why upperdir on tmpfs works at all: overlayfs in a user namespace uses
     user.overlay.* rather than trusted.*, and tmpfs carries user.* xattrs. Section 6 is built
     on this.

  t. THE OVERLAY WORKDIR CANNOT BE DELETED BY THE SUPERVISOR ACCOUNT. The kernel creates
     workdir/work as mode 000 owned by the daemon's user. A plain `rm -rf` from another account
     fails with Permission denied, and no ACL fixes a mode-000 directory. Section 6.4.

  u. BLOCK CLONING IS OFF AND SHOULD STAY OFF. zfs-2.2.2-0ubuntu9.4, and
     `zpool get feature@block_cloning rpool` returns disabled. `cp --reflink` is therefore not
     available as a cheap Library copy, and given that feature's corruption history in 2.2.x it
     is not worth enabling for this.

  v. THE REPOSITORY IS 9.9 GB BEFORE UNITY TOUCHES IT. In /opt/FinalFactory: .git is 5.6 GB of
     which .git/lfs is 4.3 GB across 3190 LFS-tracked files, and Library is 4.4 GB. Revision 2
     guessed the Library at 15 GB and the real number is a third of that, which makes every
     memory figure in 5.3 easier. The 9.9 GB is the argument for a warm workspace, and the
     4.3 GB of LFS is a bigger part of it than the Library.

  w. LIBRARY IS GITIGNORED, SO `git clean -ffdx` DELETES IT. .gitignore:4 is `/[Ll]ibrary/`.
     actions/checkout runs that clean by default whenever it finds an existing repository at the
     workspace path. Section 13.1.

  x. THE BASE IMAGE IS MISSING gh AND THE MAC PLAYBACK ENGINE. Inventoried inside
     unityci/editor:ubuntu-6000.3.19f1-windows-mono-3.2.2:

         git /usr/bin/git        git-lfs /usr/bin/git-lfs   python3 /usr/bin/python3
         curl /usr/bin/curl      jq /usr/bin/jq             unity-editor /usr/bin/unity-editor
         gh  MISSING

         /opt/unity/Editor/Data/PlaybackEngines/
           LinuxStandaloneSupport
           WindowsStandaloneSupport

     main.yml's cache-pruning step is built on `gh cache list` and `gh cache delete`, which run
     on the host today where gh exists. There is no Mac module, which is what section 10.3 is
     about.

  y. deploy.yml PASSES NO customImage. main.yml pins
     unityci/editor:ubuntu-${UNITY_VERSION}-windows-mono-3.2.2; deploy.yml passes nothing, so
     game-ci selects an image per targetPlatform and the StandaloneOSX leg gets a mac-mono image.
     Two matrix legs, two different images, chosen after the job starts. Fact q is why that is
     free today and section 10.3 is why it stops being free here.

  z. THE JOB HOOKS EXIST AND ARE THE RIGHT PLACE FOR THE LICENCE. Runner 2.298 and later honour
     ACTIONS_RUNNER_HOOK_JOB_STARTED and ACTIONS_RUNNER_HOOK_JOB_COMPLETED, set in the runner's
     environment and pointing at a script that runs before the first step and after the last.
     Revision 2 activated Unity in the container entrypoint, which would have held four seats
     continuously against idle runners. Section 10.2.


2. The shape
------------

Four slots. Each slot keeps one runner registered with GitHub and idle, exactly as today. When a
slot's runner takes a job it runs it, deregisters itself, and its container exits. The
supervisor removes the container and its overlay volume, clears the slot's scratch, and starts a
replacement that registers and goes idle.

Steady state is four runners online waiting for work, which is what the org settings page shows
today. Ephemeral describes what happens to a runner after its job, not when it is created. There
is no queued-job detector anywhere in this design, because a runner is always already listening.

    mint JIT config  ->  compose the overlay volume  ->  docker run --rm  ->  runner idles
      ->  runner takes one job, runs it, deregisters, container exits
      ->  remove container, remove volume, clear scratch, DELETE the registration
      ->  supervisor exits, systemd restarts it

The loop is a unit that handles one job and exits, restarted by systemd. Nothing polls GitHub,
nothing receives a webhook, and no inbound port is opened.

RESTART NEEDS A BACKOFF, WHICH REVISION 2 DID NOT SAY. Restart=always with systemd's default
StartLimitBurst=5 in StartLimitIntervalSec=10s turns any fast-failing condition into a permanent
failure: an unreachable GitHub API at mint time, a missing image, a daemon that has not come up.
Five restarts burn in about a second and the slot lands in `failed` needing a manual
`systemctl reset-failed`. The unit sets StartLimitIntervalSec=0 with RestartSec around 5 seconds,
and the supervisor itself backs off on API errors rather than exiting immediately.

Container start is about a second, so the gap between a runner exiting and its replacement going
online is small enough not to need a busy-triggered replacement.


2.1 TWO PHASES, AND ONLY THE FIRST IS THE POINT

Decided on 2026-08-28: get it working first and optimise later. The design does two separable
things and this is the order they land in.

PHASE 1 IS THE ISOLATION HALF, and it is why the project exists. Build ffghrunner:latest FROM
unityci/editor, put the runner inside it, mint a JIT config per job, split ffghr-super from
ffghr-run, throw the container away afterwards. That closes the hole in this document's opening
paragraph: a pushed branch stops being code execution as FinalFactoryTester with that account's
git credential, Claude token and Docker socket within reach. It needs sections 5, 7, 8, 9 and 14,
the workflow edits in 13.3, and nothing else.

PHASE 1 IS NOT SLOW AT THE THING THAT MATTERS MOST. Its workspace is a plain --tmpfs at the
runner's _work path, sized the way makeRamDisk.sh sizes one today (fact k). Fact m's 4x is a
property of _work living in RAM rather than of warm data, so phase 1 builds and tests at today's
speed. actions/checkout clones from scratch, the actions/cache steps stay exactly as they are,
and no workflow edit beyond 13.3 is needed.

WHAT PHASE 1 COSTS IS THE RE-FETCH. The current runners are persistent, so checkout is
incremental. An ephemeral container starts empty and pays for the clone, the LFS pull and the
Library cache download on every job, which fact v puts at up to 9.9 GB, now crossing slirp4netns.
How bad that actually is, is acceptance test 15.10, and it gets measured after phase 1 works
rather than guessed at before it is built.

PHASE 2 IS THE SPEED HALF: the warm workspace of 6.2, the overlay of 6.3, and the workflow edits
in 13.1 and 13.2 that make them pay. It exists to remove that re-fetch and nothing in the
security argument depends on it. It is gated on acceptance test 15.11, open question 17b, which
may well show that a simpler mechanism than the overlay is enough.

NEITHER PHASE PUTS UNITY ON THE HOST. Fact q says there is no Unity on Loth2400 today, and nothing
here adds any. Unity lives in the image, which is exactly where it lives now, inside the
container game-ci starts. Phase 2's warm-workspace refresh runs a headless import to rebuild the
Library and that runs in a container of the same image too. Nothing in this design installs
unity-editor, Unity Hub or a licence on the host itself.


3. The boundary with ffbox
--------------------------

Requirement 7. Two systems running rootless Unity containers on one box look alike enough that
sharing becomes tempting by accident.

WHAT IS BORROWED, as ideas only, each reimplemented here:

  - Building the image FROM the exact unityci/editor tag CI uses, so what runs here and what
    runs in CI are the same Unity (fact n).
  - Returning the Unity seat from a trap rather than a step (fact o).
  - Numbered, independently re-runnable install stages with the order in the filenames.
  - Rendering systemd units from templates in git rather than keeping a second copy on disk.
  - The principle that an unattended process must not be able to become root.

WHAT IS NOT SHARED, and must never become shared:

  - Folders. ffgithubrunners/ at the repo root, beside ffbox/, never inside it. No file in ffbox/
    is read, sourced, imported or called by anything here.
  - THE DOCKER DAEMON. ffbox's rootless daemon is FinalFactoryTester's, at
    /run/user/1015/docker.sock, data root /opt/ffbox_docker. This design runs its OWN rootless
    daemon under its own account with its own data root. Reaching for the existing socket would
    collapse requirement 2, requirement 7 and the account split in one move, and it will look
    like an obvious shortcut. It is not one.
  - Images. ffbox:latest is ffbox's. ffghrunner:latest is this one's. Both are built FROM the
    same public unityci/editor tag, which is the shared idea, not a shared artefact.
  - Networks. Separate Docker networks on separate daemons.
  - Datasets. rpool/ffgithubrunners/*. ffbox owns rpool/ff/*.
  - The FinalFactory checkout. ffbox's rpool/ff/golden is mounted at /opt/FinalFactory. This
    design does not read, clone, snapshot or mount it; section 6.2 gets its own checkout from
    GitHub. The two warm checkouts will look almost identical on disk and that is fine.
  - User accounts, systemd units and targets, configuration and secrets, environment prefix
    (FFGITHUBRUNNERS_*, never FFBOX_*).

THE UNAVOIDABLE OVERLAP is the machine. The ARC cap (5.3), any nftables rules (5.5) and the host
package set are host-wide; there is one of each. Add plain CPU and memory contention, budgeted in
5.3. That is coexistence on shared hardware, not shared implementation.

Fact l says an ffbox run and a CI job are the same size and shape. That is a shared design
concept, which requirement 7 permits, and it is why 5.3 budgets one pool of eight workloads. It
is NOT an argument for merging the systems, and nothing here reads ffbox's configuration at run
time to discover its concurrency: the eight-workload figure is written down in 5.3 and changed by
a human when ffbox changes.


4. Why containers, and why revision 1 said otherwise
----------------------------------------------------

Revision 1 chose KVM guests on two arguments. One was wrong on the facts and the other was
weaker than it looked.

THE ARGUMENT THAT WAS WRONG. Revision 1 held that a container could not run these jobs without
nested Docker, because game-ci works by running `docker run unityci/editor`, and that mounting a
socket in reproduces the hole rootless_docker_design.txt section 1a closed. That is true of a
job container that then calls game-ci. It is not true of the model ffbox already uses: fact n
says ffbox's image IS unityci/editor, so the container is the Unity environment and nothing is
nested.

THE ARGUMENT THAT WAS WEAK. Revision 1 held that a VM boundary is easier to state than a
container one. True in general. Less decisive here, because this box already runs a workload with
bare Bash, reachable by a stranger's Discord message, in a rootless container, and
design/single_lane_design.txt records the owner accepting that. A second, stronger isolation
technology for CI is defensible, but it is a marginal improvement over the containment already
in use, not a categorical one.

WHAT CONTAINERS BUY:

  - MEMORY BECOMES A CEILING INSTEAD OF A RESERVATION. A guest holds its RAM whether it uses it
    or not. A container with --memory=64g uses what it uses, and the unused remainder is
    available to ARC, to the page cache, and to the other seven workloads. Section 5.3.
  - NO BOOT. About a second against about thirty.
  - NO HYPERVISOR TUNING. Revision 1's whole vCPU, NUMA, interleave and topology section
    evaporates. CFS and the page cache already do the right thing.
  - NO ROOT GRANT AT ALL. Revision 1 needed anchored sudoers rules for zfs clone and destroy per
    job. This design needs none. Requirement 3 is met by having no mechanism rather than by
    constraining one.
  - ONE MODEL ON THE BOX instead of two.

WHAT IT COSTS:

  - A WEAKER BOUNDARY. The kernel is shared. Section 14 is honest about which escape classes
    that changes and which it does not.
  - THE WORKFLOW CHANGES. Revision 1 had "no workflow changes" as its requirement 4. Section 13
    is the replacement work and revision 3 found it larger than revision 2 thought.
  - THE IMAGE IS CHOSEN BEFORE THE JOB EXISTS. This is the cost revision 2 missed. Facts q and y
    together: today Unity arrives per job from inside the job, so game-ci picks a different image
    per matrix leg for free. A runner container that IS the Unity environment has to know which
    Unity it is before a job is assigned to it. Section 10.3.
  - IF A FUTURE WORKFLOW NEEDS `docker build`, this puts the nesting problem back. Recorded in 17.

The choice is also more reversible than it looks. Sections 2, 7, 8, 9, 11 and 12 are the harness,
and they are identical either way. Only "start a slot" and "destroy a slot" differ.


5. Host layout
--------------

5.1 TWO ACCOUNTS, NOT ONE

Finding F1 is that one account on this box runs everything and holds everything. This design does
not add a third instance of that.

  ffghr-super   runs the supervisor units. Holds the GitHub App private key at
                /etc/ffgithubrunners/github-app.pem, mode 0600. Not in sudo, not in docker, no
                login shell. It talks to ffghr-run's daemon socket to start and stop containers.

  ffghr-run     owns the rootless Docker daemon and therefore the namespace every job runs in.
                Its home is EMPTY: no tokens, no git credential, no ssh key, no sudo, no login
                shell, nothing in .config. This is the account a container escape lands on, and
                the whole point of it is that landing there is worth nothing.

The direction matters and only works one way: super can drive run's daemon, and a job inside that
daemon cannot reach super's files.

THE SOCKET DOES NOT LIVE IN /run/user. Revision 2 said ffghr-super would reach
/run/user/<ffghr-run-uid>/docker.sock through a group or an ACL. That does not survive contact
with logind. The directory is created by pam_systemd at mode 0700 owned by the user, on a tmpfs
that is torn down and recreated, so ACLs set on it do not persist. Worse, ffghr-run has no login
shell and never logs in, so the directory only exists at all if `loginctl enable-linger ffghr-run`
has been run, which revision 2 never said. The first reboot would have taken the whole system
down silently.

Instead the daemon listens on a stable path:

    dockerd-rootless.sh -H unix:///run/ffgithubrunners/docker.sock

with /run/ffgithubrunners created by a tmpfiles.d rule from stage 1, owned ffghr-run:ffghr,
mode 0750, and ffghr-super in the ffghr group. Linger is still enabled for ffghr-run so the user
manager starts at boot, but nothing depends on the shape of /run/user any more.

Neither account gets a sudoers entry. Section 4 explains why none is needed.

5.2 THE CI DOCKER DAEMON AND ITS DATASETS

A second rootless daemon, ffghr-run's, entirely separate from ffbox's (section 3):

    rpool/ffgithubrunners            container, mountpoint=none
    rpool/ffgithubrunners/docker     the daemon's data root, compression=lz4
    rpool/ffgithubrunners/warm       the warm workspace of 6.2, compression=lz4, read-only to
                                     everything except the refresh job

A quota on rpool/ffgithubrunners is worth setting so a runaway image build cannot fill rpool and
take ffbox down with it. That is the only coupling left between the two systems' storage and it
runs through the pool, not through any shared path.

Per-slot scratch is NOT a dataset. It is a tmpfs:

    /run/ffgithubrunners/slot-N      tmpfs, size=32g, mode 0700, owned ffghr-run

mounted by a systemd .mount unit ordered BEFORE ffgithubrunners-dockerd.service. The ordering is
not cosmetic: a tmpfs mounted on the host after rootlesskit has started may not propagate into
the daemon's mount namespace, and mounting it at boot sidesteps the question. Open question 17c
is whether it propagates anyway; the ordering means the answer does not matter.

5.3 MEMORY: LIMITS, NOT RESERVATIONS

Fact e first, because it is the thing that hurts a ZFS host: ARC is uncapped, so c_max is 377.9
GB. It is small only because the box is idle; under load it climbs, and workloads then allocate
against memory ARC gives back slowly. Stage 1 writes /etc/modprobe.d/zfs.conf with zfs_arc_max at
48 GB and rebuilds the initramfs. That is a host-wide setting shared with ffbox, per section 3.

REVISION 3 NEEDS LESS MEMORY THAN REVISION 2 ASKED FOR, for two reasons. Fact v says the Library
is 4.4 GB and not the 15 GB revision 2 assumed. And section 6's overlay means the tmpfs holds
only what a job WRITES, not the 9.9 GB of repository and Library it reads, because reads come
from the warm copy on ZFS through the page cache.

PHASE 1 gives each CI container the shape the current runners already have:

    --memory=72g
    --tmpfs <runner _work path>:size=40g,mode=1777

Fact k says makeRamDisk.sh gives each existing runner a 40 GB tmpfs _work and fact m says that
ram disk is worth about 4x. Phase 1 changes who mounts it, not what it is. The remaining 32 GB
covers Unity, the runner process and the container's page cache, which is the figure fact l puts
behind an identical ffbox workload.

PHASE 2 COMES DOWN, because the warm lower of 6.2 holds on ZFS the 9.9 GB that phase 1 keeps in
RAM, and only writes land in the scratch:

    --memory=64g
    the slot's /run/ffgithubrunners/slot-N tmpfs, size=32g, as overlay upper and scratch

32 GB of writable scratch against a 9.9 GB working set is generous. It has to cover Library churn
during an incremental import, Temp, test artifacts, whatever the job builds, and any LFS file the
smudge filter rewrites.

PHASE 2'S ACCOUNTING IS LOOSER THAN PHASE 1'S AND THAT IS WORTH KNOWING. With --tmpfs the pages
die with the container. With a host tmpfs, pages a container faults into it are charged to its
cgroup, so --memory=64g still bounds a running job, but they are not freed when the container
exits, only when the files are unlinked, and the charge reparents once the cgroup is removed. So
the per-slot size=32g cap is the real backstop rather than a formality, and the scratch clear in
6.4 runs unconditionally in the teardown path rather than only on the happy path.

Filling the scratch while Unity holds 32 GB OOM-kills the container. That kills one job rather
than destabilising the box, which is a better failure mode than revision 1's, where the same
arithmetic took out a guest.

Budget on this box, 755 GB, at the eight-workload target from fact l:

    ARC (capped)                     48 GB
    host, ffwatch, ffweb            ~24 GB
    4 ffbox runs x 72 GB            288 GB   unchanged, ffbox's own figure
    4 CI jobs x 72 GB               288 GB   phase 1; phase 2 drops this to 256 GB
    headroom                       ~107 GB   phase 1; ~139 GB in phase 2

THESE ARE CEILINGS. The sum fits inside RAM, so there is no overcommit and no way for all eight
to collectively exceed the machine. A slot sitting idle, or a job whose scratch only reaches 8 GB,
gives the difference back to ARC and the page cache instead of holding it. Fact e says there are
2 GB of swap, so the headroom row needs to stay genuine slack rather than a margin being spent.

5.4 CPU

No mask. Every container may use all 40 threads, as ffbox's already do (fact l). No cpuset, no
cgroup cpuset partition, no isolcpus.

The reason is the workload. A Unity build is spiky: long stretches near idle, then a burst that
wants everything. Eight of them will not burst together, and partitioning 20 physical cores among
eight bursty consumers spends most of the day holding cores away from the one workload that could
use them. Leaving CFS alone means an idle slot's share goes to a busy one for free, with no
configuration and no coordination between two systems that are otherwise separate.

Fact c is recorded but is not a design input here. Without pinned vCPUs and hard-allocated guest
memory there is no NUMA placement decision to make.

If measurement ever shows CI starving ffbox or the reverse, the answer is CPUWeight= on the
slice, not a narrower mask. A mask gives back the idle-borrowing above and guarantees nothing.

5.5 NETWORK

A dedicated Docker network on the CI daemon. A job must reach GitHub, Unity licensing and the LFS
endpoints, and must reach neither this host nor the LAN.

Rootless gives one of those for free. rootless_docker_design.txt section 5 records the
measurement: under the ROOT daemon a container on an --internal network could still open 22 and
445 on the bridge gateway, and under rootless the bridge lives inside the rootlesskit network
namespace where the host is not on the other side of it at all.

The LAN is the open half, and revision 3 has a cleaner lever for it than revision 2 found.
Container egress leaves through rootlesskit and appears to come from the host as ffghr-run's
uid, which is an account nothing else uses. So a host nftables output rule can match it
precisely:

    meta skuid <ffghr-run-uid> ip daddr 192.168.51.0/24 drop
    meta skuid <ffghr-run-uid> ip daddr <this host's addresses> drop

That is uid-scoped rather than address-scoped, so it cannot catch ffbox or a human by accident,
which was the objection to a plain host rule.

IT IS STILL A MEASUREMENT. Stage 1 installs the rule set; stage 6 does not declare success until
acceptance test 15.5 shows 192.168.51.0/24 unreachable from inside a container while
api.github.com is reachable. If the rule set cannot achieve that, the SNI allowlist pattern
becomes required rather than deferred, reimplemented on this daemon per requirement 7.
ffbox/egress/ffbox-egress.sh has FFBOX_EGRESS_MODE=log for discovering such an allowlist, and
reading it for the technique is allowed where copying it is not.

THROUGHPUT IS THE NEW RISK, and it belongs to requirement 8 rather than to security. Today
checkout and LFS run on the host's own stack at native speed. Inside rootless Docker they go
through slirp4netns, which is a lot slower, and fact v says a cold job moves 9.9 GB. The warm
workspace of 6.2 is most of the answer, because an incremental fetch is small. Acceptance test
15.10 times the checkout and LFS steps specifically rather than only the editmode suite, and
pasta is the lever if slirp turns out to be the bottleneck.

Worth recording so it is not rediscovered: the runner talks to broker.actions.githubusercontent.com
and a pipelinesghubeus* host, not only api.github.com. The .runner file has useV2Flow true.


6. The image, the warm workspace and the overlay
------------------------------------------------

This is the section revision 3 rewrote. Revision 2 baked a warm Library into the image and had
the container's entrypoint overlay it. Fact r says the container cannot mount anything, so that
plan is dead. Fact s says the daemon can, and once the daemon is doing the mount there is no
reason for the warm data to be an image layer at all.

The split is now clean: the IMAGE is software, the DATASET is data, and the DAEMON joins them.

ONLY THE IMAGE BELONGS TO PHASE 1, per 2.1. Phase 1 runs it against a plain `--tmpfs` at the
runner's _work path and lets actions/checkout populate that from GitHub on every job. Subsections
6.2 through 6.5 are phase 2. They exist to stop paying for the re-fetch, and none of them is
needed for the isolation the project is actually for.

6.1 THE IMAGE

ffghrunner:latest, built by stage 4 from a Dockerfile in this folder:

    FROM unityci/editor:ubuntu-6000.3.19f1-windows-mono-3.2.2

Same base as CI uses today and as ffbox uses, for the reason ffbox's Dockerfile records: if they
drift, a green run here stops predicting a green run there. The tag is pinned in one place and
tracked against UNITY_VERSION in main.yml.

On top of that:

  - the actions runner tarball at /opt/actions-runner, unconfigured
  - gh, because fact x says the base image does not have it and main.yml's cache-pruning step
    is built on it. Everything else main.yml's `run:` steps use is already there: git, git-lfs,
    python3, curl, jq, unity-editor.
  - the /BlankProject scaffolding Unity's serial activation needs, which the base image does not
    carry (ffbox hit this and it is not obvious)
  - the entrypoint of section 7 and the job hooks of section 10.2

NO CHECKOUT AND NO LIBRARY. Both moved to 6.2. The image is now small enough to rebuild in
minutes rather than an hour, and it changes only when UNITY_VERSION or the runner version does.

THE RUNNER VERSION IS A CORRECTNESS PROBLEM, NOT A SPEED ONE. Revision 2 said a stale image just
imports more. That is true of the Library and false of the runner: GitHub enforces a minimum
runner version and will stop assigning jobs to one that falls below it, and a runner baked into a
read-only container cannot self-update. So the image refresh pulls a current runner tarball, and
the container passes --disableupdate so the runner does not attempt an update it cannot complete
mid-job.

6.2 THE WARM WORKSPACE

A directory on rpool/ffgithubrunners/warm holding a complete, ready-to-build checkout:

    warm/FinalFactory/            the repository, origin
                                  https://github.com/Final-Factory/FinalFactory.git
    warm/FinalFactory/.git/       objects and .git/lfs/objects, materialised
    warm/FinalFactory/Library/    a warm Unity Library
    warm/_actions/                the actions the workflow downloads, pre-populated

Fact v is the whole argument: 5.6 GB of .git, of which 4.3 GB is LFS across 3190 files, plus a
4.4 GB Library. A container that starts with an empty _work pays all 9.9 GB on every job, over
slirp4netns, before Unity does anything. The Library is the smaller half of that, which revision 2
did not know.

The warm copy is read-only to every job. It is the lowerdir and nothing writes to it, so all four
containers read one set of inodes and share the page cache and ARC for it. That is the property
revision 2 wanted from an image lowerdir, obtained without the image.

REFRESHING IT is ffgithubrunners-warm.timer, weekly and on demand from the CLI:

  1. Build the new warm copy in warm/next: clone or fetch, `git lfs pull`, run a headless Unity
     import to rebuild the Library.
  2. Swap the `warm/current` symlink and delete the old copy.

The refresh runs in a container of the same image, with warm/next bind-mounted read-write. That
is the ONE writable bind mount in this design and it is not a job: it runs our checkout of our
repository under our control, not a workflow file from a pushed branch. Requirement 4 is about
untrusted output and this is not that. Nothing untrusted ever writes to a lowerdir.

Slots read `warm/current`, so a refresh never mutates a copy a running job is reading, and a
half-built warm/next is never visible. `drain` before a swap is polite rather than required.

THE REFRESH NEEDS A GITHUB READ CREDENTIAL and revision 2 never said where it lives. It clones a
private repository with LFS content. The credential belongs to ffghr-super, is passed to the
refresh container in the environment, and is a read-only fine-grained token scoped to
FinalFactory contents. It must not end up in warm/current/.git/config or in an LFS credential
cache, because that directory is readable by every job: the refresh unsets it and stage 4 checks
for it.

6.3 THE OVERLAY

The daemon composes it, per fact s. Per job, the supervisor:

    docker volume create --driver local \
      --opt type=overlay --opt device=overlay \
      --opt o=lowerdir=/rpool/ffgithubrunners/warm/current/FinalFactory,\
    upperdir=/run/ffgithubrunners/slot-N/up,workdir=/run/ffgithubrunners/slot-N/wk \
      ffghr-ws-<slot>-<nonce>

    docker run --rm ... -v ffghr-ws-<slot>-<nonce>:/work/_work/FinalFactory/FinalFactory ...

The container needs no capabilities for this. Fact s measured reads from the lower, writes,
copy-up on append and whiteout on delete, all from inside --cap-drop=ALL
--security-opt=no-new-privileges. Section 14's flag list stands exactly as revision 2 wrote it.

THE MOUNT IS THE WHOLE WORKSPACE, NOT JUST Library. Two reasons. Fact v says the repository is
the bigger half of the warm data, so overlaying only Library leaves 5.6 GB on the table. And
mounting a volume AT `<workspace>/Library` is actively dangerous: fact w says
`git clean -ffdx` deletes Library, and on a mountpoint it deletes the contents, fails to rmdir,
and exits non-zero. actions/checkout treats a failed clean as a corrupt working directory and
falls back to deleting the whole workspace, which also fails on the mountpoint, and the job
errors out. With the whole workspace overlaid, Library is an ordinary directory inside it and
the worst case is a slow job instead of a broken one. Section 13.1 is how the clean is handled.

COPY-UP IS WHOLE-FILE. The first write to Unity's artifact database pulls the entire file from
ZFS into tmpfs. It should be fast off ARC, but it is a spike in both time and scratch at the
start of the import and it is what acceptance test 15.11 watches.

6.4 CLEANUP, AND HOW REQUIREMENT 4 SURVIVES IT

The upperdir is a host directory that a job writes. Requirement 4 forbids reading it back, not
creating it, and the teardown never reads: it unlinks. But it cannot unlink it directly.

Fact t: the kernel creates workdir/work as mode 000 owned by the daemon's user, so `rm -rf` from
ffghr-super fails with Permission denied and no ACL fixes a mode-000 directory. Under the account
split of 5.1 the supervisor is not the daemon's user anyway.

So the delete is done by the daemon, in a throwaway container:

    docker run --rm -v /run/ffgithubrunners/slot-N:/x <small image> rm -rf /x/up /x/wk

It runs as ffghr-run, which owns the files. It reads nothing, executes nothing from the tree, and
`rm -rf` on a path with no globbing is safe against hostile filenames. This is the one place the
design comes close to the F7 pattern and the distinction is worth stating plainly: F7 is the host
running `git` in a container-written tree, where git executes hooks and config the container
placed. Unlinking a directory interprets nothing.

The scratch is a tmpfs, so a failed cleanup costs RAM until the next successful one, which is why
5.3 caps it per slot and why the teardown path runs it unconditionally.

6.5 WHAT THIS REPLACED, SO IT IS NOT RE-PROPOSED

Revision 2's fallback for a failed overlay was a plain copy of the Library into tmpfs at
container start. That is still the fallback, and fact v makes it much less painful than it looked:
4.4 GB per container rather than 15 GB. The ladder, if 6.3 fails on this box:

  1. Daemon-composed overlay volume, as above.
  2. No overlay: put the workspace on the container's own writable overlay2 layer on ZFS, seeded
     by `docker cp` or a read-only bind mount plus a copy. Zero mechanism, and worth timing first
     regardless, because if ARC makes ZFS fast enough for the Library then 6.3 is complexity that
     buys nothing. Acceptance test 15.11.
  3. Mount inside the entrypoint with --cap-add=SYS_ADMIN, then drop the whole bounding set with
     `setpriv --bounding-set=-all --no-new-privs` before exec'ing the runner. The job cannot
     mount, but the container's seccomp profile stays computed against SYS_ADMIN for its whole
     life, so a layer is lost. Only if 1 and 2 both fail.
  4. Plain copy into tmpfs at start.

`cp --reflink` is not on the ladder. Fact u: block cloning is disabled on this pool and, given
that feature's corruption history in OpenZFS 2.2.x, it should stay disabled for this.


7. The slot lifecycle
---------------------

HOST SIDE, one instance of ffgithubrunners@.service per slot, running as ffghr-super:

  1. Read /etc/ffgithubrunners/secrets.env and slots.conf.
  2. Clear the slot's scratch per 6.4, in case the last teardown did not finish.
  3. Mint an installation token from the GitHub App, then POST
     /orgs/Final-Factory/actions/runners/generate-jitconfig with the slot's name, its label set,
     and runner_group_id 1, which is Default and is the only group the free plan has (section 8).
     Keep the returned runner id. Back off on failure rather than exiting, per
     section 2.
  4. Compose the overlay volume per 6.3.
  5. `docker run --rm` against ffghr-run's daemon, with the flags in 5.3, the network from 5.5,
     the hardening in 14, the JIT config and the hook paths in the environment, the overlay
     volume as the only mount, and no bind mounts at all.
  6. Wait for the container to exit, with a watchdog. The watchdog sends TERM and waits before it
     sends KILL, so the job-completed hook of 10.2 gets to return the Unity seat.
  7. Teardown, unconditionally: remove the container if it is still there, remove the volume,
     clear the scratch per 6.4, then DELETE the runner registration.
  8. Exit 0. systemd restarts the unit and the slot comes back.

CONTAINER SIDE, the entrypoint, which is now short because 6.3 moved the hard part out:

  1. exec /opt/actions-runner/bin/Runner.Listener run --jitconfig "$JIT" --disableupdate.

The licence is not here. Revision 2 activated Unity in the entrypoint, which would have held a
seat for every idle runner, four of them, all day. Fact z moves it to the job hooks and 10.2 is
the detail.

The runner deregisters itself on a normal exit, so step 7's DELETE returns 404 on the happy path.
That is fine and is why it is unconditional.

CONTAINER LOGS OUTLIVE THE CONTAINER, which revision 2 got wrong. Section 12 promises
`ffgithubrunners logs N` and `--rm` deletes the log with the container. The supervisor tees
`docker run`'s output to /var/log/ffgithubrunners/slot-N.log with rotation. That is inert capture
of container output, which requirement 4 permits: it is written and read as text and never
executed, never fed to a shell, never used as a path.

THE WATCHDOG SITS ABOVE THE WORKFLOW'S OWN TIMEOUT, not below it. main.yml sets
timeout-minutes: 90, so the slot watchdog defaults to 120 and a job GitHub is still willing to
run is never killed by this harness. Per-slot in slots.conf, because the determinism work may
want longer.

THE JIT CONFIG GOES IN AS AN ENVIRONMENT VARIABLE, and finding F6 says environment secrets are
readable by anything in the container. That is acceptable here in a way it is not for ffbox's
Claude token: this credential is single-use, scoped to one job, belongs to the job anyway, and is
dead the moment the job ends. It is not a standing credential wearing a disguise.

THE UNITY CREDENTIALS ARE A DIFFERENT MATTER AND REVISION 2 DID NOT NOTICE. Activation needs
UNITY_EMAIL, UNITY_PASSWORD and UNITY_SERIAL, and those are standing credentials that every job
could read out of `env`. The mitigating fact is that main.yml already hands the same four secrets
to the job from the repository, so a job that legitimately runs can print them today and nothing
at this layer changes that. What the design can do is not make it worse: the hook of 10.2 reads
them from a file the hook can see, so they are not in the job's own environment block, and the
harness never introduces a Unity credential the workflow did not already carry.


8. GitHub identity
------------------

A GITHUB APP, not a PAT, installed on the org, private key at
/etc/ffgithubrunners/github-app.pem, owned by ffghr-super, mode 0600. No container ever sees it.

THE PERMISSION IS PROBABLY NOT THE ONE REVISION 2 NAMED. It said "administration: write on the
org". POST /orgs/{org}/actions/runners/generate-jitconfig wants the organization-level
SELF-HOSTED RUNNERS permission at write; `administration` is the repository-level one. Stage 5
verifies by minting a config rather than by reading documentation, so a wrong guess here fails
loudly at install time instead of quietly at run time.

JIT CONFIG, not a registration token. JIT runners are implicitly ephemeral and the config never
lands on disk, which removes the .credentials and .credentials_rsaparams files of fact a rather
than reproducing them somewhere new. Finding F3.

NAMES ARE FOR HUMANS. runs-on matches labels, so the per-run name is
ffghr-loth2400-<slot>-<nonce> and changes every job without affecting routing. The nonce is
generated locally by the supervisor at mint time. Revision 2 called it a run id, which reads as
GitHub's run id and cannot be right: the name is minted before any job exists, so GitHub's run id
is not knowable. The reaper in section 9 matches on the nonce, so the distinction matters.

LABELS: the defaults self-hosted, Linux, X64, plus ffgithubrunners. Keeping self-hosted means
main.yml keeps routing here unchanged, and it also means deploy.yml would route here, which
section 10.3 is about.

NO RUNNER GROUP, AND THE RUNNERS STAY ORG-WIDE. Decided on 2026-08-28, and this reverses what
revision 2 and the first draft of revision 3 assumed. Final-Factory is on the free plan, where
Default is the only runner group there is, and org-wide runners are wanted regardless.
Registration stays at POST /orgs/Final-Factory/actions/runners/generate-jitconfig with
runner_group_id 1, which the free plan allows.

FINDING F2 IS THEREFORE ACCEPTED RATHER THAN FIXED, and that belongs in writing so it is not
rediscovered as a surprise. Any repository in the Final-Factory org can still run code on this
box with `runs-on: self-hosted`, including one added later with looser write settings than
FinalFactory has. What this design changes is where that code lands, not whether it can get here:
a throwaway container as ffghr-run instead of the host as FinalFactoryTester. The remaining
control is who can create repositories in the org and who holds write access to them.


9. Teardown and reaping
-----------------------

The happy path deregisters itself. Two paths do not.

A CONTAINER KILLED MID-JOB never calls back, so step 7's DELETE is what removes it. This is why
the runner id is captured at mint time rather than looked up later.

A SUPERVISOR KILLED MID-JOB, by a reboot or SIGKILL, leaves a registration, possibly a container,
certainly an overlay volume and a dirty scratch. ffgithubrunners-reap.timer runs every 15 minutes
and:

  - lists org runners carrying the ffgithubrunners label and deletes any that are offline and
    whose name encodes a nonce with no matching container on this host;
  - removes any ffghr-* container on this daemon with no matching supervisor;
  - removes any ffghr-ws-* volume with no container using it, which also unmounts a stale overlay
    left behind by a daemon restart;
  - clears the scratch of any slot with no running container, per 6.4;
  - leaves anything it cannot explain alone, and logs it.

There is no storage to reap beyond that. --rm plus a tmpfs scratch means a dead container leaves
nothing on ZFS.

GitHub garbage-collects stale registrations eventually. The documented window should be checked
rather than trusted, and the reaper means it does not matter.


10. Replacing game-ci
---------------------

Requirement 5. This is the workflow-visible half of the change and revision 3 found it larger
than revision 2 described.

10.1 WHY IT IS DROPPED AT ALL

Not for taste, and not because it is bad. game-ci's unity-test-runner is a Docker action: it
shells out to `docker run unityci/editor:<tag>` on whatever machine the runner is on. Fact q is
that this is the ONLY reason Unity is available today, since there is no Unity on this host.

That works because the runner is on the host, next to a Docker daemon. Put the runner inside a
container and game-ci needs a daemon it can reach from in there, which means one of:

  - MOUNT A DOCKER SOCKET INTO THE JOB. This is the one revision 1 objected to and the objection
    is right, though not for the reason it gave. The socket would be ffghr-run's, so this is not
    a path to host root. It is a path around every constraint the design puts on the job: a job
    holding that socket can start a sibling container with any bind mount ffghr-run can reach,
    including the warm workspace read-write and the other slots' scratch, with no memory cgroup,
    on any network, outliving its own container. Requirement 1 and requirement 4 both fall.
  - RUN A NESTED DAEMON PER JOB. Needs the same mount and userns machinery fact r says is
    unavailable, and would pull an 11 GB image per job.

  - BE THE IMAGE. The container already IS unityci/editor (fact n), so there is nothing to nest
    and no daemon to reach. game-ci's main job was putting Unity around the step, and being
    inside the Unity image does that.

The third is free, and choosing it is what drops game-ci. Everything below is what else game-ci
was doing that now has to be done somewhere.

10.2 WHAT IT DOES, AND WHAT REPLACES IT

  - Runs the editor in unityci/editor. Replaced by being in that image already (fact n).

  - Activates and returns the Unity licence. Replaced by the job hooks of fact z:
    ACTIONS_RUNNER_HOOK_JOB_STARTED activates and ACTIONS_RUNNER_HOOK_JOB_COMPLETED returns,
    with `trap return_license EXIT INT TERM` inside the hook so a cancel or a crash still gives
    the seat back. This is an IMPROVEMENT on game-ci, which returns the seat in an ordinary step
    that a cancelled job never reaches, and cancelled jobs are exactly what an ephemeral harness
    produces. SIGKILL still cannot be caught by anything in-process, which is why the watchdog in
    section 7 sends TERM first and waits.

    THE SEAT COUNT IS NOT A CONSTRAINT, THE RECLAIM IS. Decided on 2026-08-28: four runners work
    today without trouble, the licence is assumed to allow around ten, and the count is not worth
    designing around until it is actually hit. What matters is that a seat comes back every time,
    which is exactly what game-ci gets wrong and the hooks get right. Activation also happens
    when a job is assigned rather than when the container starts, so an idle slot holds no seat
    and the peak is bounded by concurrent jobs rather than by slot count.

    IF THE LIMIT IS EVER HIT the symptom is an activation failure in the job-started hook. The
    hook exits non-zero and fails the job loudly rather than letting Unity start unlicensed and
    fail later with something confusing. That is the whole mitigation, and it is enough because
    the failure is legible.

  - Runs the tests. A `run:` step invoking `unity-editor -runTests` with the arguments main.yml
    already passes through, plus `-logfile /dev/stdout` which it already sets.

  - Sets outputs the rest of the workflow depends on. `steps.tests.outputs.artifactsPath` and
    `.coveragePath` feed the two upload-artifact steps. A `run:` step must write both to
    $GITHUB_OUTPUT or those uploads fail on an empty path. Revision 2 missed this entirely.

  - Posts check annotations via githubToken. RETAINED, decided on 2026-08-28: the check is how
    anyone sees at a glance whether tests passed, and losing it is not acceptable. Revision 3's
    first draft had this as the one genuine loss of dropping game-ci. It is not a loss, it is
    about forty lines.

    A `run:` step after the tests parses the NUnit XML that Unity already writes and POSTs a
    check run to /repos/{owner}/{repo}/check-runs with per-failure annotations. Everything it
    needs is already in place: main.yml:10 already grants `checks: write`, GITHUB_TOKEN is
    already in the job, python3 is in the image (fact x), and the summary step at main.yml:158
    already parses that same XML for `test-case` elements with result="Failed". The annotation
    carries the file and line from the NUnit `stack-trace` where one is present and attaches to
    the file otherwise.

    TWO LIMITS TO CODE AGAINST. The API takes at most 50 annotations per request, so a run with
    more failures than that needs to PATCH the check run in batches, and a check run holds at
    most 1000. A suite that fails 200 tests should report the first 50 and say so rather than
    silently truncating.

    A MARKETPLACE TEST-REPORTER IS THE ALTERNATIVE and it is deliberately not the first choice.
    It is more third-party code running inside a CI system whose entire purpose is reducing what
    untrusted code can reach, holding the job's GITHUB_TOKEN. If one is used anyway it must be a
    JavaScript or composite action, never a Docker one, for the reason directly below.

  - NOTHING IN THE WORKFLOW MAY BE A DOCKER ACTION. This is the general form of 10.1 and it is
    worth stating once so it is not rediscovered by whoever adds the next step. The runner
    executes a Docker container action by invoking `docker`, which needs a socket this design
    does not provide, and the same is true of a job-level `container:` or `services:` block.
    JavaScript and composite actions are unaffected. main.yml is already clean on this point
    apart from game-ci itself: checkout, cache and upload-artifact are all JavaScript actions.

  - Coverage options. Passed through to the same Unity arguments.

  - runAsHostUser, chownFilesTo. Not needed. Nothing outside the container reads what the job
    wrote, so file ownership stops mattering.

10.3 WHY deploy.yml IS OUT OF SCOPE

Facts q and y together are the reason, and it is a consequence of 10.1 rather than a separate
problem.

deploy.yml passes no customImage, so game-ci picks an image per targetPlatform: a mac-mono image
for StandaloneOSX and a windows-mono one for StandaloneWindows64. It can do that because the
choice happens inside the job, after the job is known. This design starts the container BEFORE a
job is assigned, so the image is fixed before anyone knows which matrix leg will land in it. Fact
x confirms the pinned image carries LinuxStandaloneSupport and WindowsStandaloneSupport and no
Mac module, so the StandaloneOSX leg cannot run in it at all.

Three ways out, and this revision takes the first:

  1. LEAVE deploy.yml WHERE IT IS. It is workflow_dispatch only, so it runs when a human clicks
     it. It keeps using the existing hand-installed runners until those are removed, and gets its
     own revision then. main.yml is the whole point of this system: it fires on every push and
     pull request, which is the exposure the design exists to close.
  2. ONE IMAGE, ALL MODULES. Install the Mac, Windows and Linux modules over the base with Unity
     Hub. Keeps one image and one label pool at the cost of a much larger image and a slower
     stage 4.
  3. LABELLED SLOT POOLS. Different images behind different labels, and `runs-on` in deploy.yml
     names one. Handles per-platform images properly and adds a routing concept to sections 2, 8
     and 13.

Option 1 has a loose end worth stating: this design keeps the `self-hosted` label (section 8), so
a dispatched deploy.yml run could land on an ffgithubrunners slot and fail on the missing Mac
module. Until deploy.yml is dealt with, either its `runs-on` names the old runners explicitly or
the old runners keep a label this design does not claim.

There is a second reason to defer it. unity-builder is not the same size of replacement as
unity-test-runner: it injects its own UnityBuilderAction C# build script into the project and
calls it with -executeMethod, so replacing it means vendoring that script into the repository.
The test-runner swap really is one `run:` step. This one is not.


11. The install script
----------------------

ffgithubrunners/setup.sh: POSIX sh, set -eu, numbered stages with the order in the filenames,
every stage independently re-runnable and a no-op when already satisfied. The shape is borrowed
from ffbox per section 3; none of the code is.

    01-hostSetup.sh   docker and its rootless extras, nftables, uidmap. The ffghr-super and
                      ffghr-run accounts, their subuid/subgid ranges, the ffghr group, linger for
                      ffghr-run. The tmpfiles.d rule for /run/ffgithubrunners and the per-slot
                      tmpfs .mount units of 5.2. The ARC cap and initramfs rebuild. The nftables
                      rules of 5.5. No sudoers file, because nothing here needs one.
    02-zfsSetup.sh    rpool/ffgithubrunners, its docker and warm children, properties and quota
                      per 5.2.
    03-daemon.sh      ffghr-run's rootless daemon as a user service on the stable socket path of
                      5.1, pointed at that data root, plus the wait-for-socket gate the units
                      order behind. Ordered after the slot .mount units.
    04-image.sh       build ffghrunner:latest per 6.1. That is the whole of phase 1. In phase 2
                      it also builds the first warm workspace per 6.2 and verifies: that the
                      overlay volume of 6.3 composes and a container with --cap-drop=ALL can read
                      and write through it, that no GitHub credential survived into warm/current,
                      and that the cleanup container of 6.4 can actually delete a workdir.
    05-github.sh      take App id, installation id and key path; verify the App can actually mint
                      a JIT config against the org, which is also how the permission guess in
                      section 8 gets checked; write /etc/ffgithubrunners/secrets.env.
    06-services.sh    render ffgithubrunners/systemd/*.template into /etc/systemd/system, enable
                      and start ffgithubrunners.target. Root only; --check runs without it.

Stage 4 is the slow one in phase 2. In phase 1 it is fast, because the image is software only and
there is no Unity import in it at all: the import moved to building the warm workspace, which
phase 1 does not have.

Stages 1, 2 and 6 change the system and need root. Stages 3, 4 and 5 write configuration, the
image and the warm data. Resolving who the units should name follows FFGITHUBRUNNERS_RUN_USER,
then SUDO_USER, then the checkout owner. ffbox's 06-services.sh records why SUDO_USER alone is
not enough: run from a systemd timer as root there is no SUDO_USER at all, and every automatic
re-install rendered the units pointing at root's home. Same trap, own implementation.

Templates in ffgithubrunners/systemd/ are the only source, rendered into a throwaway directory
and installed from there, so no second copy on disk can disagree with git.

12. The ffgithubrunners command
-------------------------------

    ffgithubrunners status              slots, containers, volumes, registrations, image tag,
                                        warm workspace age
    ffgithubrunners slot stop|start N   drain or return one slot
    ffgithubrunners drain               let running jobs finish, start no replacements
    ffgithubrunners image update        rebuild ffghrunner:latest, current runner tarball
    ffgithubrunners warm update         rebuild the warm workspace and swap (6.2, phase 2)
    ffgithubrunners reap                run the section 9 sweep now
    ffgithubrunners logs N              the last job's log for one slot, from the tee in 7

Revision 2 had one `image update` doing both jobs. They are separate now because they change on
different clocks: the image follows UNITY_VERSION and the runner release, the warm workspace
follows the repository, and the warm one is the slow one.

drain matters more than it looks. Updating the image, swapping the warm workspace or changing
slots.conf while jobs are running should not kill them, and draining is how to get to an idle box
without watching it.


13. What changes in FinalFactory, and the cutover
-------------------------------------------------

Revision 2 said "two `uses:` steps become `run:` steps" and that was wrong in both directions: the
deploy.yml half is deferred per 10.3, and the main.yml half is two steps rather than one. The
reason is that every `run:` step in the workflow currently executes ON THE HOST, where
FinalFactoryTester has a full toolchain and a persistent workspace. Inside a container they get
the image and a workspace that resets every job.

WHICH PHASE EACH EDIT BELONGS TO, per 2.1. PHASE 1 is 13.3 alone: the game-ci step becomes two
`run:` steps and nothing else in main.yml moves. The checkout keeps its default clean, both cache
steps stay, and the cache-pruning step keeps working because the image carries gh. PHASE 2 is
13.1 and 13.2, which exist only to make the warm workspace pay and are meaningless without it.

13.1 THE ONE DESTRUCTIVE STEP (PHASE 2)

actions/checkout@v7 at main.yml:26 runs `git clean -ffdx` and `git reset --hard` whenever it finds
an existing repository at the workspace path, and fact w says that deletes Library. With the warm
workspace of 6.2 the repository IS already there, so the clean fires on every job and throws away
the warm Library before Unity starts.

The fix is `clean: false`, and the argument for it is stronger here than it looks. `clean: true`
exists because a persistent self-hosted workspace accumulates junk across jobs. With one job per
container and the overlay upper discarded at teardown, the workspace resets to the pristine warm
state by construction. `clean: false` gets the guarantee that clean was buying without paying for
it, and it is safer than the current arrangement rather than a concession.

Two details decide whether checkout takes the reuse path at all. The warm clone's `origin` must be
exactly https://github.com/Final-Factory/FinalFactory.git, which is what it is today, and any
mismatch sends checkout down its delete-everything path. And the LFS objects in .git/lfs/objects
survive a clean regardless, because git clean does not reach inside .git, so the 4.3 GB is safe
either way.

13.2 THE CACHE STEPS COME OUT (PHASE 2)

main.yml:55 restores Library from actions/cache and main.yml:111 saves it. With a warm Library in
the lower, the restore downloads and extracts a multi-GB tarball over a copy that is already
correct, and the save uploads 4.4 GB after every green run. Both are pure cost once 6.2 exists.

Removing them also closes finding F8 for free: the restore-key fallback is what lets a job on one
branch poison a cache another branch restores. Revision 2 listed dropping the cache as a
reasonable second step. It is now required for the warm workspace to pay.

The cache-pruning step at main.yml:118 goes with them. If it stays, the image needs gh (6.1).

13.3 THE game-ci STEP BECOMES TWO run: STEPS (PHASE 1)

Per 10.2. main.yml:65 becomes a `run:` step invoking `unity-editor -runTests`, and it must write
artifactsPath and coveragePath to $GITHUB_OUTPUT or the two upload-artifact steps at main.yml:190
and :195 fail on an empty path.

A SECOND `run:` STEP POSTS THE CHECK RUN, per 10.2, replacing what `githubToken` and `checkName`
at main.yml:77-78 were buying. It runs with `if: always()` so a failing suite still reports, and
it needs no new permission because main.yml:10 already grants `checks: write`.

These two steps are the whole of phase 1's workflow diff. 13.1 and 13.2 belong to phase 2.

13.4 THE SMALL ONES

  - The Editor log dump step searches game-ci's container paths. `$HOME/.config/unity3d/Editor.log`
    is already last in its list and will hit, so it survives, but the dead paths should go.
  - `-logfile /dev/stdout` means the log is in the job output anyway.
  - The LFS materialisation step and its pointer check stay. They get cheaper, because `git lfs
    pull` against a warm .git/lfs/objects is close to a no-op. The failure mode its comment
    describes, a pointer left by an earlier failed smudge that never gets rewritten, cannot
    happen any more: that state lived in a persistent workspace and there is no longer one.
  - `runs-on: self-hosted` is unchanged, because routing is by label.
  - determinism-nightly.yml is untouched.
  - deploy.yml is untouched, per 10.3, with the labelling loose end recorded there.


13.5 CUTOVER

Section 16 used to say this design assumes an empty box, which ducked an ordering problem rather
than solving it. main.yml cannot call unity-editor until the new runners exist, because fact q
says there is no Unity on the host and the current runners would fail on the first job. The new
runners cannot be proven end to end without a workflow that exercises them. The two point at each
other.

THE LABEL IS THE WAY THROUGH. Section 8 gives the slots self-hosted plus ffgithubrunners so that
routing is unchanged. During cutover, do the opposite:

  1. Install with the self-hosted label REMOVED, so a new slot carries only ffgithubrunners,
     Linux and X64. Nothing routes to it by accident, and the old runners keep serving main.yml
     exactly as they do today.
  2. On a branch, add a second job with `runs-on: [self-hosted, ffgithubrunners]` and the `run:`
     step of 13.3. Push it. That job lands only on a new slot, the existing job keeps landing on
     an old runner, and both run against the same commit. This is also the honest version of
     acceptance test 15.10: one suite, one commit, two harnesses, a wall clock for each.
  3. When the new path is boring, delete the temporary job, apply 13.3 to the real one, and add
     self-hosted back to the slot labels.
  4. Stop and unregister the four /opt/github-actions-runner-N installs, and only then delete
     them.

STEP 4 IS WHERE THE deploy.yml LOOSE END BITES. Once the new slots carry self-hosted and the old
runners are gone, a dispatched deploy.yml run routes to a slot with no Mac module and fails. So
either deploy.yml gets an explicit runs-on naming the old runners before step 3, or the old
runners outlive this project until 10.3 is resolved. Deleting them earlier is choosing to break
deploy.yml, and that should be a decision rather than an accident.

ROLLING BACK IS CHEAP UNTIL STEP 3. Nothing in this design touches /opt/github-actions-runner-N,
and nothing touches the real job in main.yml until step 3, so before then the rollback is
`systemctl stop ffgithubrunners.target` with the old harness already running and unaffected.
After step 3 it is reverting one commit in FinalFactory and putting the old runners back on the
self-hosted label.


14. Security properties
-----------------------

WHAT THIS FIXES relative to today. A malicious workflow gets namespace-root in a container that
has no host filesystem mounted, no bind mount at all, one single-use GitHub credential scoped to
one job, a lifetime bounded by the watchdog, and an account underneath it that owns nothing. It
cannot read .git-credentials, .claude/.credentials.json or ffbox's secrets.env, because those
belong to FinalFactoryTester and this runs as ffghr-run. It cannot reach ffbox's Docker socket,
which is a different daemon under a different user. It cannot reach its own daemon's socket
either, which is the point of 10.1. It cannot leave anything for the next job, and the runner
credentials stop existing on disk.

WHAT IT DOES NOT NARROW is who can reach this box at all. Section 8 accepts finding F2 rather
than fixing it, so any repository in the org still routes here. The change is the blast radius,
not the reach.

THE FLAGS, from finding F5, which ffbox does not currently pass and this design does from the
start:

    --cap-drop=ALL --security-opt=no-new-privileges
    --pids-limit=<n> --memory=64g
    --read-only where the image tolerates it, with tmpfs for what must be writable
    default seccomp, never seccomp=unconfined

Fact r is the reason this list is worth restating in revision 3: it is what killed the entrypoint
overlay, and fact s is how the design kept the flags and got the overlay anyway. Any future
proposal to add --cap-add=SYS_ADMIN is a proposal to give the job the mount syscall, which is
precisely the surface escape class 4 says is the one that cannot be otherwise mitigated.

THE ONE WRITABLE MOUNT IN THE SYSTEM is warm/next during the refresh of 6.2, and it is not a job.
It runs our checkout under our control, not a workflow file from a pushed branch. Nothing
untrusted ever writes to a lowerdir.

WHAT IT DOES NOT FIX. Section 4 of docs/ci-runner-security-findings.md lists the escape classes.
Against this design:

  - Class 1, what you handed over: the JIT config and the Unity credentials, both discussed in
    section 7. Bounded, and no worse than the repository secrets the workflow already receives.
  - Class 2, data flow across the boundary: this is the class that bit ffbox (F7) and the one
    revision 3 had to work hardest to avoid, because 6.3 puts a host directory under a job's pen.
    6.4 is the answer: the teardown unlinks and never interprets, and it is done by the daemon
    rather than by the supervisor account.
  - Class 3, runc and crun bugs: lands the attacker on ffghr-run, which owns the daemon, the warm
    workspace and the scratch, and nothing else. Mitigated by 5.1, not eliminated. Note that
    ffghr-run CAN write the warm workspace, so a class 3 escape can poison the lowerdir that
    every subsequent job reads. The refresh rebuilds it weekly from GitHub, which bounds but does
    not close that. Keep docker and runc current.
  - Class 4, kernel exploitation from the user namespace: NOT mitigated. This is the one a VM
    would have changed, and choosing containers is choosing to accept it. The control is patching
    the kernel, and there is no other one.
  - Repository secrets: a job that legitimately runs still receives UNITY_LICENSE, UNITY_EMAIL,
    UNITY_PASSWORD, UNITY_SERIAL and a GITHUB_TOKEN because the workflow asks for them. Anyone
    with write access can print them. Nothing at this layer changes that.
  - actions/cache: finding F8, closed as a side effect of 13.2 rather than by any isolation work.

That is the honest trade. Classes 1 to 3 are handled about as well here as they would have been
under KVM. Class 4 is the price of the decision in section 4.


15. Acceptance
--------------

Grouped by the phases of 2.1. Phase 1 ships when 15.1 to 15.9 pass; nothing in phase 2 gates it.

PHASE 1

  1. Build the image, run one container by hand, run the editmode suite in it on a --tmpfs
     _work, and compare wall clock against the same suite on the host. This is the fact m check:
     the number to watch is whether _work is really in RAM and really being used.
  2. Measure container start to runner-online. Expect a second or two.
  3. Push a branch. Confirm the job lands, the tests run, THE CHECK RUN APPEARS with the right
     pass or fail state and with annotations on a deliberately failing test, both artifacts
     upload, the runner disappears from the org page when the job ends, and a replacement
     appears.
  4. Kill a container mid-job. Confirm the registration is gone within one reap interval, the
     slot comes back, and the Unity seat was returned.
  5. FROM INSIDE A CONTAINER, confirm 192.168.51.0/24 and this host's addresses are unreachable
     and api.github.com is reachable. This one gates 5.5; if it fails the SNI allowlist is
     required, not deferred.
  6. From inside a container, confirm /run/user/1015/docker.sock and
     /run/ffgithubrunners/docker.sock are both unreachable and FinalFactoryTester's home is not
     readable.
  7. Reboot the host. Confirm four slots come back with no hand-holding and ffbox.target comes
     back independently.
  8. Stop a slot with `systemctl stop` five times in ten seconds and confirm it comes back rather
     than landing in `failed`. This is the section 2 backoff.
  9. Run a real PR's worth of jobs with four ffbox runs going at the same time. Check that a lone
     CI job still soaks most of the box and that eight hot workloads divide it without either
     system starving. If one starves, reach for CPUWeight, never a mask.

PHASE 2, and 15.10 is the one that decides how much of phase 2 gets built

 10. Time a cold job against a warm one, checkout and LFS timed SEPARATELY from the suite, per
     5.5. This is requirement 8 and it is also the measurement that says whether phase 2 is worth
     doing at all. Deferred to phase 2 deliberately: it needs a working phase 1 to measure.
 11. THE ONE THAT COULD SIMPLIFY THE DESIGN. Time the suite with the workspace on the container's
     own ZFS-backed overlay2 layer against the tmpfs overlay upper of 6.3. If ARC makes ZFS fast
     enough, 6.3 collapses to 6.5 option 2 and a whole mechanism leaves the design. Run this
     before writing any of 6.3.
 12. Confirm the overlay volume of 6.3 composes on this daemon, that a --cap-drop=ALL container
     reads the lower and writes the upper, and that the cleanup container of 6.4 can delete a
     mode-000 workdir. Facts s and t say all three work; this is the regression check.
 13. Push a branch and confirm the warm Library is still warm after checkout. 13.1 is the thing
     being tested.
 14. Confirm no GitHub credential is present anywhere under warm/current, .git/config included.
 15. Reboot and confirm the slot tmpfs mounts come up before the daemon.

17. Open questions
------------------

ANSWERED BY MEASUREMENT. Revision 2's questions a and b are both settled: the overlay works, by a
different mechanism than proposed (facts r and s), and the Library is 4.4 GB rather than 15 GB
(fact v), which is what made the memory question go away.

CLOSED BY DECISION ON 2026-08-28. Kept here under their original letters so references elsewhere
in this file still resolve.

  d. THE ORG'S PLAN, AND THEREFORE RUNNER GROUPS. Final-Factory is on the free plan, and org-wide
     runners are wanted regardless. No runner group, registration stays org-scoped with
     runner_group_id 1, and finding F2 is accepted rather than fixed. Section 8.

  e. HOW MANY UNITY SEATS THE LICENCE ALLOWS. Not a constraint until it is actually hit. Four
     runners work today, ten activations is a safe working assumption, and the real requirement
     is that a seat comes back every time, which is what the hooks give and what game-ci does
     not. A hit limit shows up as a loud activation failure in the job-started hook. Section 10.2.

  h. CHECK ANNOTATIONS. Retained, not lost. A `run:` step parses the NUnit XML and posts a check
     run with annotations, using the `checks: write` permission main.yml already grants. Sections
     10.2 and 13.3.

STILL OPEN.

  a. THE NETWORK MEASUREMENT IN 5.5. The uid-scoped nftables rule is a better lever than revision
     2 had, but it is still untested. Acceptance test 15.5 decides whether an SNI allowlist has to
     be built now or can wait.

  b. WHETHER THE OVERLAY IS WORTH ITS COMPLEXITY. A PHASE 2 question, and acceptance test 15.11
     answers it. If the workspace on ZFS is fast enough, 6.3, 6.4 and most of section 9's volume
     handling all leave the design. It should be run before any of 6.3 is written.

  c. WHETHER A TMPFS MOUNTED AFTER ROOTLESSKIT STARTS PROPAGATES INTO THE DAEMON'S MOUNT
     NAMESPACE. 5.2 sidesteps it by ordering the mounts before the daemon, so this only matters
     for adding a slot without restarting the daemon.

  f. PIDS-LIMIT AND THE REAL MEMORY SHAPE. --pids-limit needs a number that a real Unity import
     does not trip. The 32 GB non-scratch half has fact l behind it but has not been measured for
     a containerised RUNNER as opposed to a containerised agent.

  g. WHETHER --read-only IS TOLERABLE for this image, or whether Unity and the runner need enough
     scattered writable paths that the tmpfs list becomes unmanageable. The runner writes _diag
     regardless.

  i. WHETHER FFBOX SHOULD ADOPT A RAM DISK. Fact m is a property of Unity on ZFS, not of this
     harness, so ffbox's runs are paying the same cost. Out of bounds to act on, and it fits the
     budget in 5.3 if it happens. Noted so it is a decision rather than a collision.

  j. IF A FUTURE WORKFLOW NEEDS `docker build`, this design has no answer that does not
     reintroduce the socket of 10.1. Revisit the section 4 choice if that day comes rather than
     bolting a socket in.
