ffgithubrunners: single-use GitHub Actions runners in rootless containers
=========================================================================

2026-08-28.

Four GitHub Actions runners on Loth2400 are hand-unpacked tarballs in /opt/github-actions-runner-N
that nothing in git describes, and every workflow step outside the game-ci container runs on the
host as FinalFactoryTester. main.yml triggers on [push, pull_request] with `runs-on: self-hosted`
and GitHub evaluates the workflow file from the pushed branch, so anyone who can push to the org
can read that account's git credential, its Claude token and its rootless Docker socket.

This replaces them with a checked-in harness that runs every job in a throwaway rootless
container under an account that owns nothing. Host findings that motivated it are in
docs/ci-runner-security-findings.md.


1. What gets built
------------------

  1. One job per container. The container did not exist before the job and does not exist after
     it. Nothing a job writes reaches the next job except through GitHub.
  2. Nothing worth stealing on the account a job runs as, and no path from a job to the
     credentials without a container escape followed by a second escalation.
  3. No sudo at run time. Install-time root only, typed by a human.
  4. No writable bind mount out of a container, and no host command run against anything a job
     wrote.
  5. game-ci's behaviour preserved, including the test-results check run, and its licence leak
     fixed.
  6. Reinstallable from git with one command.
  7. Shares ffbox's two accounts, its Docker daemon and its egress tooling. Own image, own
     network, own allowlist, own units, own folder.

Not a goal: protecting a job from itself. A job gets namespace-root in its own container.


2. The slot lifecycle
---------------------

A SLOT IS A PLACE FOR A RUNNER, NOT A RUNNER. Slots are configurable and default to 1; how many of
them hold a runner at any moment is the other knob, idle_pool, also 1 by default. A slot takes one
job, runs it, and its container exits.

    wait for a place in the pool
      -> mint JIT config -> docker run --rm -> runner idles
      -> runner takes one job, runs it, deregisters, container exits
      -> remove the container, DELETE the registration
      -> supervisor exits, systemd restarts it

The pool is idle_pool runners registered and waiting, plus one per job in flight, never more than
slots altogether. A supervisor with no container holds NOTHING: no container, no registration, and
GitHub has never heard of it. So slots is the ceiling on concurrency and idle_pool is what the
harness costs while nothing is happening, and the two are set independently.

    admit a runner  <=>  containers < slots  AND  idle containers < idle_pool

Both counts come from the daemon and from the host, never from the API: `docker ps` filtered on the
ffghr.slot label is the total, and a container is BUSY when it has a Runner.Worker process, which
the supervisor watching it sees with `docker top` and records as a file under state/. Deciding this
from GitHub instead would mean every waiting slot polling /orgs/.../actions/runners several times a
minute for an answer the machine already has.

The decision is taken under one lock, held across the mint and the docker run that follows it,
because it is read from a count that acting on it then changes. Two supervisors that both saw "no
idle runner" a millisecond apart would otherwise both mint one.

Latency is the cost, and it is bounded by the poll interval, five seconds: a job arrives, the
supervisor of the idle runner notices its Runner.Worker within five seconds, a waiting slot admits
within another five, and the replacement is listening a second or two after that. Jobs run for
minutes, so a burst walks the pool up to the ceiling without ever waiting on it.

One instance of ffgithubrunners@.service per slot, running as FinalFactoryTester. Each runs
slot.sh with the slot number as its argument:

  0. Wait for a place: if the drain flag or this slot's stop flag is set, or the pool already has
     the idle runners it wants, sleep and recheck rather than take work.
  1. Mint an installation token from the GitHub App, then POST
     /orgs/Final-Factory/actions/runners/generate-jitconfig with the slot's name, its labels and
     runner_group_id 1. Keep the returned runner id. Back off and retry on API errors.
  2. `docker run --rm` against ffbox-container's daemon with the flags in section 12, the JIT
     config in the environment, a --tmpfs workspace, and no bind mounts.
  3. Wait for the container to exit, with a watchdog that sends TERM and waits before KILL so the
     job's licence trap can return the Unity seat. The watchdog defaults to 120 minutes, above
     main.yml's timeout-minutes: 90, so a job GitHub still wants is never killed here.
  4. Tee the container's output to /var/log/ffgithubrunners/slot-N.log, rotated. `--rm` would
     otherwise take the log with the container.
  5. Teardown, unconditionally: remove the container if it is still there, then DELETE the
     registration. A clean exit deregisters itself, so this usually returns 404.
  6. Exit 0. systemd restarts the unit and the slot comes back.

Configuration follows ffbox's convention: defaults in code, overlaid with
~/.config/ffbox/githubrunners/config.json, then FFGITHUBRUNNERS_* environment overrides.
Everything ffbox owns on a machine lives under ~/.config/ffbox, and this is a component of it
rather than a second product, so it takes a subdirectory there the way the Discord CLI does.

Its own secrets.env at 0600 sits beside that config, NOT in ffbox's ~/.config/ffbox/secrets.env,
which is an EnvironmentFile for ffbox's units and reaches ffbox's containers. Using a GitHub App
that file stays empty: the App's two ids are configuration and live in config.json, and its
private key is github-app.pem beside them, at a fixed path nothing has to record.

    slots             1     the ceiling: unit instances, and so jobs in flight
    idle_pool         1     runners registered and waiting while nothing is happening
    watchdog_minutes  120
    image             ffghrunner:latest
    labels            self-hosted, Linux, X64, ffgithubrunners
    org               Final-Factory

The unit template carries WantedBy=ffgithubrunners.target, so changing the slot count means
enabling ffgithubrunners@1 through @slots and disabling the rest, which 05-services.sh and
`ffgithubrunners slots N` both do.

The unit sets StartLimitIntervalSec=0 with RestartSec around 5 seconds. With systemd's defaults a
fast-failing condition burns five restarts in a second and leaves the slot in `failed` until
someone runs `systemctl reset-failed`.

Inside the container the entrypoint sets RUNNER_ALLOW_RUNASROOT=1, which the runner requires
before it will start as root, and execs `Runner.Listener run --jitconfig "$JIT"`. There is no
--disableupdate: it is a config.sh option, not a run option, and no environment variable replaces
it. The weekly image rebuild is what keeps the runner current enough to be given jobs.

The image chowns /opt/actions-runner to root. The tarball ships owned by uid 1001, and --cap-drop
=ALL takes CAP_DAC_OVERRIDE away from root, so without it the runner cannot write its own .runner
file.
The container is the boundary, not the uid inside it. Nothing polls GitHub, nothing receives a
webhook, and no inbound port is opened. Container start is about a second.


3. Accounts and the daemon
--------------------------

  FinalFactoryTester   runs the supervisor units, and is the same account that runs ffbox and
                       the human's interactive session. Holds the GitHub App private key at
                       ~/.config/ffbox/githubrunners/github-app.pem, mode 0600.
  ffbox-container      owns the rootless Docker daemon and the namespace every job runs in. Its
                       home is empty: no tokens, no credentials, no sudo, no login shell. A
                       container escape lands here and finds nothing.

The split that matters is that no workflow code ever runs as FinalFactoryTester. A job runs in a
container under ffbox-container, with no bind mounts and no socket, so reaching the credentials
FinalFactoryTester holds takes a container escape and then a second escalation between accounts.

Neither account gets a new sudoers entry. Nothing here needs one at run time.

ffbox-container is created by this design. Today's rootless daemon runs as FinalFactoryTester on
/run/user/1015/docker.sock and is ffbox's; the new one is a second daemon. 01-hostSetup.sh creates
the account as an ordinary user rather than a system one, because useradd allocates the
/etc/subuid and /etc/subgid ranges rootless Docker needs only for ordinary users. Section 17 moves
ffbox onto this daemon afterwards, which is what makes it the one rootless daemon on the box.

The daemon listens on a stable path, NOT under /run/user:

    dockerd-rootless.sh -H unix:///run/ffbox-container/docker.sock --group 0

That directory comes from a tmpfiles.d rule, owned ffbox-container:ffbox-container mode 0750, with
FinalFactoryTester in the ffbox-container group.

--group 0 is what makes that membership worth anything. dockerd sets the socket's group itself and
defaults to --group docker, resolving the name against the host's /etc/group but applying it inside
the user namespace, where only gid 0 maps back to a real host group. The default lands the socket on
a subgid no account is in, and the supervisor gets EACCES whatever the directory permits. /run/user/<uid> is created by logind at mode 0700
on a tmpfs that is recreated per session, so ACLs on it do not persist and it does not exist at
all for an account that never logs in. Linger is enabled for ffbox-container so its user manager
starts at boot.

The daemon gets its own data root on its own ZFS dataset, outside the boot environment, with
sync=disabled and a quota, the same treatment ffbox's store gets. Until section 17 runs there are
two stores and two copies of the unityci base image on this box, so budget the disk. There are no
per-job datasets and nothing to clean up: the image is shared read-only and the workspace is
tmpfs.

BECAUSE THE DAEMON IS SHARED, EVERYTHING THIS DESIGN DOES TO IT IS NAME-SCOPED. Containers are
ffghr-*, the image is ffghrunner:latest, the network is its own. The reaper in section 9 touches
only ffghr-* names, and nothing here ever runs `docker system prune` or any other sweep that
would reach ffbox's containers or images.

EGRESS IS FFBOX'S, NOT A SECOND MECHANISM. ffbox/egress/ffbox-egress.sh already builds exactly
the fence this needs: an --internal Docker bridge with no default route, so no internet, no LAN
and no host, whose only neighbour is a proxy doing DNS and SNI filtering against an allowlist.
A name not on the list does not resolve, and a connection whose SNI does not match is refused.
Both are logged, but by different mechanisms, so read them with `03-image.sh --egress-log` rather
than ffbox's own `log`, which shows the SNI half only. No host firewall rule and no root are
involved, because under the rootless daemon the bridge lives in rootlesskit's network namespace
and the host is not on the other side of it.

The script parameterises the network, bridge, subnet, proxy IP, container name and allowlist path
through FFBOX_EGRESS_*, so this runs a second instance of the same script and the same image:

    ffghr-net        --internal bridge, its own subnet
    ffghr-egress-net the routed uplink, the proxy alone on it
    ffghr-egress     the proxy, at its own address on that subnet
    allowlist        ffbox/runners/egress/allowlist.txt

The proxy image is ffbox's, but ffbox built it onto the other daemon, so 03-image.sh builds
ffbox-egress:latest under ffbox-container before bringing the fence up. ffghr-egress.service keeps
it up and orders it after the daemon.

The container joins ffghr-net with --dns pointed at the proxy and holds no capability to change
any of it: all of it lives in the daemon's network namespace, not the job's.

TWO INSTANCES RATHER THAN ONE, and the reason is the allowlist rather than the mechanism. ffbox's
list has no GitHub entry at all, deliberately: its container never pushes, the host does. CI has
to reach github.com, the Actions broker, LFS, artifact storage and the cache service, and putting
those on ffbox's list would hand ffbox's containers a reach they do not have today.

The list starts from ffbox's Unity licensing and package entries, plus GitHub. The exact set is
discovered rather than guessed: run the proxy with FFBOX_EGRESS_MODE=log for a few real jobs and
read back what was actually asked for. Known so far: the runner talks to
broker.actions.githubusercontent.com and a pipelinesghubeus* host as well as api.github.com, and
artifact upload and actions/cache both go to storage hosts that log mode will name.


4. The image
------------

ffghrunner:latest:

    FROM unityci/editor:ubuntu-6000.3.19f1-windows-mono-3.2.2

The same tag main.yml passes as customImage and ffbox builds from. Being this image is what
replaces game-ci: the container IS the Unity environment, so nothing is nested and no Docker
socket is needed inside a job. Keep the tag in lockstep with UNITY_VERSION in main.yml.

On top of the base:

  - the actions runner tarball at /opt/actions-runner, unconfigured, with its
    bin/installdependencies.sh run so the .NET runtime has what it wants
  - gh, which the base image lacks and main.yml's cache-pruning step needs
  - the /BlankProject scaffolding Unity's serial activation wants
  - the entrypoint, and unity-license.sh at a fixed path the workflow's `run:` step calls

The base already carries git, git-lfs, python3, curl, jq and unity-editor.

`ffgithubrunners image update` rebuilds it weekly. It pulls a current runner tarball as well as
the base image: GitHub enforces a minimum runner version and a runner baked into a container
cannot self-update, so a stale image eventually stops being given jobs.

THE VERSION LIVES IN THE DOCKERFILE, NOT IN THE BUILD ARG, and that was a real bug from the day the
self-updater started rebuilding on every commit. ARG RUNNER_VERSION is what every other build path
uses, so the weekly --build-arg lasted exactly until the next push and the weekly log then said
"already current" forever, comparing against the image it had just rebuilt. Nobody would have seen
it until GitHub stopped scheduling jobs. So the weekly run commits the new version and pushes it,
and the updater distributes it.

The order is the safety property: the build proves the version (the Dockerfile runs
Runner.Listener --version) before anything is written down. The commit happens only on a clean
checkout that is exactly at origin, under update_ffbox.sh's lock so a merge cannot land underneath
it, and a failed push is rolled back — an unpushed commit and a dirty tree are each a reason the
updater does nothing, so leaving either would stop the box taking any code at all.


5. The workspace
----------------

    --tmpfs <runner _work path>:size=40g,mode=1777

The mount target must equal the work folder passed to generate-jitconfig. If they differ the
runner writes to the image's writable layer instead and the tmpfs does nothing, silently.

Empty at container start. actions/checkout clones, git lfs pull materialises, actions/cache
restores the Library, exactly as they do today. The existing runners already run _work on a 40 GB
tmpfs via makeRamDisk.sh and that ram disk is worth about 4x on build and test; this keeps it.

Measured across twelve recent jobs: checkout averages 117s, LFS 21s, cache restore 108s, tests
456s. The workspace is already empty on three jobs in four, because the tmpfs is wiped whenever a
runner restarts, so making it always empty costs about two minutes on the minority of jobs that
would have been warm.

Nothing is bind-mounted. No host directory is writable by a job, no host command runs against
anything a job produced, and results leave the way GitHub expects: the runner uploads its own
artifacts and posts its own results over its own connection.


6. GitHub identity
------------------

Ephemeral runners register a new runner for every job, so something on this box must be able to
call the GitHub API continuously. That is the only reason a credential is needed here; the
workflows are unaffected. The current runners were registered once by hand and have been coasting
on the .credentials files ever since.

Either credential works and lib/gh.sh handles both:

  a fine-grained PAT    with the organization's self-hosted runners permission at write. One
                        setting to create, and the smallest thing to start with.
  a GitHub App          installed on the org, same permission. Better hygiene, because
                        installation tokens expire in an hour and no personal account is in the
                        loop, at the cost of more setup.

It lives in ~/.config/ffbox/githubrunners/, as secrets.env for a PAT or a key file for an App,
mode 0600, owned by FinalFactoryTester. Either needs one organization permission, "Self-hosted
runners", at write. That covers registering and removing runners and nothing else: it grants no
access to code, and jobs read the repo with the GITHUB_TOKEN Actions mints per run, which
main.yml already caps at contents: read. No container ever sees it. Stage 4 verifies by actually minting
a JIT config, so a wrong permission fails at install time rather than at run time.

JIT config rather than a registration token, so nothing is written to disk: the .credentials and
.credentials_rsaparams files of the current runners stop existing.

Registration is org-scoped with runner_group_id 1. Final-Factory is on the free plan, where
Default is the only runner group, and org-wide runners are wanted anyway. Finding F2 is accepted:
any repository in the org can still reach this box, and what changes is that the code lands in a
throwaway container as ffbox-container instead of on the host as FinalFactoryTester.

Labels are Linux, X64 and ffgithubrunners, and deliberately NOT self-hosted. main.yml names
`runs-on: ffgithubrunners`, a label only these runners carry, while deploy.yml keeps
`runs-on: self-hosted`, which only the four legacy runners carry. The two sets never overlap, so
neither needs relabelling and deploy.yml needs no pinning. Names are ffghr-loth2400-<slot>-<nonce>, where the nonce is generated locally at mint
time; the reaper matches on it.


7. Replacing game-ci
--------------------

game-ci is a Docker action: it runs `docker run unityci/editor` on the runner's machine. With the
runner inside a container that would need a Docker socket in the job, which is a way around every
limit this design places on a job. Being the image instead costs nothing.

What game-ci did, and what does it now:

  - Runs the editor in unityci/editor. The container is that image.
  - Activates and returns the Unity licence. The `run:` step does it, carrying the same
    UNITY_LICENSE, UNITY_SERIAL, UNITY_EMAIL and UNITY_PASSWORD `env:` block the game-ci step
    carries today, so the credentials keep flowing exactly as they do now and nothing new holds
    them. UNITY_SERIAL is EMPTY on this project: it is a Personal licence, so the serial is
    carried base64-encoded in UNITY_LICENSE's DeveloperData field and unity-license.sh decodes it
    the way game-ci and ffbox/04-warmLibrary.sh both do. Activation is an online serial
    activation either way. The step installs `trap return_license EXIT INT TERM` before starting Unity, which is
    what ffbox/unity-license.sh does and what game-ci does not: game-ci returns the seat in an
    ordinary later step that a cancelled job never reaches, and that is how it leaks them. A seat
    is held only while the step runs, so an idle slot holds none. If activation fails the step
    exits non-zero and the job fails loudly rather than letting Unity start unlicensed.
  - Runs the tests. A `run:` step calling `unity-editor -runTests` with the arguments main.yml
    already passes, plus `-logfile /dev/stdout`.
  - Feeds later steps. That `run:` step writes artifactsPath and coveragePath to $GITHUB_OUTPUT,
    or the two upload-artifact steps fail on an empty path.
  - Posts the test-results check. A second `run:` step calls .github/scripts/post-check-run.py in
    the game repo, which parses the NUnit XML and POSTs a check run with per-failure annotations.
    main.yml:10 already grants `checks: write` and python3 is in the image. The API takes 50
    annotations per request and 1000 per check run, so a large failure set reports the first 50
    and says so. A file rather than an inline heredoc, so it can be run against a saved
    results.xml without pushing.
  - Coverage options, runAsHostUser, chownFilesTo. The first passes through to Unity; the other
    two stop mattering, because nothing outside the container reads what the job wrote.

NO DOCKER ACTIONS ANYWHERE IN THE WORKFLOW, and no job-level `container:` or `services:`. The
runner executes those by invoking `docker`, which is not available in a job. JavaScript and
composite actions are fine, and main.yml uses only those apart from game-ci itself.


8. Changes to FinalFactory
--------------------------

main.yml:65, `uses: game-ci/unity-test-runner@v4`, becomes two `run:` steps per section 7: one
that activates the licence, runs the tests and sets the two outputs, and one with `if: always()`
that calls the new .github/scripts/post-check-run.py. The first carries the same UNITY_* `env:` block the game-ci step has
today, unchanged. `githubToken` and `checkName` at main.yml:77-78 go with the old step.

Nothing else changes. The checkout keeps its default clean, both cache steps stay, the LFS
materialisation step stays, and the cache-pruning step keeps working because the image carries gh.
The Editor log dump searches game-ci's container paths but has $HOME/.config/unity3d/Editor.log
last in its list, so it still finds the log; the dead paths can go when someone is in there.

`runs-on: self-hosted` becomes `runs-on: ffgithubrunners`, in the same commit as the steps: they
call /opt/ffghr/unity-license.sh, which exists only inside the container, so on the old runners
they would fail on the first push. The Editor log dump loses game-ci's two dead container paths.
deploy.yml and determinism-nightly.yml are untouched, and deploy.yml needs no pinning because
self-hosted is carried only by the legacy runners.


9. Teardown and reaping
-----------------------

A clean exit deregisters itself. A container killed mid-job does not, which is why the supervisor
captures the runner id at mint time and issues the DELETE unconditionally.

A supervisor killed by a reboot or SIGKILL leaves a registration and possibly a container.
ffgithubrunners-reap.timer runs every 15 minutes and:

  - deletes org runners with the ffgithubrunners label that are offline and whose name carries a
    nonce with no matching container here;
  - removes ffghr-* containers with no matching supervisor, and nothing else on the shared
    daemon;
  - leaves anything it cannot explain alone, and logs it.

There is nothing else to reap. `--rm` plus a tmpfs workspace leaves nothing behind.


10. Install
-----------

ffbox/runners/setup.sh: POSIX sh, set -eu, numbered stages, each independently re-runnable and
a no-op when already satisfied.

    01-hostSetup.sh   docker and its rootless extras, uidmap. The ffbox-container account and
                      group, its subuid/subgid range, FinalFactoryTester's membership of that
                      group, linger for ffbox-container, the tmpfiles.d rule for
                      /run/ffbox-container, the daemon's data root dataset, and
                      /var/log/ffgithubrunners with its logrotate rule. No sudoers file and no
                      firewall rule.
    02-daemon.sh      ffbox-container's rootless daemon as a user service on the stable socket,
                      its data root and quota, and the wait-for-socket gate the other units order
                      behind. A no-op if the daemon is already running.
    03-image.sh       build ffghrunner:latest, and bring up ffghr-net and ffghr-egress by
                      calling ffbox/egress/ffbox-egress.sh with this system's FFBOX_EGRESS_*
                      values.
    04-github.sh      take App id, installation id and key path, verify the App can mint a JIT
                      config, record the ids in config.json and the key at github-app.pem. Takes
                      no arguments once configured.
    05-services.sh    render ffbox/runners/systemd/*.template into /etc/systemd/system, enable
                      ffgithubrunners@1 through @SLOTS, start ffgithubrunners.target.

Stages 1 and 5 need root. Which user the units name resolves as FFGITHUBRUNNERS_RUN_USER, then
SUDO_USER, then the checkout owner: run from a timer as root there is no SUDO_USER, and ffbox has
already been bitten by units rendered pointing at root's home.

Templates in ffbox/runners/systemd/ are the only source, rendered into a throwaway directory and
installed from there, so no second copy on disk can disagree with git.

    ffgithubrunners/
      setup.sh

      Dockerfile
      entrypoint.sh                    exec the runner

      slot.sh                          the supervisor: one slot, one job, teardown
      wait-for-docker.sh               the gate: After= does not cross into a user manager
      ffgithubrunners                  the CLI
      lib/gh.sh                        PAT or App auth, jitconfig, delete
      lib/config.sh                    defaults, config.json, FFGITHUBRUNNERS_* overrides
      egress/allowlist.txt             this system's allowlist, per section 3
      systemd/ffgithubrunners@.service one slot, restart with backoff
      systemd/ffgithubrunners.target
      systemd/ffbox-container-dockerd.service  the shared daemon
      systemd/ffghr-egress.service     the fence, after the daemon
      systemd/ffgithubrunners-reap.{service,timer}
      systemd/ffgithubrunners-image.{service,timer}
      config.json.example              slots, idle_pool, watchdog, image, labels, org

      secrets.env.example
      README.md


11. The ffgithubrunners command
-------------------------------

    ffgithubrunners status              the pool, containers, registrations, image tag and age
    ffgithubrunners slots [N]           show or set the ceiling, default 1
    ffgithubrunners idle [N]            show or set the idle pool, default 1
    ffgithubrunners slot stop|start N   drain or return one slot
    ffgithubrunners drain               let running jobs finish, start no replacements
    ffgithubrunners image update        rebuild the image with a current runner tarball
    ffgithubrunners reap                run the section 9 sweep now
    ffgithubrunners logs N              the last job's log for one slot

drain is what makes an image update or a slot-count change safe while jobs are running.

drain and slot stop|start write a flag file under ~/.config/ffbox/githubrunners/ which slot.sh checks
before it mints a JIT config, so a drained slot stays running and idle rather than being stopped.
Nothing there talks to the system manager, which is why the image timer can drain on its own and
why no account needs a sudoers entry. slots N is the exception: it enables and disables unit
instances, so it re-invokes itself through sudo and prompts.

idle N is the cheap one: it writes one integer to config.json, which every waiting slot re-reads
each time round its loop, so it needs no privilege and nothing restarts. It only ever ADDS runners.
Lowering it stops none, because killing an idle runner races GitHub handing it a job and the runners
are single-use anyway: the extra ones retire by taking one job each.


12. Security properties
-----------------------

A malicious workflow gets namespace-root in a container with no host filesystem mounted, no bind
mount at all, one single-use credential scoped to one job, a lifetime bounded by the watchdog, and
an account underneath it that owns nothing. It cannot read .git-credentials,
.claude/.credentials.json or ffbox's secrets.env, cannot reach ffbox's Docker socket or its own
daemon's, and cannot leave anything for the next job. The runner credentials stop existing on
disk.

The flags, per finding F5:

    --cap-drop=ALL --cap-add=CHOWN --cap-add=FOWNER --cap-add=DAC_OVERRIDE
    --security-opt=no-new-privileges
    --pids-limit=<n> --memory=72g
    --read-only where the image tolerates it, with tmpfs for what must be writable
    default seccomp, never seccomp=unconfined

Egress is closed by default: the job's network has no route off the box except a proxy that
refuses any name not on the allowlist, and the job cannot change that because the network lives
in the daemon's namespace.

--memory IS A CEILING, NOT AN ALLOCATION. Nothing is reserved: a container uses what it uses and
an idle slot uses almost nothing, so N slots at 72g do not commit N x 72 GB. The limit exists for
one failure. Workspace tmpfs pages are charged to the container's cgroup and this host has 2 GB of
swap, so a job that fills the 40 GB workspace while Unity is resident would push the host into
swap, where things fail rather than slow down. The ceiling turns that into one dead job. 72g is
the 40 GB workspace plus about 32 GB for the editor, which is what ffbox measures for the same
work; a legitimate job never comes near it.

THE THREE CAPABILITIES ADDED BACK ARE WHAT UNITY NEEDS, AND WERE FOUND BY RUNNING IT. A real
editmode job on 2026-08-29 activated, started the editor, resolved packages for 39 seconds and
then failed with

    com.unity.jobs: TAR_ENTRY_ERROR: EPERM: operation not permitted, fchown

UPM extracts package tarballs as root and preserves the ownership recorded in them: a chown, then
a chmod on the file it just gave away, then a write into a directory it just gave away. CHOWN,
FOWNER, DAC_OVERRIDE, each found by adding the previous one and hitting the next wall. Docker's
default capability set includes all three, which is why game-ci never met this.

They are filesystem-permission capabilities inside a container whose filesystem is already
entirely the job's own, and none is a step toward leaving it. The same class of problem took the
runner's own .runner file earlier, which the image fixed by chowning /opt/actions-runner to root
rather than by adding DAC_OVERRIDE.

CAP_SYS_ADMIN is never added. It hands a job the mount syscall, which is the kernel surface with
no other mitigation.

What this does not fix: kernel exploitation from the user namespace, which is the one a VM would
have changed and which patching is the only control for. Repository secrets, which a job receives
because the workflow asks for them. Runtime bugs in runc, which land on ffbox-container and are
the reason that account owns nothing. The org-wide reach of section 6. And finding F1:
FinalFactoryTester still holds every credential on this box and is still in sudo, so a second
escalation out of ffbox-container reaches all of it at once.


13. Cutover
-----------

main.yml cannot call unity-editor before the new runners exist, because there is no Unity on the
host, and the new runners cannot be proven without a workflow that uses them. The label is the way
through.

  1. Install with the self-hosted label removed, so a new slot carries only ffgithubrunners, Linux
     and X64 and nothing routes to it by accident. The old runners keep serving main.yml. This is
     now the permanent label set, not a temporary one.
  2. On a branch, add a second job with `runs-on: [self-hosted, ffgithubrunners]` and the steps
     from section 8. Both harnesses then run the same commit side by side.
  3. When the new path is boring, delete the temporary job and apply section 8 to the real one.
     Section 8 changes main.yml's runs-on to ffgithubrunners in the SAME commit as its steps,
     because those steps call /opt/ffghr/unity-license.sh, which exists only inside the container:
     the steps on the old runners would fail immediately. No label is added to anything.
  4. Stop and unregister /opt/github-actions-runner-N, and only then delete them.

deploy.yml passes no customImage, so game-ci picks a per-platform image and its StandaloneOSX leg
needs a Mac module ffghrunner:latest does not have. It needs no edit: it asks for self-hosted,
which only the legacy runners carry. Those runners therefore stay until deploy.yml is dealt with
separately, and step 4 below applies to main.yml's traffic rather than to the machines.

Before step 3 the rollback is `systemctl stop ffgithubrunners.target`, with the old harness still
running. After it, revert one commit.

     BOTH HALVES OF GAME-CI'S ANSWER, now read from the source rather than from memory. The pin is

     forward compatibility for unity activation", and the hex decodes to "Webber&GabLeRoux". It is
     right for a .ulf licence FILE, which is bound to a machine, so one downloaded licence works in
     every container. The ACTION then undoes it for a personal SERIAL activation —
     unity-test-runner v4 dist/platforms/ubuntu/entrypoint.sh:3-7, identical in unity-builder:

         # Ensure machine ID is randomized for personal license activation
         if [[ "$UNITY_SERIAL" = F* ]]; then
           dbus-uuidgen > /etc/machine-id && ... ln -sf /etc/machine-id /var/lib/dbus/machine-id
         fi

     main.yml stopped running that action when it dropped the docker action for a direct
     unity-license.sh call, and nothing replaced it. Our .ulf is bound to a real 2018 machine, not
     to the pinned container id, so the file-licence path was never available to us either; the
     serial activation is what we do and it is what needs a distinct machine.

     WHAT WE DO INSTEAD OF RANDOMIZING. entrypoint-ci.sh writes an id the supervisor derives from
     the SLOT (sha256 of host and slot number, first 32 hex; machine_id in config.json, 'image'
     restores the pin). An activation registers a machine and only -returnlicense gives it back, so
     a job that is SIGKILLed leaks one: with game-ci's per-container random id every leak is
     permanent, because that machine never comes back, while a per-slot id bounds the licence's
     registrations at the slot count and lets the next job on that slot reuse its entitlement.
     That reuse is not a guess — it is why sequential jobs work today on the pinned id despite
     whatever the watchdog has leaked.

     ffbox's agent lane keeps the pinned id, and for its own reason: a loop re-running constantly
     would burn an activation every time. Open item (d) — whether the watchdog's TERM reaches the
     licence trap — is now the only thing that leaks a seat, and it leaks a REUSABLE one.

     Still unmeasured: how many machines this Personal licence will hold seats for at once. Six
     slots do not create six entitlements if the licence only grants two.

  d. Whether the watchdog's TERM reaches the licence trap. PID 1 in the container is
     Runner.Listener and the trap is two processes below it, so the seat may not come back on a
     watchdog kill. Measure it; if it does not hold, exec the return before killing or say in the
     README that a killed job leaks a seat.
  c. Whether --read-only is tolerable, or whether Unity and the runner want enough scattered
     writable paths that the tmpfs list becomes unmanageable. The runner writes _diag regardless.

17. Afterwards: moving ffbox onto the shared daemon
---------------------------------------------------

Once the runners are boring, ffbox moves off FinalFactoryTester's daemon and onto ffbox-container's.
That ends the two-store duplication of section 3 and takes the last workload off the account holding
the credentials.

The blocker is the bind mount. ffbox mounts its ZFS clone read-write and its entrypoint drops to the
uid owning it, which works only because FinalFactoryTester owns both the clone and the daemon. Under
ffbox-container's daemon that uid maps to a subuid nobody has, so nothing the run writes can be read
back or committed. Deciding how the workspace crosses the boundary is the whole of this work; the
rest is rebuilding ffbox's images and networks under the new account, repointing everything that
names the socket, and destroying the old store.

Two things happen by hand at the end, by a human who can see what is still running: removing
FinalFactoryTester from the docker group, and uninstalling its daemon.
