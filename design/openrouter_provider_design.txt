OpenRouter as a credential type, and GLM-5.3 Flash for the work nobody's subscription pays for
============================================================================================
Revision 6, 2026-09-10. Revisions 1-5, 2026-09-10. Tasks: design/openrouter_provider_tasks.md.
2026-09-11: the operator field that names a credential was renamed from `claude` to `model`, in
config.json and in the code, and this file says `model` throughout. Later the same day the
top-level `claude` block was split: `default`, `classifier`, `health` and `classify_retry` moved to
a top-level `model` block beside the model aliases (the old top-level `model`, `fallback_model` and
`classifier_model`, now `model.container`, `model.container_fallback` and `model.classifier_model`),
and the window reading and the holds became `subscription`. This file still says `claude.default`,
`claude.classifier` and so on; read them as `model.*`, and the holds as `subscription.*`.

Section 13's measurements run before phases C onward are deployed. Phases A and B (sections 7 and
14) rest on failure shapes the code already recognises (`result_failure_detail`,
ffwatch.py:17231) and ship first.

eb4cfaa ("whose subscription pays is decided by who asked", design/operator_subscriptions_design.txt)
gave every request exactly one payer. An operator's request is billed to the credential that
operator claims. Everything else goes to one metered default: players in forum threads, the
engagement gate, the selector, and a fix leg spawned off a player's report. It left two kinds of
credential, an Anthropic subscription per operator and one `ANTHROPIC_API_KEY`.

This design makes the provider a property of each credential rather than of the box. secrets.env
can hold three types of credential under one namespace of names: an Anthropic subscription, an
Anthropic API key, and an OpenRouter key. An operator can claim any of them. The default can be
any metered one. The routing eb4cfaa built does not change; what a name resolves to does.

Revision 6 folds in a cross-check of revision 5 against its tasks and the code:

  - Health and flag state are in the database, because `ffwatch status` and ffweb are separate
    processes and could never have read a daemon's memory.
  - A failure has one of five kinds, read from the error fields the CLI already writes. Only an
    outage or a spent budget counts toward a credential's health, never a 429. A subscription's
    session limit is a 429, and counting it would have looped: the hold would lift on the next
    probe and every run would fail the same way.
  - A turn on a credential that is down stays queued because `schedule` skips it. `launch` has
    already marked the turn running, and cannot put it back.
  - `launch` resolves the credential before `build_job`, so section 10's crossing rule has
    something to compare.
  - Callers revision 5 missed: `claude_route_for_comment`, ffweb's `claude_claims`, and
    `review_held`, which now also checks health.


1. What gets built
------------------

  1. Classification failures wait. A gate or selector call that does not produce a usable answer
     leaves the conversation's messages unclaimed and ungated, and they are classified again
     later. `failed_open` is retired for new turns.
  2. A health hold per credential, recorded in the database. While a credential cannot be
     reached, or its provider-side budget is spent, nothing billed to it starts, and nothing that
     could need a classification billed to it starts either.
  3. Three credential types in secrets.env, one namespace of ids across them (section 2).
  4. `claude.default` and `claude.classifier` in config.json name the credential that pays for
     requests no operator made, and for the two classifications.
  5. `ffbox` accepts any of the three types as `--claude-key` and hands the container the
     environment that type needs, and no other credential.
  6. The classifier builds its child's environment from the classifier credential's type.
  7. `claude_keys` reads and reports all three types, and can probe one credential on its own.
     An OpenRouter credential's budget comes from `GET /api/v1/key`.
  8. `openrouter.ai` on `ffbox/egress/allowlist.txt`.
  9. `config.md`, `secrets.env.example`, `CREDENTIALS.md`, `setup.sh`, `05-discord-setup.sh`,
     `ffbox/README.md` and `docs/docker-security-model.md` updated in the same commits as the code
     they describe.

Not a goal: choosing between credentials. eb4cfaa removed that; each request still has exactly one
place it can be billed.

Not a goal: more than one model per OpenRouter credential. Every alias resolves to the one model
the credential declares. Two models means two credentials.

Not a goal: providers other than Anthropic and OpenRouter, or Codex, or the CI lane.


2. Credentials have a type
--------------------------

The type is the variable family a credential is declared in. A type field that could disagree with
its variable name would be a new way to be wrong, so there is none.

    type           variables                                        answers to
    ---------------------------------------------------------------------------------------------
    subscription   CLAUDE_CODE_OAUTH_TOKEN<n>    the token          its NAME, its variable name,
                   CLAUDE_CODE_NAME_TOKEN<n>     the id             and its bare slot number
                   CLAUDE_CODE_RATE_TOKEN<n>     plan, printed only
    api_key        ANTHROPIC_API_KEY[<n>]        the key            its NAME and its variable name
                   ANTHROPIC_NAME_KEY[<n>]       the id
    openrouter     OPENROUTER_API_KEY<n>         the key            its NAME and its variable name
                   OPENROUTER_NAME_KEY<n>        the id
                   OPENROUTER_MODEL_KEY<n>       optional, default z-ai/glm-5.3-flash
                   OPENROUTER_URL_KEY<n>         optional, default https://openrouter.ai/api

`<n>` is 1 to 16. `[<n>]` means the unnumbered spelling is valid too.

The type names are the `kind` values `claude_keys` already writes to its shared store and ffweb
already reads: `subscription` and `api_key` exist today, and `openrouter` is new.

The unnumbered spellings that already exist keep their meaning. `CLAUDE_CODE_OAUTH_TOKEN` is the
legacy single subscription, read only when no numbered slot is set, exactly as today. The
unnumbered `ANTHROPIC_API_KEY` is read whether or not numbered API keys exist, may carry an
unnumbered `ANTHROPIC_NAME_KEY`, and is the default when `claude.default` is unset, which is
eb4cfaa's behaviour unchanged. OpenRouter has no unnumbered spelling, because it has no history to
be compatible with.

**One namespace.** An id is matched case-folded and stripped, as eb4cfaa matches it, against every
credential of every type. An id two credentials answer to is refused, whether they are the same
type or not: "Loth" on a subscription and "Loth" on an OpenRouter key is somebody mid-edit, and
guessing which they meant is the decision eb4cfaa removed. The bare slot number stays a
subscription-only alias, because "2" across three families would be ambiguous by construction.
Every credential also answers to its own variable name, which is unique, so `"model":
"OPENROUTER_API_KEY2"` works on a box whose keys were never named.

**What each type brings.**

    type          metered  window holds   probe, one credential on its own     budget reading
    subscription  no       yes (eb4cfaa)  one-token Haiku, rate-limit headers  --
    api_key       yes      no             one-token Haiku, x-api-key           --
    openrouter    yes      no             GET /api/v1/key, then one request    GET /api/v1/key
                                          to its model

The probes exist today for the first two types, but only inside `ClaudeKeys.read()`, which reads
every credential at once behind a cache. Section 7 needs one credential probed on demand, so
`claude_keys` gains that (section 9). How many tokens the OpenRouter request asks for is a constant
set by section 13d, because Flash reasons by default and one token may not be enough for a reply.


3. Who pays
-----------

eb4cfaa's routing table, restated in credential ids:

    request                                tier      billed to
    ------------------------------------------------------------------------------------------
    forum thread, mention, player DM       player    the credential `claude.default` names
    a fix leg spawned off a player report  player    the credential `claude.default` names
    a mixed player/operator batch          player    the credential `claude.default` names
    the engagement gate and the selector   --        `claude.classifier`, else `claude.default`
    operator message, directive, DM        operator  the credential that operator claims
    #codereview on a pull request          operator  the credential that operator claims
    shell or web prompt                    operator  the credential that operator claims

`claude_route` (ffwatch.py:1944) is unchanged in shape and still returns a variable name or a
refusal. What changes is the lookup underneath it: `subscription_named` becomes `credential_named`
over all three types, and the default is resolved from `claude.default` instead of being the
constant `ANTHROPIC_API_KEY`. Its four callers move together: `claude_route_for`,
`claude_route_for_turn`, `claude_routes` and `claude_route_for_comment`.

**An operator may claim any type.** `"model": "Ben-glm"` beside `OPENROUTER_NAME_KEY2=Ben-glm` puts
everything Ben asks for on that OpenRouter key and its model. Nobody else's request can reach it,
for the same reason nobody else's could reach his subscription.

**The default and the classifier must be metered.** `claude.default` or `claude.classifier` naming
a subscription is refused. That is eb4cfaa's line: a stranger's bug report cannot eat an operator's
window. The refusal has the same shape as a default that names nothing. The daemon logs it at
startup, and `/claude` and `ffwatch status` show it.

What the refusal does to requests:
  - A request routed to a default that does not resolve is refused by `claude_route`, as today.
  - A conversation that could need a classification while the classifier credential does not
    resolve gets `conversation_held`'s `refused` verdict. It waits, and it says so once.
  - Neither of these is a health failure. Nothing is probed, because a missing name will not start
    answering.

**Unset keeps today's behaviour.** `claude.default` unset means the unnumbered `ANTHROPIC_API_KEY`.
`claude.classifier` unset means whatever `claude.default` resolved to.


4. The two classifications
--------------------------

ffwatch asks a model two questions on the host. Both go through `classifier_invocation`
(ffwatch.py:3831), the only place a host model call is built: no tools, `--safe-mode`, no settings,
no session persistence, the prompt on stdin. Ingest calls neither: `select_conversation`
(ffwatch.py:6574) routes every message deterministically, so ingest cannot block on a model or fail
when one is down.

**a. The conversation selector (S4).** "Does this new message continue one of these conversations,
or start a new one?"

  - Where: `resettle` (ffwatch.py:6312) -> `select_for_turn` (:6412) -> `model_selection` (:6498).
  - When: a non-thread, non-local conversation whose pending batch ingest routed as `recent`, the
    S4 band. The message is not a reply to a known message (S1), there is at least one live
    conversation in the channel (S2), and it is not a lone candidate under `certain_secs` (900)
    with nothing in between (S3).
  - Shown: up to `max_candidates` (5) conversations, each with its id, title, how long ago it was
    last active, how many channel messages have passed since, and its last two messages.
  - Answers `{"continues": <an offered id or null>, "reason": <200 chars>}`. An id moves the batch
    there, null splits it into a new conversation, and an id that was not offered is refused.
  - On failure today: the batch stays where ingest put it, in the most recent candidate.

**b. The engagement gate.** "Does the newest message need the bot at all?"

  - Where: `create_turn` (ffwatch.py:7554) -> `should_engage_for` (:4136) -> `should_engage` (:4077).
  - When: only in a watched channel with `engage: all`. Never for a kind in GATE_BYPASS_KINDS
    (:2720), never when `always_a_turn` already decided (the bot was addressed, evidence was
    attached, a thread was opened), and never in a mention-only channel.
  - Shown: where it was said, the conversation's last 12 messages (600 characters each, 6000 in
    total), and the new messages, each labelled player, developer or bot from the stored author id.
  - Answers `{"engage": <bool>, "reason": <200 chars>}`. False only for a closed list: social
    acknowledgement and nothing else, people talking to each other with nothing asked of the
    project, or the same author restating the message before it.
  - On failure today: `failed_open` (ffwatch.py:4119). It engages, the turn row gets
    `failed_closed=1`, and the reply footer reads "I could not work out what this was asking for, so
    treat what follows with care."

`run_classifier` (ffwatch.py:4031) makes up to two attempts with the same credential: prose JSON
first, because `--json-schema` is served as a tool and measured three to four times slower, then
`--json-schema` if the prose answer does not validate. That is a shape retry. On a dead provider
both attempts fail, each waiting up to `classifier_secs` (120).

A failed-open gate CLAIMS the messages for a new turn (ffwatch.py:7617), and they are never offered
again. During an outage that also takes the containers down, every message the gate lets through is
spent on a turn that fails.


5. What a credential puts in a Claude Code environment
------------------------------------------------------

Whether the process is a container turn or a host classification, a credential produces exactly one
of these environments, and never pieces of two:

    subscription  CLAUDE_CODE_OAUTH_TOKEN=<token>
    api_key       ANTHROPIC_API_KEY=<key>
    openrouter    ANTHROPIC_BASE_URL=<OPENROUTER_URL_KEY<n>, or https://openrouter.ai/api>
                  ANTHROPIC_AUTH_TOKEN=<key>
                  ANTHROPIC_API_KEY=                              (set and empty, per OpenRouter)
                  ANTHROPIC_DEFAULT_FABLE_MODEL=<model>
                  ANTHROPIC_DEFAULT_OPUS_MODEL=<model>
                  ANTHROPIC_DEFAULT_SONNET_MODEL=<model>
                  ANTHROPIC_DEFAULT_HAIKU_MODEL=<model>

where `<model>` is `OPENROUTER_MODEL_KEY<n>`, or `z-ai/glm-5.3-flash` when the slot declares none.

**Aliases stay aliases.** job.json keeps `model: opus` and `fallback_model: sonnet`, and the
classifier keeps `--model haiku`. The credential's environment decides what they mean. That is what
lets one pool, one job and one session serve every type: the same `opus` is Opus on an operator's
subscription and Flash on the player default. `run.claude_key` records the credential, and the
credential determines the model. On OpenRouter, `--fallback-model sonnet` is the model falling back
to itself, which is harmless.

`CLAUDE_CODE_SUBAGENT_MODEL` is left unset. Every ff-discord and ff-agents role declares a `model:`
by alias, and a role that did not would inherit the session's model.

Authentication precedence ranks `ANTHROPIC_AUTH_TOKEN` above `ANTHROPIC_API_KEY` and
`CLAUDE_CODE_OAUTH_TOKEN`. Nothing here relies on that, for the reason ffbox's comment gives since
eb4cfaa: a container is handed one credential, and precedence is a fact about a version of `claude`,
not a decision this box made.

A full model id bypasses the alias variables. An agent that names `claude-opus-5` in a subagent call
would get real Opus from OpenRouter, billed per token. The env map is scope; the key's model
allowlist (section 8) is what refuses the request.

**Why Flash is the default model.** It takes text, image and video; GLM-5.3 takes text only, and a
player's bug report routinely carries a screenshot the agent Reads out of `/ffbox/attachments`. From
OpenRouter's endpoints API on 2026-09-10: `z-ai/glm-5.3-flash`, released 2026-08-26, 1M context, 25
providers, tools, tool_choice and structured outputs supported. USD per million tokens:

    most providers (Fireworks, Together, Cloudflare, Z.AI, ...)   0.15 in   0.50 out   0.03 cache
    DeepInfra fp4, the cheapest                                   0.075     0.25       0.015
    Modal fp8, the dearest                                        0.45      1.50       0.09

Three endpoints are fp4 (DeepInfra, Relace, Crusoe). When it was read, Z.AI's own endpoint showed
79.10% uptime over 30 minutes, against 99.5% or better for most others.

An operator who wants a different model declares it on their own credential. A slot that names a
text-only model cannot read screenshots, and that is the operator's call for their own work.

config.json:

    "operators": {
      "lothsahn": { "discord": "801...", "github": 10092359, "shell": "lothsahn", "model": "Loth" },
      "ben":      { "discord": "800...", "github": 10092360, "shell": "ben",      "model": "Ben-glm" }
    },
    "claude": { "refresh_secs": 900, "timeout_secs": 10,
                "review_hold_pct": 0.75, "new_conversation_hold_pct": 0.9,
                "default": "Players",
                "classifier": null,
                "health": { "after_failures": 2, "probe_secs": 60, "notice_after_secs": 600 },
                "classify_retry": { "first_secs": 60, "max_secs": 1800, "flag_after": 5 } }

`default` and `classifier` are ids, never tokens, like every credential reference on this box.
`health` and `classify_retry` are section 7.

**Everything about a credential lives in secrets.env**: the key, its id, and for OpenRouter its
model and base URL. config.json only says who uses which id. ffbox reads one file to build a
container, and the update timer, which already hashes secrets.env, drains and restarts `ffbox.target`
when it changes. That restart destroys idle spares too, so a model change reaches the next turn
within a tick, spares included.

**Declaring a credential is not quite free.** A new credential whose NAME matches an id already in
use makes that id ambiguous, and the operator using it is refused until one of the two is renamed.
The startup line names both variables.

Per CLAUDE.md, config.md changes in the same commit as the shape. `health`, `classify_retry` and the
gate's new failure behaviour ship with phases A and B. `default`, `classifier`, the credential types
and the routing table's wording ship with phases C onward. The seeded template in
`05-discord-setup.sh` does not seed `default`, and its missing-id hint names all three NAME
variables. `setup.sh`'s `api_key_ready` counts any metered credential and points at ffwatch's
startup line for whether the default actually resolves.


7. A classification that fails waits
------------------------------------

**The rule.** If the gate or the selector does not produce a usable answer, nothing is decided.
`create_turn` returns None with the conversation's messages unclaimed, ungated and unmarked. That is
the shape quiet hours use (ffwatch.py:7468), and the shape of eb4cfaa's `refused` and `hold`
verdicts. No turn row, no 👀, no `failed_closed` footer. The messages come back on a later pass and
are classified then.

The gate and a player's container bill the same default, so a box that cannot get an answer out of
the gate most likely cannot get one out of the container either. A fail-open turn during an outage
claims the messages and fails. Waiting keeps them.

**Five kinds of failure.** A classification or a container run that did not produce an answer is
sorted by what the CLI reports, using the fields `result_failure_detail` already reads
(`is_error`, `terminal_reason`, `api_error_status`):

    kind        what it is                                            counts toward health
    ------------------------------------------------------------------------------------------
    refused     the credential does not resolve                       no; conversation_held
                                                                      refuses instead
    outage      no envelope, a timeout, a non-zero exit with nothing   yes
                parseable, or an API error of 401, 403 or 5xx, or one
                with no status
    budget      an API error of 402                                   yes, at once
    limited     an API error of 429: a rate limit, or a               no
                subscription's session limit
    unusable    the call ran and its answer did not validate, even    no
                under --json-schema

A 429 is never a health failure. A subscription over its session limit answers 429, and eb4cfaa's
window holds already cover that. A metered key's 429 is the org's per-minute limit, and it clears
on its own. Counting either would take the credential down, the probe would read the 429 as a live
key (claude_keys.py:583, deliberately), the hold would lift, and the next run would fail the same
way.

The `--json-schema` retry runs only after an `unusable` first attempt, because it fixes shape and
nothing else.

One thing is NOT a failure: a selector answer that validates but names an id that was never offered.
The model answered and the harness refused the content, so the deterministic answer stands, as
today. If it waited instead, a message written to make the selector name a fake id would stall its
conversation for good.

`failed_open` is retired for new turns. The `failed_closed` column, its prompt note
(ffwatch.py:10060) and its reply footer (:17356, :17480) stay so historical rows still render. In
`create_turn`, the two `if not fc` guards before `say_route_refused` and `say_holding` (:7575-7587)
have nothing left to guard and go.

**Two scopes of waiting**, both recorded in the database, so the daemon, `ffwatch status` and ffweb
read the same thing, and a restart does not forget a credential that is down.

  - **The health hold** is per credential, any type, in a `credential_health` table. It is entered
    after `after_failures` (2) consecutive `outage` failures billed to that credential, across
    conversations and counting container runs, or at once on `budget`. Only calls count. A window
    READING that fails does not, because eb4cfaa's rule that an unreadable reading runs the work
    stands.

    While it holds, `conversation_held` (ffwatch.py:7180) returns a new `down` verdict for a
    conversation whose route is that credential, or that could need a classification billed to it.
    "Could need" is decided before `resettle`, so it is conservative. The selector could run for a
    non-thread, non-local conversation holding a message routed `recent`. The gate could run for a
    conversation of a kind outside GATE_BYPASS_KINDS, in an `engage: all` channel, that
    `always_a_turn` does not force.

    `create_turn` returns on `down` ABOVE `resettle` and the gate, the way `hold_until_morning`
    does, so a down credential costs no model calls. `schedule` skips a queued turn whose route
    credential is down with `continue`, so it stays queued; `launch` is not involved, because by
    then the turn is already running. `review_held` treats a down credential the way it treats a
    window over its line: the trigger stays in the cursor.

    Every `probe_secs` (60) the credential is probed on its own (section 2), and success lifts the
    hold. A budget hold with a known end (below) is not probed before that end.

  - **The conversation backoff** is one conversation whose classification failed with `limited`,
    `unusable`, or an `outage` that did not take the classifier's credential down. It retries after
    `first_secs` (60), doubling to `max_secs` (30 minutes), and is stored on the conversation row.
    This is the case "queue regardless" makes new: a message the model reliably cannot classify would
    otherwise be re-asked every few seconds forever.

A success resets the credential's failure count and clears that conversation's backoff.

**Why every type, subscriptions included.** An operator's subscription that starts refusing is the
same situation as a dead OpenRouter key: waiting keeps the request, and failing it throws the
request away. The window holds are unchanged and sit beside this one. A window over its line holds
with a known end; a credential that is down holds until it answers.

**Operators whose work needs a classification.** An operator's own turn bills their credential, but
the gate and selector bill the classifier's. While the classifier's credential is down, an operator
conversation that could need a classification waits too, even if its own credential works. One that
cannot still runs: an addressed message, a DM, a directive, a local prompt, a `#codereview`.

**A message that never classifies.** After `flag_after` (5) failures on one conversation, the
conversation is flagged, not released. `ffwatch status`, `/claude` and the conversations page list
it with the last error, the journal gets one WARNING, and it keeps waiting at `max_secs`.
`ffwatch release <conversation>` records who released it on the conversation row. The next turn
then runs without the gate, keeps the selector's deterministic answer if the selector fails again,
and ignores the backoff. An operator @-mentioning the bot in that thread also gets a turn, because an
addressed message never reaches the gate.

**Budget exhaustion is a hold with a known end.** On `budget` from an OpenRouter credential,
`claude_keys` reads `GET /api/v1/key` for it (`limit`, `limit_remaining`, `limit_reset`,
`usage_daily`). If the key's own limit is spent, the hold lasts until `limit_reset`. A negative
account balance has no reset time and needs a person: an error in the journal, on `/claude`, and in
`ffwatch status`. A `budget` from an Anthropic API key has no reading behind it and holds as an
outage does.

**What the person waiting is told**, and only where `always_a_turn` says the message would have got
a turn, the same filter `hold_until_morning` uses (ffwatch.py:7272). A message above the gate may
turn out to be one the gate would decline, and a notice under it would be a promise nobody made.

  - A hold with a known end goes through `say_holding` and HOLD_NOTE (ffwatch.py:17300) unchanged.
  - A hold with no known end says nothing for the first `notice_after_secs` (10 minutes), since
    most blips end before anyone notices. It then posts once per hold under its own
    `down:<conversation>:<turns>` local_id, so an earlier window or quiet-hours notice does not
    silence it. The sentence promises no time. Its wording goes through max-voice, section 15.

**Containers during an outage.** A turn already running when its credential goes down fails the
normal way. The hold only stops new containers starting into the outage. Its result counts toward
the credential's health by the table above.


8. OpenRouter keys
------------------

Each OpenRouter credential is its own key in OpenRouter's console, and each gets guardrails there:

  - **A budget limit with a daily reset.** eb4cfaa's design section 12 says the box has no spend cap
    on a metered key and building one is separate work. OpenRouter's per-key limit is that cap,
    enforced by the provider. A spent limit is what section 7's budget hold waits on.
  - **A model allowlist** holding the slot's `OPENROUTER_MODEL_KEY<n>` and nothing else. This closes
    the full-model-id hole from section 5.
  - **A provider allowlist.** For Flash, leave out the fp4 endpoints until section 13 shows they
    answer the same way, and leave out endpoints with poor uptime.
  - **A data policy.** Restrict to providers that do not train on inputs. The player default's key
    carries Discord messages from strangers and the repository contents an agent reads.

`max_budget_usd` is passed as it is today. It is Claude Code's own estimate from its own price table,
so on an OpenRouter credential it may not stop anything; the key's limit is the ceiling that does.
`run.cost_usd` (ffwatch.py:11817) and ffweb's cost columns carry the same estimate for those runs,
and the `/claude` row carries OpenRouter's own `usage_daily`.

The player default and a host-only classifier key can be two credentials, which lets the container
key be rotated after an incident without stopping the gate. `claude.classifier` is how that is
expressed. One key for both is also fine, and matches what eb4cfaa does with `ANTHROPIC_API_KEY`.


9. The code
-----------

**claude_keys.py.**

  - `claude_credentials()` scans the three families (section 2), unnumbered spellings included, and
    returns one tuple per credential: name, token, kind, label, rate, model and url, with fields
    that do not apply to a kind left empty. `claude_subscriptions()` becomes the subscription filter
    over it, so existing callers keep working.
  - `credential_kind(name)` answers a kind from a variable name's prefix. `slot_ids(name, label)`
    keeps its two arguments and uses it: every credential answers to its declared NAME and its
    variable name, and a subscription also to its bare slot number. `credential_named(key_id,
    creds)` replaces `subscription_named`, with the same three answers: found, "no slot",
    "ambiguous".
  - `default_api_key()` (:173) goes. `credential_for(name, creds)` returns one credential's tuple for
    callers that need its token, kind and model together.
  - `_claude_secrets_file` (:296) widens its `wanted` set to the new families and nothing else. This
    process still never learns the Unity password or the GitHub token.
  - `ClaudeKeys` takes a `credentials` callable in place of `tokens` and `api`. `read()` (:841) builds
    its list from it, with `kind` set on every record. `_load` (:634) branches three ways: a
    subscription reads usage as today, an API key probes as today, and an OpenRouter key reads
    `GET /api/v1/key`, which costs nothing, recording `limit`, `limit_remaining`, `limit_reset` and
    `usage_daily`, and makes one `OPENROUTER_PROBE_MAX_TOKENS` request to its model.
  - `ClaudeKeys.probe_one(name)` probes one credential with no cache and no dependence on whether a
    window hold is configured. `claude_records` returns `[]` when neither hold is set, and the health
    hold must still be able to lift.
  - `KIND_OPENROUTER` beside `KIND_SUBSCRIPTION` and `KIND_API_KEY`, and `metered(kind)`.

**ffwatch.py.**

  - `classifier_credential(cfg, creds)`, at module level beside `claude_route`: resolves
    `claude.classifier`, else `claude.default`, else the unnumbered `ANTHROPIC_API_KEY`, and refuses a
    subscription. `classifier_invocation` calls it itself, so the module-level classifier functions
    keep taking only `cfg`. The Watcher calls the same function to know which credential's health a
    classification reports to.
  - `claude_keys_now` (:11060) returns `(credentials, default, classifier)`. `claude_route` (:1944)
    resolves an operator's id with `credential_named` and a non-operator through the resolved
    default. Its refusal sentences name the id and variable involved.
  - `classifier_invocation` (:3831) builds the child's environment from section 5 for the
    credential's type. `ANTHROPIC_API_KEY` leaves the passthrough list at :3889, so only the
    credential puts a credential in the child.
  - `classifier_attempt` and `run_classifier` (:4002, :4031) return a failure that carries its kind
    (section 7), read from the envelope's `is_error`, `terminal_reason` and `api_error_status` as well
    as the exit code. `should_engage` and `model_selection` return HOLD instead of failing open or
    keeping the deterministic answer.
  - `conversation_held` (:7180) gains `down`, the classifier-unresolved `refused`, and the
    conversation backoff. `create_turn` returns on `down` above `resettle`, and on a HOLD from either
    classification, with nothing written.
  - `schedule` (:9188) skips a queued turn whose route credential is down.
  - `review_held` (:15600) holds a trigger whose operator's credential is down.
  - `finish_run` sorts a failed run's `result.json` into section 7's kinds and reports it.
  - `launch` (:11393) resolves the credential before `build_job` (today it resolves it at :11521,
    after the job is written) and passes it in. That lets section 10's rule read it.
  - `pool_stage_key` (:8339) stages player-pool spares on the resolved default instead of calling
    `default_api_key()` itself. `pool_claim_for` (:9108) already matches spares on the credential name.
  - `claude_hold` (:11170) needs no change. `usable()` is false for a record with no windows, so a
    metered record never holds on a window, OpenRouter included.
  - The startup check (:11134) and `claude_status` (:11270) name the resolved default and classifier,
    each operator's credential and its kind, each credential's health, and flagged conversations.
  - `ffwatch release <conversation>`.

**ffbox.** The `--claude-key` block scans the three families the way `claude_credentials` does and
accepts only a name it found. The type comes from the prefix. For OpenRouter it reads
`OPENROUTER_MODEL_KEY<n>` and `OPENROUTER_URL_KEY<n>` for the same slot, out of the secrets.env it has
already sourced; the loop already knows `<n>`. It exports that type's environment from section 5 and
sets `CLAUDE_ENV_ARGS` to forward it. Every credential goes by bare name, so no value reaches argv,
and the empty `ANTHROPIC_API_KEY` is passed as a literal `-e ANTHROPIC_API_KEY=`. A name whose
variable is empty exits 78, as `ANTHROPIC_API_KEY` does since eb4cfaa. With no `--claude-key` at all
it still takes the first subscription slot, as eb4cfaa left it.

**ffweb.py.**
  - `page_claude` (ffweb.py:2719) renders one row per credential with its kind. A subscription row is
    unchanged, an API key row reads "metered, no window", and an OpenRouter row shows its model and
    its budget ("$X of $Y left today, resets in Z", or "no limit set").
  - Every row carries its health from `credential_health` and names the operators, default or
    classifier that use it.
  - The header names what the default and classifier resolve to.
  - A section lists flagged conversations with the command that releases them.
  - `claude_claims` (:3815) matches across every kind rather than excluding `api_key`, because an
    operator may now claim any.

**Egress.** `openrouter.ai` joins `ffbox/egress/allowlist.txt`, because any credential in a fenced
container may now be an OpenRouter one. `api.anthropic.com` and `platform.claude.com` stay.

**The security model.** docs/docker-security-model.md:236 says the allowlist narrows exfiltration to
two vendors because the model endpoint is a POST sink; it becomes three. Its credential table (:98)
still lists only `CLAUDE_CODE_OAUTH_TOKEN` and gains both metered types. An OpenRouter key's blast
radius is money, like an API key's, bounded by a provider-side daily limit and a one-model allowlist.
CREDENTIALS.md's "the two Claude credentials" becomes three.


10. Conversations that move between credentials
-----------------------------------------------

**This is intended.** A turn is billed to whoever asked it, and a credential carries its provider
and model with it. A conversation that a player and an operator both speak in therefore moves between
credentials from turn to turn. A player's report runs on the default. The developer who @-mentions
the bot in the same thread runs on what they chose. The next player message goes back to the default.
Nothing in the harness should resist that, and nothing should warn about it.

**What has to be true for it to work: the session survives the switch.** Turns in a conversation
share one Claude Code session. That session's transcript is replayed to whichever endpoint the next
turn's credential points at, thinking blocks included, and those blocks carry a signature from the
model that wrote them. Three crossings matter:

  - Anthropic to OpenRouter (a subscription or API key turn, then an OpenRouter turn).
  - OpenRouter to Anthropic.
  - OpenRouter model A to OpenRouter model B, when two credentials declare different models.

Anthropic subscription to Anthropic API key already happens since eb4cfaa, on the same models, and
is not in question.

Section 13e measures all three crossings. For any crossing that does not resume, the harness uses
the path a lost transcript already takes (`resume_summary` in `build_job`): that turn starts a new
session carrying the host-rendered summary, and the conversation carries on. The switch key is the
pair (base URL, model) of the previous run's credential against this turn's, which `launch` passes
to `build_job`. Two credentials on the same pair never trigger it. If every crossing resumes, no rule
is needed and this section keeps only its first paragraph.

`run.claude_key` already records each turn's credential, so a conversation's history on the web page
shows the moves without new columns.


11. What is not moved, and why
------------------------------

Nothing is moved by this design on its own. Every credential stays where its config puts it, and a
box with no OpenRouter credentials and no `claude.default` behaves as eb4cfaa left it, except for
section 7.

The window reads in `claude_keys.py` still ask Anthropic how full a subscription is, and only
Anthropic can answer.

The CI lane never runs a model.


12. Risks, most serious first
-----------------------------

  1. **Venue policy is enforced by the prompt.** A public-venue reply must not carry file paths or
     internals, and Max's voice is binding. The preamble carries both rules. A model that follows a
     long system prompt less closely will post something it should not in a public channel, and no
     fence stops that, because it is the reply itself. Player turns are the ones in public venues.
  2. **Flash doing player work.** With the default on Flash, the triage verdict, the answers, and the
     fix legs a triage verdict spawns all run on the smallest GLM model, and fix legs push branches.
  3. **Injection resistance on the lane that reads hostile text.** The containment does not change:
     network fence, no git credential, no `gh`. What can change is how often an injected message gets
     the agent to do something inside that fence.
  4. **Waiting is silent for the first ten minutes, and possibly for hours.** A message the model can
     never classify waits for a person, and on a quiet week nobody may look.
  5. **The gate on Flash.** A gate that declines more is the one failure nobody sees. The 1024 thinking
     budget was tuned against Haiku's answers.
  6. **Tool calling through Claude Code.** OpenRouter's own guide says the integration is only
     guaranteed against Anthropic's first-party models. Edits, the triage verdict under
     `--json-schema`, and subagent calls depend on it.
  7. **Prompt caching.** An agent turn re-sends its whole context on every tool call. If
     `cache_control` does not survive the trip, input cost multiplies.
  8. **More ways to misconfigure.** Three families, one namespace, and a model line per slot. The
     startup line, `/claude` and `ffwatch status` have to make a wrong id obvious before somebody's
     request is the thing that finds it.
  9. **Provider variance.** 25 providers for Flash, three of them fp4.


13. Measure before building phases C onward
-------------------------------------------

By hand on the build server. No code ships and no config changes. Each result goes into the next
revision of this file.

  a. **The classifications.** A scratch script imports ffwatch, re-renders the gate and selector
     prompts for the last few hundred messages that reached them (message.gate, routed_by = 'model',
     routed_reason), and runs each through the real flag set with section 5's OpenRouter environment
     on Flash. Record: agreement with the stored answer, p50 and p90 latency, how often the prose
     attempt fails to parse, how often both attempts fail (each of those would now wait), and
     reasoning tokens. The bar for the gate: it never declines a message the current gate engaged.
     Read every selector disagreement by hand.
  b. **Player turns.** Take finished player runs' job.json files, a bug report with a screenshot among
     them, and run each through a scratch copy of ffbox with an OpenRouter credential wired by hand,
     the egress proxy in log mode, and `--debug-file` on. Record: whether the screenshot was read,
     whether the triage verdict validated and agrees with the original, `cache_read_input_tokens`,
     `total_cost_usd` next to OpenRouter's activity page for the same requests, the model every request
     actually named, every SNI, and whether the reply would have been fit to post.
  c. **Failures, on purpose.** A key with a $0.01 limit (402), a model the key's allowlist refuses, a
     provider allowlist no endpoint satisfies (503), and a revoked key (401). For each: the
     classifier's exit code and envelope, and the container's `result.json`, `claude.log` and
     `stream.jsonl`, so section 7's kinds can be read off real shapes.
  d. **The OpenRouter probe.** `GET /api/v1/key` against a real key, its fields as documented and at no
     cost, and the smallest `max_tokens` Flash will answer a request with, which sets
     `OPENROUTER_PROBE_MAX_TOKENS`.
  e. **Session crossings**, section 10's three, each in both directions where there are two, on a
     throwaway session with at least one thinking block and one tool call in it before the switch.
  f. **A bug-report thread and an ask thread from the last week**, replayed on Flash, each reply read
     against max-voice and the venue rules.
  g. **An operator's own turn on an OpenRouter credential in ffdev**: one small real change through
     compile and the fast suite, to see whether a dev turn is workable before anybody claims one.


14. Rollout
-----------

**Phase 1, wait instead of failing open.** Section 7 on today's credentials:
  - HOLD from the classifications
  - the five failure kinds
  - the health hold for both existing types
  - the conversation backoff and flagging
  - `ffwatch release`
  - `schedule`'s skip and `review_held`'s check

No OpenRouter. It changes behaviour on every box, so it ships and runs on its own first.

**Phase 2, credential types.** The scan, `credential_named`, `classifier_credential`, the OpenRouter
record, probe and page row, the ffbox environment, the egress entry, and `claude.default` and
`claude.classifier`. Shipped with neither key set and no OpenRouter credential declared, it changes
nothing. Declaring a credential changes only the page, unless its name collides with an id already in
use (section 6).

**Phase 3, the classifications.** An OpenRouter credential for the classifier, and `claude.classifier`
naming it. Players' containers stay where they are. Unsetting `claude.classifier` undoes it. Run a
week and compare the gate's decline rate with the week before.

**Phase 4, player turns.** `claude.default` naming an OpenRouter credential, with `approve_before_send`
on for the trial. It is box-wide (ffwatch.py:1297), so operators' replies wait for approval too.
Accept that for a week, or make it per route first, which is a small change at `_send_row`.

**Operators opt in whenever they like after phase 2**, by pointing their `model` id at an OpenRouter
credential. Section 13g first.

**Rollback** is config. Unset `claude.default` and `claude.classifier`, and point operator ids back.
Spares are destroyed by the updater's restart, and conversations cross back over section 10's path.
Phase 1 stays.
