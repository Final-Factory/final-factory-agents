ffbox rootless Docker design
============================

Revision 1, 2026-08-25.

Scope: move ffbox's containers off the root Docker daemon onto a rootless daemon owned by
FinalFactoryTester, and close the second passwordless-root route that the ZFS sudoers rule
leaves open. Both, or neither: each one alone leaves the account root without a password.

Why this exists: on 2026-08-25, while narrowing the updater's sudoers grant, the account the
updater runs as turned out to already hold passwordless root by a route that has nothing to do
with sudo. FinalFactoryTester is in the docker group, and the docker group talks to a root
daemon. The narrow grant was written to keep an unattended process from becoming root; it does
not do that while a second, wider route is open next to it. The owner's requirement, stated the
same day: FinalFactoryTester may sudo with a password, and must have no root access without one.


0. What this must do
--------------------

  1. NO UNATTENDED ROOT. A process running as FinalFactoryTester with no human at a keyboard
     must not be able to become root. Interactive `sudo` with a password stays, and is the
     point: a person can still administer the box, a timer cannot.

  2. KEEP THE EGRESS FENCE. The run container reaches the network only through the SNI
     allowlist proxy, and reaches this host not at all. Whatever replaces the current
     mechanism has to hold that line, and be checkable.

  3. LEAVE THE WORKSPACE OWNED BY THE HOST USER. Files a container writes into the ZFS clone
     must come back owned by FinalFactoryTester, or the harvest step on the host cannot read
     or clean them.

  4. DO NOT BREAK THE OTHER USERS OF THIS MACHINE. The root daemon serves accounts that are
     not ffbox's. This change removes one member from a group; it does not turn a daemon off.

Explicitly NOT a requirement: removing FinalFactoryTester from the sudo group. A human at a
terminal is meant to be able to become root on this box. The password is what separates that
human from the timer.


1. Verified facts
-----------------

Measured on Loth2400 on 2026-08-25, not assumed. A rootless daemon was run on a scratch data
root under /home/FinalFactoryTester, exercised, and removed; the root daemon was not touched.

  a. THE ACCOUNT HAS PASSWORDLESS ROOT TODAY, VIA DOCKER. As FinalFactoryTester, with no
     password:

         docker run --rm -v /etc:/hostetc:ro alpine sh -c 'id -u; wc -l < /hostetc/shadow'
         0
         84

     The socket is srw-rw---- root:docker and dockerd runs as root. sudo is not in the path,
     so nothing prompts.

  b. SUDO ITSELF IS PASSWORD-GATED. `sudo -n -l` reports `(ALL : ALL) ALL` from the sudo group
     with no NOPASSWD, and a NOPASSWD list containing four zfs commands and nothing else.

  c. THE NOPASSWD ZFS RULE IS WIDER THAN IT LOOKS. It contains

         /usr/sbin/zfs clone -o * rpool/ff/golden@ffbox-* rpool/ff/run-*

     and sudo matches wildcards per argument, so `-o mountpoint=/etc` is inside the grant.
     /opt/FinalFactory is owned by 1015, and `zfs snapshot rpool/ff/golden@ffbox-*` is granted
     too. Write files into golden, snapshot, clone with mountpoint=/etc, and the real /etc is
     shadowed by a dataset whose sudoers and shadow the caller wrote. This is section 4.

  d. THE SANDBOXED AGENT IS NOT THE PROBLEM. ffbox/ffbox:636 runs the agent container with no
     /var/run/docker.sock mount and no --privileged. There is no docker route out of it. The
     accounts that hold the group are host-side: the daemons, and any Claude Code session
     started as FinalFactoryTester.

  e. EVERY ROOTLESS PREREQUISITE IS ALREADY INSTALLED. Kernel 6.8.0-138, /usr/bin/newuidmap
     and newgidmap, /etc/subuid and /etc/subgid carrying FinalFactoryTester:1083040:65536,
     /usr/bin/dockerd-rootless-setuptool.sh, rootlesskit, slirp4netns, systemd 255 with
     Delegate=yes on user@1015.service. Nothing needs installing except the change itself.

  f. OVERLAY2 WORKS ON ZFS IN A USER NAMESPACE. This was the go/no-go. A rootless daemon with
     its data root on rpool/USERDATA/FinalFactoryTester reported

         Backing Filesystem: zfs
         Storage Driver:     overlay2
         Native Overlay Diff: true
         Supports d_type:     true

     and completed a pull, a `docker build` with a RUN layer, and a run. No fuse-overlayfs
     fallback, and no performance caveat from one.

  g. THE ESCALATION IS CLOSED, INCLUDING THE OPT-OUT. Against the rootless daemon, all three
     forms return Permission denied: a plain `-v /etc:/hostetc:ro` read, `--privileged -v /:/host`,
     and `--userns=host`. The last is why a userns-remap on the root daemon would not have
     done: a docker-group member can ask for the host namespace back, and a rootless daemon
     has no host namespace to give.

  h. THE ENTRYPOINT ALREADY DOES THE RIGHT THING UNDER ROOTLESS. entrypoint.sh reads the
     workspace's owner and skips its uid dance when that owner is 0:

         uid=$(stat -c '%u' "$WORKSPACE")
         if [ "$uid" -eq 0 ]; then exec bash "$TASK"; fi

     The same 1015-owned directory stats differently depending on the daemon:

         host-side owner                        uid=1015 gid=1015
         inside a rootless container            uid=0    gid=0
         inside a rootful container (today)     uid=1015 gid=1015

     Rootless maps host 1015 to container 0, so the branch fires and the task runs as
     container root, which is host 1015. Files written into a bind mount came back owned by
     1015, confirmed directly. Requirement 3 is satisfied by code that already exists,
     because it keys off observed ownership instead of a hardcoded uid.

  i. NETWORK THROUGHPUT IS UNCHANGED. A 20 MB download inside a container took 1.05s rootless
     and 1.09s rootful. slirp4netns is not a bottleneck for this workload.

  j. THE EGRESS TOPOLOGY WORKS UNCHANGED. Built under the rootless daemon: an --internal
     network with a fixed subnet and a pinned bridge name, a proxy container holding a static
     --ip on it and a second attachment to a routed uplink, and a client on the internal
     network only.

         proxy -> 1.1.1.1:443                   reached
         client -> proxy:8053                   reached
         client -> 1.1.1.1:443                  sealed
         client -> host 192.168.51.10:22        blocked

     The last line is the one that retires work: the bridge lives inside the rootlesskit
     network namespace, so the host is not on the other side of it. See section 5.

  k. WITHOUT CGROUP DELEGATION, CONTAINERS DO NOT START AT ALL. With no user session the
     daemon starts but every run fails:

         open /sys/fs/cgroup/user.slice/user-1015.slice/cgroup.controllers: no such file or directory

     There is no /run/user/1015 and user@1015.service is inactive, because lingering is not
     enabled for this account. This is a hard prerequisite, not a loss of resource limits.

  l. A CONTAINER ON THE DEFAULT BRIDGE STILL REACHES THIS HOST. It connected to
     192.168.51.10:22. --disable-host-loopback blocks 127.0.0.1, not the host's LAN address.
     True on the root daemon today as well, so not a regression, but it means ffbox's
     deliberately unfiltered `--network bridge` mode stays genuinely unfiltered.

  m. OTHER PEOPLE USE THE ROOT DAEMON. getent group docker lists spaceengineers,
     FinalFactoryTester and rrobin, and there is a docker user at uid 1017 with lingering
     already enabled. Requirement 4 comes from this line.

     A full inventory of that daemon on 2026-08-25 found one container (ffbox-egress),
     six images and two networks, all ffbox's, and one thing that is not: the volume
     devops_postgres_data, 489 MB, created 2026-08-20 by a compose project named devops, with

     Rootless is not new to this machine. /home/lothsahn/.local/share/docker is a populated
     store dating from January 2025 and lothsahn holds a subuid range, though without
     lingering. Only the root daemon was running at the time of the inventory.

  n. THE IMAGES ARE HEAVY. ffbox:latest is 11.3 GB on an 11 GB unityci/editor base; total
     image weight 11.42 GB with 3.4 GB of build cache. /var/lib/docker is its own dataset,
     rpool/docker, with 2.1 TB free.

  o. ffbox-egress.sh FALLS BACK TO `sudo docker`. Line 70, taken when the caller is not in the
     docker group, which is exactly what this change makes true.

  p. 01-dockerSetup.sh ADDS THE OWNER TO THE DOCKER GROUP, at line 533, and warns at 534 that
     the membership is root-equivalent.

  p2. ffwatch.service GRANTS ITSELF THE DOCKER GROUP. Line 33 carried

         SupplementaryGroups=docker

     A unit that names a group gets it whether or not the account is still a member, so
     `gpasswd -d` would have closed the docker route for every process on this box EXCEPT the
     one that launches containers. Found while implementing phase 3 on 2026-08-25, not during
     the survey. It is the reason phase 6 alone was never sufficient, and the reason there is

  q. NOTHING IN ffbox/ MENTIONS DOCKER_HOST. Every caller finds the daemon by its default

  r. NOTHING IN ffbox/ SETS A RESOURCE LIMIT OR PUBLISHES A PORT. No --memory, --cpus, -p or

  s. THE WORKSPACE TREES ARE ALREADY OWNED BY THE USER. /opt/FinalFactory and /opt/ffruns are
     both 1015:1015, as is the golden dataset's content.


2. Why rootless, and not one of the cheaper options
---------------------------------------------------

Three alternatives were considered and rejected before the probe was run.

USERNS-REMAP ON THE ROOT DAEMON is one line in daemon.json and looks like it does the job:
container root maps to an unprivileged host uid, so a bind mount of / stops being readable. A
docker-group member defeats it by passing --userns=host or --privileged, both of which restore
the host namespace. It hardens against a container breaking out. It is not a boundary against
the account holding the socket, which is the boundary this needs.

A SOCKET PROXY filters the Docker API by endpoint. The endpoint ffbox needs is
POST /containers/create, and that is the request carrying the bind mount. There is nothing left
to filter once it is allowed.

AN AUTHORIZATION PLUGIN, such as the OPA one, does express the policy: deny --privileged, deny
bind mounts outside an allowed prefix. It also puts a third-party component in the path of every
container start, where a bug or an unmaintained release stops all work on the box. The
protection is real and so is the new failure mode.

Rootless removes the privilege rather than policing its use. There is nothing to bypass because
there is no root daemon on the other end of the socket.


3. What the change is
---------------------

The daemon moves and everything else follows the socket.

  - A rootless dockerd runs inside user@1015.service, installed by
    dockerd-rootless-setuptool.sh, kept alive across logout by lingering, with its data root at
    /opt/ffbox_docker: a ZFS dataset, rpool/ff/docker, owned by 1015. The path is set in
    ~/.config/docker/daemon.json, since the rootless default is under the home directory.
  - Every ffbox caller learns DOCKER_HOST=unix:///run/user/1015/docker.sock: the four systemd
    units, and a profile.d line so an interactive session does not quietly talk to the root
    daemon instead.
  - ffbox-egress.service loses User= root and its iptables work, and becomes another unit
    running as the owner (section 5).
  - ffbox-egress.sh loses the `sudo docker` fallback (fact o), which after this change would
    silently address the wrong daemon.
  - 01-dockerSetup.sh stops adding anyone to the docker group and instead performs the
    rootless install.
  - FinalFactoryTester leaves the docker group. Last, after the rest is proven.

What does not change: ffbox itself, the entrypoint's uid handling (fact h), the ZFS clone
mechanism, the target and unit topology, and the root daemon that other accounts use.

ONE AWKWARDNESS IN WHERE THE INSTALL RUNS. 01-dockerSetup.sh is a system stage: setup.sh runs
it under sudo because installing the engine needs root. The rootless install is the opposite,
a per-user operation that must run AS FinalFactoryTester and needs that user's systemd session,
because dockerd-rootless-setuptool.sh finishes with `systemctl --user enable docker`. runuser
alone does not provide the session. With lingering already on, the working form is

    runuser -u FinalFactoryTester -- env XDG_RUNTIME_DIR=/run/user/1015 \
        DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1015/bus \
        dockerd-rootless-setuptool.sh install --force

which is why lingering has to be enabled before the install rather than after it. setup.sh
already has an as_owner helper for HOME-scoped work; this needs that plus the two variables.

--force IS REQUIRED HERE, and it is not a shortcut. The setuptool aborts when
/var/run/docker.sock is WRITABLE, on the assumption that a working rootful docker means you did
not mean to do this (its line 92). Both halves of that assumption are wrong on this machine: the
root daemon stays because other accounts use it, and the socket is writable only because the
owner is still in the docker group, which is what phase 6 removes at the END. The check would
pass by itself after that, and until then it is asking about a decision already made. --force
skips that one test and changes nothing else.


4. The ZFS sudoers hole
-----------------------

Rootless alone does not satisfy requirement 1. Fact c is a second passwordless route to root,
and it is live right now.

The rule allows any property on the clone. `-o mountpoint=` takes a path, ZFS will mount a
dataset over a populated directory, and the dataset's content is a clone of a tree the caller
owns. The sequence is: write /opt/FinalFactory/sudoers as yourself, `sudo zfs snapshot
rpool/ff/golden@ffbox-evil`, `sudo zfs clone -o mountpoint=/etc rpool/ff/golden@ffbox-evil
rpool/ff/run-evil`. Neither sudo call prompts.

PINNING IT WITH A WILDCARD DOES NOT WORK, which revision 1 of this document got wrong. Checked
against sudoers(5) on 2026-08-25 while implementing it: "Command line arguments are matched as a
single, concatenated string", and in that string a wildcard matches across word boundaries and
matches '/' as well. Two consequences. The `-o *` does not mean "one property": it swallows the
rest of the command line, so extra arguments ride along on all four rules. And a pinned-looking
`-o mountpoint=${RUNS_MNT}/run-*` would still admit
`-o mountpoint=/opt/ffruns/run-x/../../../etc`, because the '*' eats the slashes too.

The fix is a regular expression, anchored at both ends. sudoers has supported POSIX extended
regexes for arguments since sudo 1.9.10, and this machine runs 1.9.15p5. ffbox:523 calls

    sudo zfs clone -o mountpoint="$MNT" "$SNAP" "$CLONE"

with MNT=${RUNS_MNT}/run-${RUN_ID}, so the whole argument string is known and can be spelled
out. The only free part is a run id, held to [A-Za-z0-9._-]+ — the same class ffbox already
enforces on --run-id at its line 185. No '/' in that class is what stops a mountpoint climbing
out of ${RUNS_MNT}.

    Cmnd_Alias FFBOX_ZFS = ${ZFS_BIN} ^snapshot ${GOLDEN_DS}@ffbox-${RE}$, \
                           ${ZFS_BIN} ^clone -o mountpoint=${RUNS_MNT}/run-${RE} \
                                             ${GOLDEN_DS}@ffbox-${RE} ${FF_DS}/run-${RE}$, \
                           ${ZFS_BIN} ^destroy ${FF_DS}/run-${RE}$, \
                           ${ZFS_BIN} ^destroy ${GOLDEN_DS}@ffbox-${RE}$

Anchoring the other three closes the ride-along at the same time. 02-zfsSetup.sh refuses to
write the file at all on a sudo older than 1.9.10, where these would be read as literal text,
match nothing and fail every clone.

This is independent of everything else in this document and should land first. It is a one-line
change to a hole that exists today, and it does not wait on the daemon move.


5. The egress fence under rootless
----------------------------------

The fence has two mechanisms today. One survives untouched and one becomes unnecessary.

The SNI allowlist proxy is the fence proper: an --internal Docker network that no container can
route off, a proxy holding a fixed address on it with a second leg on a routed network, and run
containers pointed at that address with --dns. All of it worked unmodified under the rootless
daemon (fact j).

The iptables INPUT rule is the other mechanism, and it exists for a specific reason recorded in
the unit: on the root daemon, a container on an internal network can still reach the host at the
bridge gateway, so the rule drops packets arriving on the ffbox0 interface. Under rootless the
bridge is created inside the rootlesskit network namespace. The host is not at the other end of
it, and the internal client could not reach 192.168.51.10:22 with no rule anywhere. The rule has
nothing left to drop.

Removing it takes the last root requirement out of ffbox. ffbox-egress.service is currently the
only unit with no User=, precisely because iptables is not something the ffbox user has. With
the rule gone the unit runs as the owner like the other four, and the ExecStart pointing at a
script inside a user-writable checkout stops being a root shell with extra steps.

Two things to preserve while doing it. The pinned bridge name exists so that a rule can name an
interface Docker did not choose; with the rule gone the pin is no longer load-bearing, but it is
still worth keeping for diagnosis. And `ffbox-egress.sh status` reports on the INPUT rule; that
reporting should be removed rather than left to print a permanent MISSING.

What is not fixed: fact l. A container started with --network bridge reaches this host's LAN
address, on either daemon. That mode is documented as deliberately unfiltered and the comment
should say that the host is included in what it does not filter.


6. Boot ordering
----------------

The one genuinely new failure mode. ffbox's units are system units that run as the owner. The
rootless daemon lives in user@1015.service, on the other side of the boundary that
After= and Wants= cannot cross. At boot the units will start before the socket exists.

Lingering makes /run/user/1015 exist from boot, which is necessary and not sufficient: the
directory appears before dockerd inside it is listening. The fix is an ExecStartPre on each unit
that needs docker, waiting for the socket with a bounded timeout, so a daemon that never comes
up fails the unit visibly instead of producing a container error at the first turn.

ffbox-egress.service is the one that matters most, because the proxy container carries
--restart unless-stopped and the whole point of that unit is to be the thing that answers
"is the fence up".


7. Failure modes
----------------

  CALLER TALKS TO THE WRONG DAEMON. The quiet one. A missing DOCKER_HOST does not error; it
  finds the root daemon, which is running, and does the work in the wrong place with different
  images and different networks. The `sudo docker` fallback in fact o is the same failure with
  a different cause. Both are why removing the group membership is the last step and not the
  first: until it is gone, a wrong-daemon call succeeds and looks fine.

  CONTAINERS REFUSE TO START. Fact k, if linger is not enabled or is turned off later. Loud
  and unmistakable, and recorded here so the message is recognisable.

  IMAGES ARE MISSING AFTER THE MOVE. The rootless daemon starts with an empty store. Nothing
  breaks silently; the first run reports the image is not built. Rebuilding is 11.4 GB of pull
  and build (fact n).

  THE OLD DATASET IS NOT ORPHANED. rpool/docker holds the root daemon's store, and the other
  accounts still use that daemon (fact m), so it stays where it is and keeps its 2.1 TB. The
  rootless store is a separate dataset at /opt/ffbox_docker. Nothing is migrated between them;
  the images are rebuilt (fact n).

  A PRUNE ON THE ROOT DAEMON DELETES devops_postgres_data. That volume (fact m) has nothing
  attached to it, so `docker system df` reports it 100% reclaimable and
  `docker system prune --volumes` takes it. AUTHORISED 2026-08-25 by the owner, who holds
  backups of it, so this is a decision already made rather than a hazard to route around.

  Two things about the timing, neither of which changes the authorisation. Nothing forces the
  prune: the rebuild writes to /opt/ffbox_docker, and rpool/docker has 2.1 TB free regardless.
  And the natural moment is AFTER phase 6, not during phase 5, because until the rootless
  daemon has run a real turn the root daemon's ffbox images are the fallback. Pruning them at
  phase 5 deletes the way back.

  Confirm the devops backup restores before running it. Everything else in that daemon can be
  rebuilt from a Dockerfile; that volume cannot.

  NO RESOURCE LIMITS. Only if the cgroupfs workaround used during the probe is shipped by
  accident. With linger on, delegation is real. Nothing in ffbox sets a limit today (fact r),
  so the exposure is a runaway container rather than a regression.

9. Open questions
-----------------

  a. WHERE THE ROOTLESS STORE LIVES. DECIDED 2026-08-25 by the owner: its own dataset,
     rpool/ff/docker, mounted at /opt/ffbox_docker and owned by 1015. Not under the home
     directory, and not by repointing rpool/docker, which stays with the root daemon the other
     accounts use. This follows the shape already in place for rpool/ff/golden at
     /opt/FinalFactory, and rpool/ff carries mountpoint=none so the child needs the mountpoint
     named explicitly.

     The overlay2 driver needs xattr=sa on the dataset. rpool sets it pool-wide, along with
     acltype=posix, dnodesize=auto and compression=lz4, so a new child of rpool/ff inherits all
     four and no property has to be set by hand. Worth checking anyway after creation, because
     a store that silently lacks xattr=sa fails later and further away.

     A quota is available and not set, matching rpool/docker. If the build cache turns out to
     grow without bound it belongs here, at a size well clear of the 11.4 GB the images need.

  b. WHETHER THE SOCKET WAIT BELONGS IN EACH UNIT OR IN ONE. DECIDED 2026-08-25 while
     implementing: the shared oneshot. ffbox-docker.service, Type=oneshot with
     RemainAfterExit=yes, so the wait is paid once per boot rather than on every dependent
     start, and a failure gets its own name in `systemctl status` instead of being buried
     inside whichever service happened to start first.

     It waits on the DAEMON, not on the socket file: lingering creates /run/user/<uid> at boot
     and the socket appears a moment before anything behind it will answer. ffbox/
     wait-for-docker.sh asks `docker version` in a bounded loop and prints the three things
     that are usually wrong when it gives up.

  c. WHETHER 01-dockerSetup.sh SHOULD REMOVE THE GROUP MEMBERSHIP ITSELF. DECIDED 2026-08-25
     by the owner: no. This is the only ffbox machine, so the removal is one command run once
     by a human, and a script that performs it could cut the daemons off from the socket they
     are using, mid-flight.

     The script must still stop ADDING the membership. That half is not optional: leaving the
     usermod in place means the next run of setup.sh silently reopens the hole this document
     closes, and setup.sh is now re-run unattended by the updater. Report the membership in
     --status, add nothing, remove nothing.

  d. WHETHER THE OTHER MEMBERS SHOULD BE TOLD. spaceengineers and rrobin hold the same
     root-equivalent membership on this machine (fact m). Out of scope here, worth raising
     with the owner separately.
