ffbox self-update design
========================

Revision 1, 2026-08-22.

Scope: a daemon that keeps this checkout current — `git fetch` plus a fast-forward, on a
schedule and on demand — and that restarts ffbox into the new code without killing work that
is already in flight.

Why this exists: on 2026-08-22 the ffwatch daemon on the build server was found running code
from a checkout twelve hours older than HEAD. Nothing was wrong with the code on disk; nothing
had restarted the process. A guard committed at 16:46 was not live at 20:41, and the pipeline
spent five containers and roughly a dollar re-answering questions that already had answers.
Editing a file is not deploying it. That gap is what this closes.


0. What this must do
--------------------

Four requirements, in the order they constrain the design.

  1. UPDATE ON A SCHEDULE AND ON DEMAND. One mechanism for both. A human triggering an update
     must not take a different code path from the timer, or the rare path is the broken one.

  2. SURVIVE A BROKEN FFBOX. If a bad commit stops ffwatch from starting, the updater must
     still be running five minutes later to take the commit that fixes it. This is the
     requirement that decides the process boundary: an updater that is part of ffbox goes
     down with ffbox, exactly when it is needed.

  3. STOP GRACEFULLY BEFORE UPDATING. No new containers while an update is pending; existing
     containers get their working time to finish and exit on their own; only then does the
     code on disk move. A container reading a shell script that changes underneath it is the
     race this avoids.

  4. RESUME AFTERWARDS. Queued work runs, and nothing needs a human to un-stick it. A drain
     that outlives the updater must lift itself.

Explicitly NOT a requirement: rolling back a bad update. The owner's call, 2026-08-22 — a
commit that breaks ffbox takes the box down until the next good commit lands, and requirement
2 is what makes that recoverable without touching the machine. No test gate, no reset --hard,
no held-back "known good" revision. This keeps the updater small enough to trust.


1. Verified facts
-----------------

Everything below is read out of this repository as it stands, not assumed.

  a. THE UNITS RUN THIS CHECKOUT DIRECTLY. ffwatch.service is
     `ExecStart=/usr/bin/env python3 @FFWATCH@ run`, with @FFWATCH@ substituted by
     06-services.sh at install time. There is no installed copy and no build step for the
     Python. New code on disk is live at the next process start and NOT before.

  b. ONE TARGET OWNS THE THREE SERVICES. ffbox.target carries
     `Wants=ffdiscord-listener.service ffwatch.service ffweb.service`, and each of the three
     carries `PartOf=ffbox.target`, which is what makes a stop or restart of the target
     propagate down. Wants= and not Requires=: a failed web UI must not take the pipeline
     with it.

  c. LAUNCHES ARE THREADS, NOT THE MAIN LOOP. Watcher.schedule() starts each turn on its own
     daemon thread and returns immediately; the loop keeps polling. In-flight work is
     therefore invisible to a process-level check and must be counted in the database.

  d. IN-FLIGHT IS ONE PREDICATE. Watcher.running_counts() reads
     `SELECT ... FROM run WHERE terminal_state IS NULL`. A run row is written before the
     container starts and given its terminal_state by finish_run when the container is gone,
     so that predicate is exactly "containers this machine still owns".

  e. A RUN CANNOT RUN FOREVER. Watcher.launch() calls subprocess.run() with
     `timeout = warmup_secs + agent_secs + 300` — 4800 seconds on the defaults (3600 + 900 +
     300). ffbox enforces its own three clocks inside that (WARMUP_TIMEOUT=3600,
     AGENT_TIMEOUT=900, VERIFY_TIMEOUT=1800, KILL_GRACE=10), and whichever fires first,
     finish_run still writes a terminal_state. The drain therefore has a computable ceiling
     rather than an open-ended wait.

  f. THE EXISTING KILL SWITCH IS TOO BROAD FOR THIS. `~/.config/ffbox/discord.disabled` gates
     BOTH Watcher.schedule() (launches nothing) and Watcher.send_pending() (holds every
     outbound row); a third reference, in Watcher.status(), only reports it. Draining wants
     the first and not the second: replies that in-flight runs produce should still reach
     Discord while we wait for those runs to end.

  g. TWO OF THE CONTAINER'S SCRIPTS ARE READ FROM THIS CHECKOUT AT RUN TIME. ffbox bind-mounts
     the --task script at /ffbox/task.sh:ro, and Watcher.launch() mounts ffverify.sh at
     /usr/local/bin/ffverify:ro. Neither is baked into the image; both are the working copy,
     live, for the whole life of the container. A merge while a container is running really
     does change the script under it. This is requirement 3's race, stated concretely.

  h. A STOP IS NOT FREE TODAY. ffwatch.service sets KillSignal=SIGTERM and
     TimeoutStopSec=120, and its own comment says an in-flight run is terminal-failed and
     requeued by the recovery pass on the next start. The container belongs to dockerd, not
     to the unit's cgroup, so it survives on the strength of ffbox's `docker stop` trap
     winning a race against that 120-second kill. Correct, but it costs a container.

  i. NON-INTERACTIVE FETCH ALREADY WORKS. origin is
     https://github.com/Final-Factory/final-factory-agents.git, credential.helper is `store`,
     and the owner's ~/.git-credentials exists. `git ls-remote origin` succeeds with no
     prompt. No new credential is needed; the updater must simply run as the owner.

  j. SYSTEMD'S DEFAULT START TIMEOUT IS 90 SECONDS. DefaultTimeoutStartUSec on this machine
     is 1min 30s. A Type=oneshot updater that drains for an hour is killed at 90 seconds
     unless TimeoutStartSec says otherwise. See section 7.


2. Architecture
---------------

Three new files, one new flag, two new subcommands. Nothing else moves.

  ffbox/update_ffbox.sh              all of the logic. POSIX sh, sibling to restart_ffbox.sh.
  ffbox/systemd/ffbox-update.service Type=oneshot, runs the script. THIS IS THE TRIGGER.
  ffbox/systemd/ffbox-update.timer   the schedule. Nothing else.

  ~/.config/ffbox/draining           the drain flag. Honored by ffwatch, written and removed
                                     by the updater. Outside the checkout, so a merge cannot
                                     touch it and a git-clean cannot delete it.

  ~/.config/ffbox/update.config-sha  (added 2026-09-02) one `name hash` line per start-time-only
                                     file — config.json and secrets.env — as the RUNNING
                                     services started on them. The second trigger.

  ~/.config/ffbox/update.applying    (added 2026-09-02) exists only between step 3a and the end
                                     of the run, and carries started_at and a one-line reason.
                                     Nothing in this design reads it: it exists so ffstatus can
                                     tell an update apart from the five-minute poll that finds
                                     nothing, which the unit being `activating` cannot. Removed
                                     on every exit path, stale ones cleared at step 1.

  ~/.config/ffbox/update.last-applied (added 2026-09-03) one line, `<epoch> <sha>`, written by
                                     the pass that actually fast-forwarded — never by a
                                     config-only restart. Read by ffstatus.sh and shown on
                                     ffweb's /status page beside the next scheduled check;
                                     see open question 1.

  ffwatch drain [--wait] [--timeout N]   write the flag; optionally block until quiet.
  ffwatch resume                         remove the flag.

One mechanism for both triggers (requirement 1): the timer's only job is to start
ffbox-update.service, and a human runs `sudo systemctl start ffbox-update.service`. Same unit,
same script, same environment, same log destination. There is no second path to test.


3. Independence
---------------

Requirement 2 is not satisfied by being a separate file; it is satisfied by four specific
choices, each of which is a way the updater could have been coupled and is not.

  1. THE TIMER IS ENABLED ON ITS OWN. `WantedBy=timers.target`, never ffbox.target.
     `systemctl stop ffbox.target` leaves it firing. This is the whole point: the update
     mechanism must outlive the thing it updates.

  2. NO Requires=, BindsTo=, PartOf= OR After= ON ANY FFBOX UNIT. Only
     `Wants=network-online.target`. A Requires= on a failed unit would refuse to start the
     one thing that can repair it, and PartOf= would let a target restart kill an update
     mid-merge.

  3. THE DRAIN CAN NEVER BLOCK THE UPDATE. Timeout, non-zero exit, Python traceback, ffwatch
     not running at all — every one of those logs and falls through to stop-update-start.
     Without this the failure mode is circular: a commit that breaks ffwatch.py on import
     also breaks `ffwatch drain`, and an updater that treats that as fatal can never install
     the fix. The drain is an optimisation over a hard stop, and is treated as one.

  4. THE UPDATER'S DEPENDENCIES ARE git, systemctl AND THE CHECKOUT. It imports nothing from
     ffbox, reads no ffbox configuration it cannot default, and needs no database. The one
     ffbox thing it calls — `ffwatch drain` — is covered by choice 3.

Consequence worth stating: the updater is trusted code that runs whatever the remote branch
says. `--ff-only` on a pinned branch is the containment, and section 8 covers the loop risk.


4. The drain protocol
---------------------

A NEW FLAG, NOT THE KILL SWITCH, for the reason in fact (f): draining must stop launches
without holding replies. ffwatch grows one check in schedule(), beside the existing kill-switch
check and with the same shape — log once on entry, clear the log latch on exit, return [].
Turns are still claimed and still queued while draining; they simply do not launch. Nothing is
lost, and the queue drives the work forward the moment the new code is up.

`ffwatch drain --wait --timeout N` writes the flag and then polls the predicate from fact (d)
until it reads zero. It writes only the flag file, never the database, so it does not violate
"ffwatch is the SOLE writer to ffwatch.db" — the daemon keeps writing, and this reads.

DRAINING DESTROYS THE IDLE STAGED CONTAINERS AND NOTHING ELSE. Revised 2026-09-01; it used to
destroy every container carrying the `ffbox.pool` label, and that label is set at creation and
survives the rename at dispatch, so the sweep included the one serving a turn. `pool_drop` then
removed the spool directory the run was writing into. See section 4a.

WHAT COUNTS AS QUIET IS NOT "NO CONTAINERS". Also 2026-09-01. A container is the first half of a
turn; the durable half runs on the host after it exits — ffbox harvests the work bundle out of
the run directory, and ffwatch's launch thread sweeps the transcript home, records the
verification, pushes the branch, opens the pull request and composes the reply. That is a
thread, not a queue, so `systemctl stop ffbox.target` in the middle of it loses the push.

And `run.terminal_state IS NOT NULL` does not mark the end of it: finish_run() records the exit
code first and publishes afterwards. The TURN row closes last, in finish_turn(). So the predicate
is three counts, exposed as `ffwatch quiet` (exit 0 when quiet, 1 while anything is left):

  runs      run rows with no terminal_state — a container this box still owns.
  turns     turns marked running — a launch thread still harvesting, pushing or replying.
            Queued turns are deliberately not counted: nothing launches under a drain, so
            waiting on one would never end.
  outbound  replies composed and not yet sent, and only those the sender will send by itself.
            Under approve_before_send a `pending` row waits on a person, possibly for days, and
            counting it would make every update on such a box wait out the whole window.

TWO THINGS THAT BOUND THE WAIT:

  * NO DAEMON, NO DRAIN. If ffwatch is not running, `drain --wait` returns at once. It decides
    that with the same flock probe Watcher.daemon_alive() already uses for `ffbox "prompt"` —
    trying to take the daemon's pid lock, not reading a pid. This matters because a daemon
    that was hard-killed leaves run rows with terminal_state NULL that nothing will ever
    settle; without this check the updater would wait the full ceiling for containers that
    died hours ago. That is precisely the broken-ffbox case requirement 2 exists for.

  * THE CEILING IS AN HOUR, and it is a policy rather than an arithmetic result. It used to be
    the computed one — from fact (e) no run outlives warmup_secs + agent_secs + 300, so the
    default was that sum plus slack, rounded to 7200 — but the number that matters is not how
    long a run can take, it is how long the box may go without the code somebody pushed. An hour
    covers any agent turn and all but the longest CI job.


4a. What happens at the end of the window
-----------------------------------------

THE UPDATE GOES AHEAD. Until 2026-09-01 it stood down instead and waited for the next tick,
which is the wrong trade on a box that is busy for hours at a stretch: the update that never
lands is often the one that would have fixed whatever is keeping it busy.

FORCING IS NOT KILLING. Every remaining container is PID 1 running a task whose trap harvests the
workspace out of a tmpfs and hands the Unity licence seat back, so the updater stops each one
with `docker stop --timeout` and a real grace (FFBOX_FORCE_STOP_GRACE, default 120 — the same
floor ffbox uses for its own timeout stops, which is the licence round trip). `rm -f` would run
neither trap, and the tmpfs is the only copy of the run's work.

Those stops then hand every launch thread a finished container, so the host gets a bounded window
of its own to publish what they released (FFBOX_FORCE_SETTLE_SECS, default 300). Publishing takes
seconds, not minutes; the point of waiting at all is that a forced update should give up on the
AGENT, never on the work the agent already did.

WHAT IT COST TO LEARN THIS. On 2026-09-01 the drain destroyed the pool container serving
conversation 30's turn 5, by label, while it was working. The forced removal missed the container
because dispatch had renamed it; the rmtree behind it did not. `out/` is host-owned and went —
result.json, stream.jsonl, the work bundle and the `.container-rc` ffbox scores the run from —
while `claude/` is 0700 under the container's subuid and survived, which is why the transcript
came home and nothing else did. The agent ran to completion and verified 774/774 clean. ffbox
found no exit code, scored the run 70, and the harness posted "the run failed / no branch — the
run changed no files" into the thread. Nothing was lost from git, because that turn changed no
files; a turn that had changed files would have lost them.

Two rules came out of it, and both are enforced by tests:

  * `out/owner` decides whether a staged container is busy. The `ffbox.pool` label cannot, and
    nothing may go back to asking it.
  * `pool_drop` refuses to delete a claimed spool. An operator naming one id by hand passes
    force=True and means it; nothing automatic may.

WHO REMOVES THE FLAG. Three places, deliberately overlapping, because a stranded flag means a
silently idle build server:

  * the updater, immediately before `systemctl start` — ffbox is stopped at that moment, so
    there is no window in which anything observes the removal;
  * the updater's EXIT trap, so a crash or a systemd timeout still lifts it;
  * the NEXT updater run, unconditionally, before it does anything else. The flock in section
    6 is what makes that safe: a resume can never land inside another updater's drain.


5. What happens after the merge
-------------------------------

A restart is only the right action for a pure Python or shell change, and the actions that are
NOT a restart are what makes "pull and restart" wrong as a general rule: a unit template is inert
until rendered, an image file is inert until rebuilt, a plugin is inert until the marketplace
cache is refreshed.

THIS USED TO BE A TABLE KEYED ON `git diff --name-only OLD_SHA..HEAD` — Dockerfile means rebuild,
plugins/** means registerAgents, systemd/** means 06-services. That table is a second,
hand-maintained model of what setup.sh already knows, and it is wrong the moment a commit moves a
file or adds a stage. Worse, it can only ever react to what CHANGED IN GIT: a config key added by
a commit, or a channel somebody added to the watch block by hand, has no diff to match and never
gets applied.

So the updater runs the real thing instead. Both of them, from the NEW tree, after the merge:

    sh ffbox/setup.sh          --non-interactive
    sh ffbox/runners/setup.sh  --non-interactive --skip-github --skip-image-build

Every stage is idempotent and no-ops when it is already satisfied, so on a machine that is set up
this is a few seconds and a lot of "already exists"; on one that is behind it is exactly the
commands a human would have run. The second call is what makes ffgithubrunners deploy itself: its
egress allowlist, its networks and its git mirror are in this tree too, and before it they were
merged and then applied by nobody.

  --skip-image-build       because ffbox/03-build.sh in the first call has just built that exact
                           tag from that exact Dockerfile. One cached rebuild, not two.
  --skip-github            because that stage verifies the credential by minting a real JIT config
                           and deleting the runner it created. Right for a human setting a machine
                           up, pointless noise on the org's runner list once per commit.

NOTHING IN THE SECOND CALL MAY DISTURB A RUNNING JOB, and that is a constraint on the scripts it
calls rather than on the updater. Only ffbox is drained above; ffgithubrunners is not, because
waiting for a Unity job would hold the whole update for up to ninety minutes. So `egress up` and
the git mirror are fingerprinted — image id, mode, allowlist checksum — and leave a healthy
container alone rather than recreating it under a job that is mid-fetch. An unconditional recreate
anywhere in that path puts this back.

WHAT NEITHER CALL DOES IS ROOT. --non-interactive skips the stages that need it and prints what is
owed, so a commit that changes a unit template is live everywhere except the units until somebody
runs `sudo sh ffbox/06-services.sh --install` or `sudo sh ffbox/runners/05-services.sh --install`.
That is the deliberate cost of an updater that fetches code off the internet and then executes it
holding no root.

  discord-task.sh, ffverify.sh   restart alone, but see fact (g): these two are MOUNTED from
                              the checkout, not baked, so the new copy is in effect for the
                              next container with no rebuild — and would have been in effect
                              mid-run without the drain.

  slot.sh, runners/lib/**     no restart to give: a slot supervisor is a long-lived process that
                              the pool may leave WAITING for hours. It stamps the mtime and size
                              of its own two files at start and exits when either changes, which
                              costs nothing — a waiting slot holds no container, no registration
                              and no lock — and systemd starts it again on the new code.


6. Sequence
-----------

  0. re-exec from a temp copy of self
  1. flock, or exit 0                      (a trigger during a running update exits, section 7)
  2. ffwatch resume                        (lift a flag stranded by a previous run)
  3. git fetch --prune origin; exit 0 if:
       kill switch present | working tree dirty
       | HEAD == origin/BRANCH AND config.json + secrets.env hash to update.config-sha
  3a. write update.applying                 (the boundary: every exit above it changed nothing)
  4. ffwatch drain                         (sets the flag, drops the idle staged containers)
     then poll: busy containers, then `ffwatch quiet`, up to FFBOX_DRAIN_TIMEOUT
     at the ceiling: docker stop each straggler, let the host settle, go on (section 4a)
  5. systemctl stop ffbox.target
  6. OLD_SHA=$(git rev-parse HEAD); git merge --ff-only origin/BRANCH  (skipped if the trigger
                                                                       was the config alone)
  7. act on the diff (section 5)
  8. rm the drain flag; write config.json's hash to update.config-sha, and — only when step 6
     merged something — the epoch and new sha to update.last-applied
  9. systemctl start ffbox.target
 10. report each unit's state and OLD_SHA -> HEAD
 11. rm update.applying                    (on the EXIT trap, so a crash at any step above
                                            does it too)

STEP 0 IS NOT OPTIONAL. `sh` reads a script incrementally, by byte offset. Step 6 rewrites
update_ffbox.sh underneath the running shell, which can resume in the middle of different
text. Copy self to a temp file and `exec` it with a marker variable set; the copy is what
survives the merge. This also gives steps 7 and 9 clean access to the new tree.

STEP 3 COMES BEFORE STEP 4 for cost: the common case is "nothing new", and that case must not
drain the pipeline. It is a fetch and a rev-parse, nothing more.

STEP 3 ASKS TWO QUESTIONS, NOT ONE (added 2026-09-02). Two files reach a service only through a
process start. config.json is read once per process — ffwatch's main() calls load_config() and
the daemon then runs for weeks off that dict — and secrets.env is read once per start, by
systemd, as the EnvironmentFile= of all three units. So an edit to either is exactly as
undeployed as an edit to a .py file, and neither is in git, so the SHA comparison never saw them.
On 2026-09-02 an ffwatch that started at 04:18 was still holding the config as it stood before a
04:25 edit, and would have held it until an unrelated commit happened along. So the updater
hashes both and compares them against update.config-sha, and either trigger runs the SAME pass;
the merge in step 6 is the only part that is conditional.

  * A HASH, NOT AN MTIME. Step 7 re-runs setup.sh, whose config stage is setdefault the whole
    way down, so config.json is rewritten on every pass. An mtime trigger would restart the box
    every tick. Confirmed the same day: the 04:35 pass left config.json with an 04:35 mtime and
    an unchanged hash.
  * ONE LINE PER FILE, `name hash`, so the journal can say WHICH file changed — the first thing
    an operator reading that line wants to know — and so that adding a file to the watched set
    is a non-event rather than a restart on every box.
  * NOT the runners' ~/.config/ffbox/githubrunners/secrets.env. It is sourced per invocation by
    the ffgithubrunners CLI rather than held by a daemon, and its slots live in
    ffgithubrunners.target, which this script does not restart.
  * THE STAMP IS WRITTEN AT STEP 8, not at step 3. The drain can take an hour, and a config
    edited during it is picked up by the step-9 start; stamping the step-3 value would spend a
    second full drain-and-restart on settings that are already live. Written before the start
    rather than after, so a start that fails does not leave the box owing a restart nothing
    will ever tell it about.
  * A LINE THE STAMP HAS NEVER CARRIED IS NOT A CHANGE. A fresh machine, a deleted stamp, a
    newly watched file, or the single-hash stamp written before secrets.env joined the set: all
    are recorded, none restarts anything. The alternative spends one whole drain on a file
    nobody touched, on every box, once per addition.
  * A MISSING OR UNHASHABLE config.json answers with a CONSTANT ("absent"), never the empty
    string: the comparison is for inequality, and an empty answer differs from every stored
    value forever — a box with no config restarting itself every five minutes.
  * THE DIRTY-TREE REFUSAL COVERS THIS TRIGGER TOO. It is the same guard in the same place, and
    a config edit does not get to bypass "someone is working on this checkout".

A DIRTY TREE IS REFUSED, NEVER STASHED OR RESET. The working copy is someone's workspace; the
updater has no business deciding that uncommitted work is expendable. Consequence to accept
rather than design around: on a machine where someone is actively editing, auto-update stops
until that work is committed, and says so once per tick.


7. Failure modes
----------------

  ffwatch is dead                  drain returns immediately (section 4); update proceeds.
  ffwatch.py is broken by a commit drain fails or crashes; logged; update proceeds. The next
                                   good commit lands on the next tick. This is requirement 2.
  drain times out                  logged with the number of runs still live; stop proceeds,
                                   and those runs are terminal-failed and requeued by
                                   recovery on the next start — the pre-existing behaviour,
                                   not a new loss.
  the merge is not a fast-forward  logged; nothing stops, nothing restarts, no services are
                                   touched. A diverged local branch is a human problem.
  06-services.sh / 03-build.sh
    fails                          logged; the restart still happens, so the box comes back on
                                   the new Python even if the image or the units did not move.
                                   Half-updated and running beats consistent and down.
  a unit fails to come back        reported per unit. `systemctl restart` exits 0 for a Wants=
                                   member that died (fact b), so the script asks each unit
                                   what it is rather than trusting the restart's exit code.
  the updater is killed mid-drain  the EXIT trap lifts the flag; if even that is missed, the
                                   next tick's step 2 does.
  two updaters at once             the flock serialises them; the second exits rather than
                                   queueing behind a possibly hour-long drain.
  a container outlives the stop    the one case the drain does not fully close, and it is
                                   pre-existing. Watcher.recover() skips a non-terminal run
                                   whose container is still live, so an orphan left by fact
                                   (h)'s race keeps its run row at terminal_state NULL — and
                                   recover() runs once at daemon start, not per pass, so
                                   nothing settles the row when that container later exits.
                                   The row then counts as in-flight forever: it eats a slot
                                   against max_concurrent_runs, and the NEXT drain waits the
                                   full ceiling for a container that is already gone. The
                                   drain makes this rarer by emptying the machine first; it
                                   does not fix it. See open question 5.

SYSTEMD'S 90-SECOND DEFAULT (fact j) would turn a normal drain into the "killed mid-drain" row
above, every time, on a busy machine. TimeoutStartSec on ffbox-update.service is therefore set
explicitly to the drain ceiling plus fifteen minutes of slack: 8100 seconds. Not `infinity` —
a wedged updater holding the flock forever is worse than one that gets killed and retried,
because the flock is what keeps the next tick from starting.


8. Configuration and privilege
------------------------------

  branch                pinned in the script, default `master`, overridable by
                        FFBOX_UPDATE_BRANCH. Not "whatever is checked out": the updater
                        auto-executes what it pulls, and the branch is part of that trust.
  merge                 `--ff-only`, always. Never rebase, never a merge commit, never a
                        `reset --hard` onto the remote.
  kill switch           ~/.config/ffbox/update.disabled. Its own file, not discord.disabled:
                        pausing replies and pausing code updates are different intents, and
                        the second is what a human debugging on the box wants.
  cadence               OnBootSec=5min, OnUnitActiveSec=5min, RandomizedDelaySec=1min,
                        Persistent=true so a machine that was off catches up.
  drain timeout         FFBOX_DRAIN_TIMEOUT, default 3600 (section 4).
  forced stop grace     FFBOX_FORCE_STOP_GRACE, default 120 (section 4a).
  forced settle window  FFBOX_FORCE_SETTLE_SECS, default 300 (section 4a).

PRIVILEGE. Revised 2026-08-25; this section used to say the opposite and the reasoning was
wrong. The unit runs as @USER@, unprivileged, and reaches for root exactly twice, through
`sudo -n systemctl` for `stop ffbox.target` and `start ffbox.target`. 02-zfsSetup.sh grants
those two invocations by name in /etc/sudoers.d/ffbox and nothing else.

What the old text called an argument against that — "adds a permission file to maintain and
gains nothing" — had it backwards. The thing that fetches code off the internet every five
minutes and then executes it is the last process on this box that should begin with root and
hand privilege away, and the permission file is the artefact that says, in one readable place,
precisely how much it may take back. Installing a unit is deliberately NOT in it: writing
/etc/systemd/system defines a unit that runs anything as anyone, which is root by another name.
A unit-template change waits for a human running `sudo sh ffbox/06-services.sh --install`, and
the updater says when that is owed.

`sudo -n`, never bare sudo: a rule that is missing must fail in a log line rather than block
forever on a password prompt nobody is there to answer.

Two things that used to break when this ran as root, kept here because the reasons still shape
the script:

  * ROOT-OWNED OBJECTS IN .git. When root ran the fetch and merge, new objects landed
    root-owned and every later `git pull` by the owner failed on permissions. Running as the
    owner removes the failure mode rather than working around it.
  * HOME. `runuser -u USER --` does NOT reset HOME, so git read root's configuration and missed
    the owner's ~/.git-credentials — and fact (i) is the only reason the fetch works
    unattended. HOME is still set explicitly by the unit, which now simply matches the user it
    already runs as.

as_owner() keeps a runuser branch for the one path that can still arrive here as root (a human
running the script by hand under sudo); as the owner it is a straight call.

registerAgents.sh writes into the owner's ~/.claude, which is now simply where it runs.
03-build.sh needs docker, and since 2026-08-25 that is the ROOTLESS daemon owned by @USER@ —
root has no ffbox images at all. See design/rootless_docker_design.txt.

THE LOOP RISK. This repository is also where the Discord dev lane's work lands. That is safe
today because discord-dev-agent opens pull requests and never merges, so nothing reaches
`master` without a human. If anything ever auto-pushes to the pinned branch, an auto-pulling
build server turns that into a code-execution loop. `--ff-only` on a pinned branch is the
containment, and this paragraph is the reason not to relax it.

10. Open questions
------------------

  1. SHOULD AN UPDATE BE VISIBLE IN ffweb? Answered 2026-09-03, and smaller than the row this
     question imagined. No table and no migration: the updater stamps update.last-applied when
     it merges, ffstatus.sh reads that plus the timer's next elapse out of systemd, and both
     land on /status's header line as "last update 2h07m ago (sha) · next check in 4m". LAST
     APPLIED, NOT LAST CHECKED, which is the number the timer makes easy and nobody wants: the
     timer looks every five minutes and finds nothing almost every time, so a "last checked"
     clock reads five minutes old on a box three days behind master. Old sha and outcome stay
     in the journal — they are what you read when something went wrong, and the page is what
     you read to find out whether anything did.

  2. SHOULD THE UPDATER ANNOUNCE ITSELF IN DISCORD? Tempting and cheap, and wrong by the rule
     the pipeline already holds: the host composes, and an update is not a reply to anyone. If
     it happens it belongs to a future dev-chat escalation path, not to this script.

  3. IS 5 MINUTES RIGHT? It started at fifteen, chosen to be small against a drain that can
     take an hour and large against a fetch that costs nothing. Fifteen turned out to be the
     wrong side of that trade in practice — the wait to see a pushed fix live on the box is
     what people actually feel — so the cadence is five. A fetch with nothing to take exits
     before the drain, so the extra passes cost one `git fetch` each and nothing else.
     OnUnitActiveSec is still the only knob that needs to move.

  4. WHAT ABOUT THE GAME REPO? ffbox clones it per run at a pinned ref; nothing here updates
     it, and nothing should. Named so it is not mistaken for an omission.

  5. SHOULD recover() RUN EVERY PASS? Found while writing this document, and not caused by it:
     a run row whose container outlived a stop is skipped by recover() and then never revisited
     because run() calls recover() once, before the loop. once() does call it every pass, which
     is why the offline suite never sees this. A per-pass sweep would settle those rows and
     make the drain's predicate honest, at the cost of a `docker ps` per pass. It belongs to
     ffwatch, not to the updater, and should be decided on its own rather than smuggled in
     with this.


11. Phasing
-----------

  PHASE 1  the drain: the flag, schedule()'s check, `ffwatch drain` and `ffwatch resume`,
           with tests. Useful on its own — it is the graceful stop that restart_ffbox.sh
           does not have.
  PHASE 2  update_ffbox.sh and the two units, installed AND enabled by 06-services.sh.
           Revised during implementation: the script's own rule is that installing a unit and
           leaving it stopped is a half-finished job, and carving out an exception for this one
           would mean the enable step is the one nobody tests. `--dry-run` and
           ~/.config/ffbox/update.disabled are how you hold it off instead, and both are
           cheaper than a flag that exists for one afternoon. Paths to exercise by hand:
           nothing-new, dirty-tree, kill-switch, not-a-fast-forward, drain-times-out,
           ffwatch-already-dead.
  PHASE 3  watch one real update land, then one deliberately broken commit, and confirm the
           next good commit recovers the box without anyone touching it.

Phase 3 is the only one that proves requirement 2, and it is the reason to do the broken
commit on purpose rather than waiting to meet it by accident. Until it has been done, the
recovery story is a design claim and not a tested one.
