# ffgithubrunners egress allowlist — the ONLY hostnames a job may reach.
#
# One name per line. A bare name matches exactly; a leading "*." matches any subdomain of it (and
# not the bare domain — list that separately if it is needed). Blank lines and # comments are
# ignored. Anything absent is refused at the SNI, with the attempt logged.
#
# THIS IS NOT ffbox's LIST, and the difference is the point. ffbox's has no GitHub entry at all,
# deliberately: its container never pushes, the host does. CI has to reach github.com, the Actions
# broker, LFS, artifact storage and the cache service, and putting those on ffbox's list would
# hand ffbox's containers a reach they do not have today. Two instances of the same script, two
# lists.
#
# Nothing Anthropic is here. A job runs a workflow, not an agent.
#
# docs/egress.md is the reference: how a name is decided, the two ways one is refused, and why a
# refused host can leave no trace in the SNI log.
#
# HOW TO ADD SOMETHING. Do not guess. Put the proxy in log mode for a few real jobs —
#     FFBOX_EGRESS_MODE=log sh ffbox/runners/03-image.sh --egress-only
# — which permits everything and records every destination, then read the SNIs back out:
#     sh ffbox/runners/03-image.sh --egress-log
# Add what the jobs actually asked for, restart in enforce mode, and confirm nothing new appears.
#
# THE IMAGE BUILD IS NOT BEHIND THIS FENCE. `docker build` uses the daemon's default network, so
# pulling the base image, the runner tarball and gh is unfiltered. Nothing build-time belongs
# here, and a failing build is never a reason to add a line.

# REMOVED 2026-08-31: github.com, api.github.com, github-cloud.githubusercontent.com.
#
# All three went because a job stopped NEEDING them, not because they were filtered. That is the
# difference that matters: an SNI fence cannot restrict github.com to one repository -- the repo
# lives in the URL path, inside the TLS -- so while any of these were reachable, hostile test code
# could push to its own repo or POST to /gists with a credential of its own. Measured from a live
# runner while they were still listed: api.github.com/repos/torvalds/linux answered 200 and
# /gists answered 200.
#
#   github.com + github-cloud   The repository and its LFS objects now come from ffghr-gitmirror
#                               on this network: git daemon for objects, a download-only LFS batch
#                               server beside it. The runner image rewrites the GitHub URL with
#                               url.<mirror>.insteadOf, so actions/checkout never knows. There is
#                               no repository but ours at the other end, so "restricted to our
#                               repo" is a property of what exists rather than a rule to maintain.
#   api.github.com              Used by NEITHER the runner NOR any action -- only by our own two
#                               scripts. post-check-run.py now hands its payload to the supervisor,
#                               and mode2Freshness moved to ubuntu-latest, off this fence entirely.
#
# WHAT BREAKS IF THE MIRROR IS DOWN: every job, immediately and loudly, because there is no longer
# a fallback. That is deliberate -- a silent fallback to GitHub is exactly what hid the mirror
# serving only master for a day -- but it makes ffghr-gitmirror load-bearing. It is
# --restart unless-stopped and 03-image.sh brings it up.

# --- actions/cache and actions/upload-artifact ----------------------------------------------------
# CONFIRMED 2026-08-29: upload-artifact went to productionresultssa5.blob.core.windows.net. Sixteen
# distinct shards have been seen since — sa0, 2, 4-14, 16-18 — which is why this cannot be a list.
# main.yml restores a Library cache and uploads two artifacts on every job, so if this were wrong
# the failure would be loud rather than subtle.
#
# A REGEX AND NOT `*.blob.core.windows.net`, and this is the most important line in the file.
# blob.core.windows.net is a MULTI-TENANT namespace: an Azure storage account name is claimed
# first-come by anyone with a free account. The wildcard therefore permitted `<attacker>.blob.
# core.windows.net` — an open, unauthenticated, high-bandwidth path out of the fence that had
# nothing to do with GitHub and would not have been closed by any amount of GitHub filtering.
#
# Contrast *.actions.githubusercontent.com and *.githubusercontent.com above, which stay wildcards
# and are fine as wildcards: GitHub owns those DNS zones, so no third party can put a name under
# them. Vendor-controlled namespace, safe. Customer-controlled namespace, not.
#
# Non-matching names under the suffix still resolve here and are refused by nginx, so an attempt
# lands in the SNI log with the name it asked for. See docs/egress.md.
# REMOVED 2026-09-02: the productionresultssa* regex, and with it every path to blob storage.
# PUT BACK THE SAME DAY, NARROWED -- see RESTORED below. The reasoning here is kept because the
# half of it about the namespace is still why the replacement looks the way it does.
#
# It was the last entry a job needed for anything but the Actions runtime, and it was the most
# dangerous line in this file. `[0-9]{1,2}` admits 110 names -- sa0-sa9 AND sa00-sa99 -- and eleven
# of those were UNREGISTERED when checked on 2026-09-01: sa00 through sa09, which GitHub will never
# use because it does not pad its shard numbers, and sa22. Ninety-nine resolved; those eleven
# returned nothing from two public resolvers, with a control lookup ruling out a wildcard zone.
#
# An Azure storage account name is free and claimed first-come. Anyone could have registered one of
# the eleven and owned an allowlisted, unauthenticated, high-bandwidth HTTPS endpoint reachable
# from every CI job on this box, with no GitHub credential involved and nothing in the SNI log to
# tell it from an ordinary artifact upload. That is the exact failure the regex replaced a bare
# *.blob.core.windows.net to prevent, surviving because narrowing the namespace did not empty it.
#
# It is gone because NOTHING NEEDS IT, not because it was narrowed further. actions/upload-artifact
# was the only user; actions/cache stopped using blob when the host ffcache replaced it, and the
# coverage upload had never uploaded anything at all. main.yml now hands its artifact to the
# supervisor, which uploads it on the job's own credential from a host that is on the open internet
# regardless, and refuses any repository_id not on its list. See docs/ci-egress-exfiltration-audit.md.
#
# SOMETHING STILL ASKS FOR BLOB, AND IT IS NOT THE ARTIFACT. Measured on the first job after this
# removal, 2026-09-02: 64 A-queries for productionresultssa17.blob.core.windows.net from the job
# container, every one NXDOMAIN. They begin two seconds into the job -- before any workflow step --
# recur every few seconds for its whole life, and stop when it ends. That is the RUNNER retrying,
# not a step, and one shard hammered rather than the thin spread across nineteen that normal use
# produced. Most likely a Results API object: the step summary or the log archive.
# ANSWERED LATER THE SAME DAY: the log archive. See RESTORED below.
#
# NOTHING HAS BROKEN YET -- true of the job, false of the record it left behind, and the distinction
# is the whole lesson. That job Succeeded, the tests ran, the check run posted and the artifact
# uploaded through the host, so every signal this file knew how to read said the removal was clean.
# Its logs were already gone. "Find out what degrades" only works if you are watching the thing that
# degrades, and nothing here was watching the log.
#
# WHERE TO LOOK, AND IT IS NOT THE DENY SINK. This file said "the name appears in the deny sink with
# upstream=127.0.0.1:9", and that was wrong in a way that cost an hour of believing the removal was
# clean. A name is only refused BY NGINX if some allowlist entry's suffix resolves it here; with the
# blob entry gone entirely, these die at DNS and produce no sni= line at all. The deny sink was
# empty and 64 refusals had already happened. docs/egress.md, "the two ways a name is refused", is
# exactly about this trap. Read BOTH halves:
#     sh ffbox/runners/03-image.sh --egress-log     # allowed, deny-sink, AND the NXDOMAIN names
#
# Live logs are not at risk: they ride *.actions.githubusercontent.com, measured at 271 connections
# to pipelinesghubeus14 across roughly 55 jobs, and that entry is not going anywhere.

# RESTORED 2026-09-02, NARROWED, AND FOR NOW. What needed this entry is the job LOG.
#
# WHAT THE REMOVAL COST. Opening a finished job's logs in the Actions UI returns
# <Code>BlobNotFound</Code> from Azure -- an answer about a blob the runner never got to write. That
# settles the question the removal left open. The 64 A-queries for productionresultssa17, starting
# two seconds into a job before any workflow step, recurring every few seconds and stopping when the
# job stopped, were the runner streaming its own log to a Results API blob.
#
# WHY THIS CANNOT BE MOVED TO THE HOST the way the artifact was. upload-artifact was a WORKFLOW
# STEP, so it could be deleted and the supervisor could do the PUT while the job waited on
# artifact.done. The log has no step to intercept: Runner.Worker uploads it itself, from inside the
# container, with Azure.Storage.Blobs.dll shipped in /opt/actions-runner/bin. Nor can the supervisor
# do it afterwards -- slot.sh already records what the Results API tells a finished job,
# `403 permission_denied, "job is completed"`. There is no seam here, only the runner.
#
# FOR NOW, because the replacement is host-side capture rather than a better regex. The runner reads
# ACTIONS_RUNNER_PRINT_LOG_TO_STDOUT (confirmed in Runner.Common.dll, runner 2.337.0, in
# ffbox:latest); with it set on the job container, the `docker logs -f` that slot.sh already runs
# picks up the whole job log instead of the six listener lines it captures today. That gets the log
# onto the host with no egress at all, and the supervisor can hand it to the existing
# artifact-upload.py channel to put it on the run page. When that lands, this entry goes again.
#
# WHY THIS QUANTIFIER AND NOT THE OLD ONE. `[0-9]{1,2}` admitted 110 names, sa0-sa9 AND sa00-sa99,
# eleven of which resolved nowhere and were free for anyone to claim. `(0|[1-9][0-9]?)` admits 100:
# the padded sa00-sa09 are gone STRUCTURALLY rather than because they happened to be unregistered on
# the day someone looked, since GitHub does not pad its shard numbers. `(?!22\.)` removes the one
# unpadded name that still resolves nowhere. Swept 2026-09-02 from this box, all hundred:
#
#     for n in $(seq 0 99); do h=productionresultssa$n.blob.core.windows.net; \
#         getent hosts "$h" >/dev/null || echo "claimable: $h"; done
#
# sa22 was the only line it printed. sa100 is NXDOMAIN too, so two digits is still the whole
# namespace. RE-RUN THAT SWEEP whenever this entry is touched, and read a new name in its output as
# an open door rather than a curiosity: every name this regex admits is an unauthenticated,
# high-bandwidth HTTPS endpoint the moment the wrong person owns it.
#
# WHAT THE SWEEP DOES NOT PROVE. A name that resolves is owned by SOMEONE, and nothing visible from
# out here says that someone is Microsoft. Only the nineteen shards real jobs have actually used
# have positive evidence behind them. They are deliberately NOT written out as exact entries: a
# shard GitHub adds next month would then lose its logs silently, which is the failure this whole
# block is a record of.
#
# IF LOGS GO MISSING AGAIN it is a shard this regex does not admit, and THIS TIME the deny sink is
# the right place to look. blob.core.windows.net resolves here again while this entry exists, so a
# non-matching name reaches nginx and is logged with the name it asked for at upstream=127.0.0.1:9
# -- which is exactly why the suffix goes to dnsmasq rather than being left to NXDOMAIN. A
# three-digit shard is the one exception, dying at DNS with no sni= line. Read both halves:
#     sh ffbox/runners/03-image.sh --egress-log     # allowed, deny-sink, AND the NXDOMAIN names
~^productionresultssa(?!22\.)(0|[1-9][0-9]?)\.blob\.core\.windows\.net$   blob.core.windows.net
