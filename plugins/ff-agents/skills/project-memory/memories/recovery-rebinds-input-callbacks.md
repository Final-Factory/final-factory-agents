# Snapshot recovery rebinds live input callbacks

Snapshot application reuses player presentation state rather than building it from scratch. `SaveGameManager.SetupPlayersAndControllers` routes through `PlayersManager.LinkAllPdcToEntitiesImpl` (`Assets/Scripts/PlayerController/PlayersManager.cs:278-296`), which can retain an existing `PlayerDataController`. `PlayerDataController.FinishSetupWithoutAddingOrConstructingPlayer` (`Assets/Scripts/PlayerController/PlayerDataController.cs:479-505`) then calls `PlayerController.SetupController` again (`Assets/Scripts/PlayerController/PlayerController.cs:103-109`) on the existing `StateActions` collection. Any event wiring performed by `StartNewGame` must therefore be idempotent: retain the exact publisher instance, detach before rebinding, and detach again from `DestroyAction`.

`-=` removes only one matching subscription. Repeated `+=` registrations leave callbacks alive after later destruction. Remote actions also subscribe: `StateAction.Run`'s local-player filter limits frame updates, not event callbacks. The `a9c1488e4` inventory-action repair guards the actual hotbar callback with `LocalPlayerReady` and `Me == DataController`; an icon appearing is not acceptance evidence.

Test the live click path after forced resync, reconnect, and another forced resync. In the two-Mac `.11` run, `live-hotbar-binding-fixed011/hotbar` passed the correct two-structure preview and all three clicks; the prior build failed on reconnect with a dead-entity `IsBlueprintActive` stack. The automated suite reported 3777 passed, 0 failed, 16 ignored. Do not broadly change netcode despawn behavior for this presentation-subscription leak.
